# Workspace Rules

## 1. File Path & Link Specification (文件与链接路径规范)
- **严格使用项目相对路径**：知识库项目内的所有文件引用、文档关联链接（Markdown Links）以及说明文本中的路径，**必须且只能使用项目级别的相对路径**（例如 `./01_Inbox/03-K8S/04-集群网络/05-1-Ingress基础全景与进化延伸指南.md` 或相对当前文件的相对路径 `./xxx.md`）。
- **严禁使用绝对路径**：禁止使用任何包含特定用户本机主机的绝对路径（例如 `/Users/hexianghong/...` 或 `file:///Users/hexianghong/...`），以保证知识库在不同设备与部署环境下的可移植性与通用性。

## 2. Directory README Specification (目录 README 规范)
- **每个目录必须包含 README.md**：知识库内的**每一个文件夹**（包括根目录及所有子目录）都必须有一个 `README.md` 文件。
- **内容要求**：`README.md` 须列出并简要说明当前目录下**所有一级子目录或文件**的名称与用途，格式示例如下：
  ```markdown
  # 目录名称

  ## 目录说明
  简要描述本目录的整体用途。

  ## 内容索引
  | 名称 | 类型 | 说明 |
  |------|------|------|
  | ./子目录A/ | 目录 | 说明A |
  | ./文件B.md | 文件 | 说明B |
  ```
- **用途**：README.md 是 AI 导航知识库的核心索引，AI 在查找文件或分析项目结构时，应**优先读取**目标目录的 README.md，而非直接扫描全部文件内容。
- **及时更新**：每当目录下新增、删除或重命名文件/子目录时，必须同步更新对应的 `README.md`。

## 3. Temporary File Specification (临时文件规范)
- **优先在项目根目录或指定临时目录下创建**：创建任何执行脚本、辅助工具或中间临时文件时，**优先且必须在当前项目工作区内创建**（如项目根目录下的临时脚本、`./scratch/` 或 `./tmp/`），严禁使用项目外部路径或系统级临时目录（如 `/tmp`、`/var/tmp` 等），并在使用完毕后及时清理。

## 4. Cross-Document Reference Specification (跨文档技术点关联跳转规范)
- **网状知识关联原则**：编写或更新任何技术文档时，若内容中涉及、对比或依赖知识库中其他已有文档的技术点（如组件通信、运行时 CRI、网络插件 CNI/Calico/Flannel、服务发现 CoreDNS/kube-proxy、存储 CSI/Ceph、优雅停机/无损发布、安全准入、可观测性监控等），**必须建立可点击的相对路径跳转链接**。
- **正文内联自然引用**：在正文中首次提及关键概念、技术选型对比或时序流程流转时，将概念关键词直接加挂相对路径链接（如 `[Calico BGP 路由](../04-集群网络/02-1-Calico架构与calico-node及kube-controllers深度剖析.md)` 或 `[CRI 运行时接口](./04-Kubelet/CRI.md)`），避免在代码块和行内代码内建立破坏性链接。
- **标准化章末卡片**：技术专题文档末尾统一提供标准的 GitHub 风格提示块 `> [!TIP] 💡 关联技术与延伸阅读`，列出 2~5 篇强相关前置原理、底层实现或进阶实战文档的相对路径，形成闭环知识链。格式规范如下：
  ```markdown
  ---

  > [!TIP] 💡 关联技术与延伸阅读
  >
  > * [前置原理文档标题](相对路径.md)
  > * [底层实现/协作组件文档标题](相对路径.md)
  > * [进阶实战/调优排障文档标题](相对路径.md)
  ```
- **相对路径与有效性校验**：所有跳转链接必须精确计算相对当前文档目录的有效相对路径，严禁使用本机绝对路径（如 `/Users/...`），杜绝 404 死链。

  - 变更与运维规程：使用 [`./07_Templates/03_生产环境运维SOP标准模板.md`](../07_Templates/03_生产环境运维SOP标准模板.md)
  - 技术选型评估：使用 [`./07_Templates/04_技术选型与对比评估模板.md`](../07_Templates/04_技术选型与对比评估模板.md)

## 6. SRE & Database Disaster Recovery Rules (数据库与集群运维红线)
- **生产环境资产未清严禁写操作红线 (Zero-Write Before Full Assessment)**：排查生产环境复杂故障（尤其是数据库、有状态服务、存储卷）时，**严禁在未摸清底层资产、拓扑关系与存活状态前执行任何写操作（如强杀进程 `kill -9`、删除锁文件 `rm -f *.lock`、变更配置、重启/驱逐控制器等）**；必须严格坚持“全量只读取证先行 $\rightarrow$ 摸清底层进程、网络监听、数据卷归属 $\rightarrow$ 编写带回滚预案的详细说明方案 $\rightarrow$ 用户审批确认”的生产红线，杜绝任何破坏性盲目试错。
- **MGR 单节点恢复原则**：MGR 集群执行物理恢复时，**严禁在多节点同时执行恢复脚本**；只需在 Node1（主节点）单机恢复后执行 `dba.createCluster('myCluster', {force: true})` 引导集群，Node2 / Node3 必须通过 `cluster.addInstance(..., {recoveryMethod: 'clone'})` 自动物理克隆入群。
- **无主键表治理规范**：MGR 环境中所有表必须具备主键。遇到历史无主键表时，使用 `PRIMARY KEY INVISIBLE`（不可见自增主键）或执行 `./05-Install/mysql/mysql8.0.43_huazhuo_prod/mysql_mgr_fix_pks.sh` 进行治理，禁止对业务产生字段侵入。
- **Router 重新引导规范**：集群强制重建（`createCluster force`）后，MySQL Router 必须重新执行 `--bootstrap ... --force`，方可启动服务。

## 7. Multi-Version Configuration File Specification (多版本配置文件管理规范)
- **单文件双轨内嵌原则**：工程部署包（如 `./05-Install/`）中遇到因软件大版本断代、内核演进或不同平台体系（如 MySQL 5.7 vs 8.0/8.4、K8s 1.21- vs 1.25+、Docker vs containerd、原生 K8s vs Rancher）导致的配置差异时，**严禁无序拆分多个同质化 YAML 文件**，统一采用**单文件双轨/多版本内嵌交付模式**。
- **排版与高亮结构规范**：
  - **当前生产推荐版本**：作为默认生效项直接呈现；
  - **备用/过渡版本**：作为注释项紧随其后呈现；
  - 必须使用标准化的分隔线与中英文标签明确标注版本属性，示例：
    ```yaml
    # -------------------------------------------------------------
    # 【当前生效：containerd 运行时 (K8s 1.24+ 现代化标准)】
    # -------------------------------------------------------------
    - "--containerd=/run/containerd/containerd.sock"
    # -------------------------------------------------------------
    # 【注释备用：传统 Docker 运行时 (K8s <= 1.23)】
    # -------------------------------------------------------------
    # - "--docker=unix:///var/run/docker.sock"
    ```
- **文件末尾必须附加说明规范**：所有包含版本差异的配置文件，**必须且只能在文件最末尾附加统一标准格式的 `# 📝 版本差异与切换说明 (Version Compatibility Notes)` 代码块**，详细说明：
  1. **版本断代背景**（为何存在差异，涉及的底层内核/API/互斥锁等）；
  2. **切换操作指引**（如何解除/添加注释完成 1 秒平滑切换）；
  3. **避坑与风险警告**（误用版本可能造成的 Pod 崩溃、扫盘或全局锁等后果）。
- **用户裁决优先原则**：遇到版本差异时，AI 助手**严禁擅自单方面决定唯一版本**，必须全面梳理版本差异对照清单，提请用户裁决哪个版本为生效项、哪个版本为注释项后，方可执行更新。
- **底层理论联动规范**：在配套的技术深度专题文档（`01_Inbox/...`）中，必须开辟专门章节从底层原理、数据结构与锁机制维度深度论证版本配置差异的根因，形成“工程配置有指引，技术文档有原理”的双向闭环。

## 8. Document Delivery Quality & Syntax Verification Specification (文档交付质检与语法校验硬性规范)
- **交付前硬性自检红线（Mandatory Quality Gate）**：任何技术文档、SOP 规程或部署配置编写/修改完成后，**必须作为不可跳过的硬性卡点**执行全量自检自查，严禁未经验收直接交付。
- **Mermaid 架构图语法防崩溃规范**：
  - **连线标签转义**：`-->|文本|` 之间的连线文本，**严禁直接出现原生竖线字符 `|`**（如 `ES|QL` 必须转写为 `ESQL` 或实体符号），避免 Mermaid 将其误判为标签结束符导致解析崩溃；
  - **节点特殊字符包裹**：节点显示文本若包含括号 `()`、方括号 `[]`、花括号 `{}`、斜杠、冒号或引号等特殊符号，**必须使用双引号完整包裹**（例如 `NodeA["K8s Pod (Hot)"]`），杜绝渲染爆红；
  - **子图命名与连接严谨**：`subgraph` 标题与节点 ID 必须符合字母数字规范，避免特殊符号导致解析失败。
- **链接与相对路径 100% 物理有效性校验**：
  - 交付前必须核验文档中所有新增或引用的 Markdown 链接（`[text](相对路径)`），确保目标文件在知识库中真实存在，严禁文件更名后的残留死链。
- **Markdown 格式与排版自检**：
  - 代码块（```` ``` ````）必须严格成对闭合，且必须标明语言标识（如 `yaml`、`bash`、`json`）；
  - Markdown 渲染表格的表头与对齐分隔行（`|:---|:---|`）必须完整；
  - GitHub 风格提示块（`> [!NOTE]` / `> [!TIP]` / `> [!IMPORTANT]` 等）必须严格符合规范，避免连续堆叠或嵌套。

## 9. Source Link Preservation Specification (外部输入链接溯源保存规范)
- **原始链接必须落盘保存**：当用户提供外部链接（如 GitHub 仓库 URL、技术文档、论文、技术博客等外部网络资源）要求进行深度学习、分析并整理入库时，**整理生成的知识库文档必须且强制保留原有的完整原始链接地址**。
- **保存与排版规范**：
  1. **文首提示块 (Header Callout)**：在文档首部的 `> [!NOTE]` 或元数据区域，明确注明来源链接（如 `> **原始参考来源**：[项目名称](https://...)`）；
  2. **文末溯源章节 (References Section)**：在文档文末或扩展阅读部分，设置专门的来源索引，附带原始完整 URL 与项目元数据，确保未来版本更新、比对核验时具备 100% 可追溯性。
