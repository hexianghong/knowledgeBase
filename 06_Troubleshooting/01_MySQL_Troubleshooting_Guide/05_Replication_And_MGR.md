# 🌐 第五部分：主从复制与 MGR 高可用集群篇

为了保证数据不丢，我们通常会把数据库配置成“一主多从”或者 MGR（MySQL Group Replication）集群。但是，多节点之间的数据同步往往会因为网络、硬件或者人为失误而掉链子。这一篇带你搞定集群瘫痪的各种场景。

---

## 1. 复制中断：Error 1062 (主键冲突) 或 1032 (找不到数据)

**🌟 小白秒懂**
主库是“老师”，从库是“学生”，老师在黑板上写什么，学生就在笔记本上抄什么。
有一天，有个人偷偷在学生的笔记本上写了一句“第一行：张三”。结果老师在黑板上写“第一行：李四”，学生一抄，发现自己笔记本第一行已经被占了（1062 主键冲突），学生直接当场罢工不抄了。或者老师叫学生“把第一行擦掉”，学生一看笔记本第一行是空的（1032 找不到数据），学生也罢工了。

**🚩 故障现象**
在从库执行 `SHOW REPLICA STATUS\G` 时，发现 `Replica_SQL_Running: No`，并且报错 Error 1062（Duplicate entry）或者 1032（Key not found）。

**🕵️ 根本原因**
从库没有开启“严格只读”，有开发人员或业务代码连错了数据库，直接往从库里写入了数据。导致主库传过来的修改动作在从库上无法重放。

**💊 解决方案**
- **紧急恢复复制（跳过报错事务）**：
  如果你们使用的是 MGR 或者开启了 GTID 模式，需要用空事务来顶替掉那个报错的事务：
  ```sql
  STOP REPLICA;
  -- 假设报错信息里提示冲突的 GTID 是 'aaaa-bbbb-cccc:123'
  SET @@SESSION.GTID_NEXT= 'aaaa-bbbb-cccc:123';
  BEGIN; COMMIT; -- 强行制造一个空操作跳过它
  SET @@SESSION.GTID_NEXT= 'AUTOMATIC';
  START REPLICA;
  ```
- **长期避坑**：
  所有从库（Secondary 节点）必须死死锁住，谁也不准写！
  ```sql
  SET GLOBAL read_only = ON;
  SET GLOBAL super_read_only = ON;
  ```

## 2. MGR 脑裂与网络分区 (Network Partition)

**🌟 小白秒懂**
MGR 集群是 3 个人（节点）组成的小组。规定是：任何决议必须有 2 个人（多数派）同意才能执行。
某天，机房网络突然断了，节点 A 被单独关在了一个小黑屋里，节点 B 和 C 在外面。A 发现联系不上 B 和 C，它凑不够 2 个人，于是它立刻封锁自己，拒绝所有读写（这叫防止脑裂）。这就是网络分区保护。

**🚩 故障现象**
数据库集群突然不可读写，所有成员状态异常，报错提示无法达成共识。

**🛠️ 解决方案**
如果你确定节点 A 是当前数据最新、最健康的节点，你可以作为“上帝”强行赋予 A 特权，让它自己一个人组成多数派恢复工作：
```sql
STOP GROUP_REPLICATION;
SET GLOBAL group_replication_force_members="A节点的IP:33061";
START GROUP_REPLICATION;
-- 等系统恢复、其他节点连上来后，必须立刻清空特权！
SET GLOBAL group_replication_force_members=""; 
```

## 3. MGR 写入突然掉速：被流控（Flow Control）掐了脖子

**🌟 小白秒懂**
在 MGR 小组里，大家规定要保持同步。节点 A 写得飞快，但节点 B 的硬盘很烂，抄得极慢。为了防止 B 落后太多最终掉队，MGR 引入了“流控机制”——强制把 A 的双手绑起来，让 A 写得跟 B 一样慢。

**🚩 故障现象**
主库所在的物理机配置极高，没有任何资源瓶颈，但业务写入 QPS 突然出现周期性的断崖式下跌。

**💊 解决方案**
1. **排查硬件差异**：集群内所有节点的物理配置（特别是磁盘 SSD）必须完全一致，绝不能有短板！
2. **适当放宽流控限制**（允许从库稍微落后一点）：
   ```sql
   -- 调大触发流控的积压事务阈值
   SET GLOBAL group_replication_flow_control_applier_threshold = 25000;
   ```
3. **暴力解法（全集群执行）**：如果业务绝不接受主库被降速，可以直接关掉流控（有从库延迟风险）：
   ```sql
   SET GLOBAL group_replication_flow_control_mode = 'DISABLED';
   ```

## 4. MGR 多写模式下的“连环翻车”

**🌟 小白秒懂**
单主模式是一人当老板，大家听他的；多写模式（Multi-Primary）是 3 个人都是老板，都能签字批款。如果两个老板同时在两家分行对同一个银行账户扣钱，总行一核对发现冲突了，就会直接把这笔钱的单子全撕了（事务回滚），大家都别弄了。

**🚩 故障现象**
开启了 MGR 多主模式，在大并发写入同一张表时，频繁报错事务被中止（Transaction aborted）。

**🛡️ 避坑指南**
**强烈建议放弃多主模式！** 
在真实的企业级高可用架构中，99% 的场景都应该使用**单主模式（Single-Primary）**。读写分离通过路由（如 MySQL Router）来实现即可，完全没有必要在数据库底层搞多写去自找麻烦。

## 5. MGR 扩容加节点方式的降维打击 (5.7 vs 8.0)

**🌟 小白秒懂**
新来的节点想加入集群，它说：“各位大哥，把你们的数据全盘复制给我一份吧。”
- **MySQL 5.7 的苦逼做法**：大哥说：“我没空，你自己去找个叫 XtraBackup 的搬家公司，把我硬盘里的数据全打包拷过去，自己装好了再来找我连 Binlog。”
- **MySQL 8.0 的降维打击**：大哥说：“没问题，你站着别动，我直接用内部法术（Clone Plugin）把我的状态一比一传给你，连网线都不用拔。”

**🛡️ 版本差异与避坑指南**
1. **MySQL 8.0.17+ (全自动 Clone 插件)**：
   8.0 引入了极其强大的 `Clone Plugin`。加节点时，新节点会自动连接主库，通过内部流式传输自动拷贝全量数据并启动，完全解放了 DBA 的双手。
   **常见报错排查 (缺少 Donor 权限)**：如果新节点卡在 RECOVERING 状态报错 `clone_valid_donor_list`：
   - 在主节点（Donor）上授权：`GRANT BACKUP_ADMIN ON *.* TO 'mgr_user'@'%';`
   - 在新节点上加白名单：`SET GLOBAL clone_valid_donor_list = '主节点IP:3306';`

2. **MySQL 5.7 (纯手工硬核加节点)**：
   5.7 完全没有 Clone 插件。如果新加入的节点是一台空机器，**绝不能**直接 `START GROUP_REPLICATION`（会因缺少历史数据瞬间报错崩溃）。
   **正确做法**：
   - 必须先在主库手动使用 Percona XtraBackup 或 mysqldump 导出全量物理/逻辑备份。
   - 传到新节点并恢复数据。
   - 配置新节点指向主库的正确 GTID 坐标。
   - 最后才能将其加入 MGR 小组。
   > 💡 **最佳实践**：如果您还在用 5.7，扩容节点是一项极高危、极繁琐的操作，请务必预留充分的停机维护时间！
