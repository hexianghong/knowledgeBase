# 🔧 第六部分：连接、网络、日志与备份运维篇

这一部分是我们整个终极故障排查指南的收官之作。当你的 SQL 没问题，架构也很牛逼，但就是经常连不上数据库，或者半夜报警磁盘打满，多半就是运维层面的配置出了问题。掌握这些，你就能成为一个全栈型的护航大拿。

---

## 1. 拒之门外：Too Many Connections (连接数爆满)

**🌟 小白秒懂**
数据库是一家饭店。里面有 100 张桌子（`max_connections=100`）。外面来了 500 个客人，前 100 个进去了，剩下的 400 个在外面无论怎么敲门，保安都只回一句：“客满了，进不来”。

**🚩 故障现象**
应用接口大面积返回 500 错误，后台日志疯狂打印：
`ERROR 1040 (08004): Too many connections`

**🕵️ 根本原因**
1. 突发流量暴涨，超出了预设的最大连接数。
2. 饭店里有很多客人吃完饭了就是不走（连接池泄漏，或慢查询导致连接长时间挂起不释放）。

**🛠️ 解决方案与版本差异 (5.7 vs 8.0)**
- **MySQL 8.0 的终极救命后门**：
  MySQL 8.0.14 专门给管理员留了一个 VIP 后门（Dedicated Admin Interface，默认端口 `33062`）。无论前门有多挤，DBA 永远能进去救火。
  ```bash
  mysql -u root -p -P 33062
  ```
- **MySQL 5.7 的挣扎**：
  5.7 没有专用管理端口。它只会在满载之上额外保留 **1 个** 特权连接名额给拥有 `SUPER` 权限的账号。如果这个唯一名额也被 DBA 的某个监控脚本占用了，那唯一的解法就是重启数据库服务（极其惨痛）。
- **进去后临时加桌子**：
  ```sql
  SET GLOBAL max_connections = 2000;
  ```
- **避坑指南**：应用端的连接池必须设置合理的最大生存时间（`maxLifetime`），强制断开死链接！

## 2. 莫名其妙的拉黑：Host is Blocked

**🌟 小白秒懂**
你的应用服务器像一个追求者，一直在给数据库发微信（尝试连接），但是发了 100 次都没对上暗号（密码错误或网络抖动断开）。数据库觉得你是骗子，直接把你拉黑了。以后就算你密码输入对了，数据库也根本不理你。

**🚩 故障现象**
客户端机器连接数据库时抛出严重异常：
`ERROR 1129 (HY000): Host '172.16.50.88' is blocked because of many connection errors`

**💊 解决方案**
- **原谅他（清空拉黑名单）**：
  登录数据库执行：
  ```sql
  FLUSH HOSTS;
  ```
- **提高容忍度**（防止稍微一抖动就被拉黑）：
  ```sql
  SET GLOBAL max_connect_errors = 100000;
  ```

## 3. 为什么输入密码后要卡 10 秒钟才进得去？

**🌟 小白秒懂**
你拿着身份证（IP 地址）去住酒店。前台不但看了你的身份证，还要打电话去公安局查这个身份证对应的人具体叫什么名字（反向 DNS 解析）。公安局电话打不通，前台就死活让你在外面等着，直到 10 秒钟后电话超时断了，才放你进去。

**🚩 故障现象**
通过 IP 远程连接 MySQL 时，握手极度缓慢，耗时 2~10 秒。

**💊 解决方案**
直接让前台别查名字了，只认身份证号！
在 `/etc/my.cnf` 中配置：
```ini
[mysqld]
skip-name-resolve = ON
```
*(注：配置这个后，你在 MySQL 授权账号时只能用 IP 授权，不能用主机名授权)*。

## 4. 塞不进去的大包裹：max_allowed_packet

**🌟 小白秒懂**
你要寄一个 100 公斤的大冰箱，但是快递公司的流水线只能承载 10 公斤以下的包裹。快递柜直接报错“包裹太大，拒收”。

**🚩 故障现象**
导入大批量 SQL 脚本，或者程序里往数据库插入一张巨大的图片/长文本时，抛出报错：
`Got a packet bigger than 'max_allowed_packet' bytes`

**💊 解决方案**
调大快递柜的容量！
```sql
-- 设置为 128MB
SET GLOBAL max_allowed_packet = 134217728; 
```

## 5. 日志撑爆系统盘：No space left on device

**🌟 小白秒懂**
你请了一个速记员（Log），规定他把你每天说的每一句话都记下来。结果记了 3 年，记事本堆成了山，把你的房间完全塞满了，你连站的地方都没有，直接被挤死。

**🚩 故障现象**
MySQL 服务突然闪退，尝试启动报错，使用 `df -h` 查看发现系统盘剩余 0 字节。

**🕵️ 根本原因**
开启了慢查询日志（Slow Log）或者更恐怖的通用查询日志（General Log），但是却没有做“日志轮转”（定期清理或压缩老日志）。

**🛠️ 解决方案**
1. **千万别用 `rm` 直接删文件！** 因为 MySQL 进程还死死抓着这个文件句柄，即使你用 rm 删了表面文件，磁盘空间依然不会释放！
2. **正确清空法**（像挤牙膏一样把文件掏空）：
   ```bash
   > /app/mysql/log/slow.log
   ```
3. **长期预防**：
   在 Linux 中配置 `logrotate` 脚本，每天自动切割旧日志并保留最近 7 天，自动压缩打包。

## 6. 从外面连不上 root？（Access Denied for 'root'@'%'）

**🌟 小白秒懂**
老板（root）规定，只有在公司办公室的工位上（localhost）才可以查账。你在家里（外网 IP）想用老板的账号查账，保安肯定把你拒之门外。

**🚩 故障现象**
用 Navicat 或应用服务远程使用 root 连接 MySQL，提示 `Access Denied`。

**💊 解决方案**
登录本地 MySQL，给 root 开通全网漫游权限（虽然不建议在公网这么干，但内网一般需要）：
```sql
UPDATE mysql.user SET host = '%' WHERE user = 'root';
FLUSH PRIVILEGES;
```

## 7. 密码对了却连不上：密码认证插件之痛 (5.7 vs 8.0)

**🌟 小白秒懂**
你的数据库升级了安保系统，从原来的四位数字密码锁升级成了指纹人脸复合锁。结果你的老旧业务系统（老版本的 Java/PHP 驱动）还只懂得按密码，根本不认识指纹锁，直接被无情拒绝。

**🚩 故障现象**
应用连接数据库报错，密码明明正确，却提示：
`Authentication plugin 'caching_sha2_password' cannot be loaded`

**🕵️ 根本原因与版本差异**
- **MySQL 5.7**：默认使用老式的 `mysql_native_password` 认证插件。所有的客户端驱动都支持它。
- **MySQL 8.0**：为了防范密码被破解，默认将全局认证插件强制升级为了 `caching_sha2_password`。如果你的客户端驱动包太老（比如 JDBC 5.1.x），就会报出上述错误。

**💊 解决方案**
1. **彻底解决（推荐）**：将你的应用端驱动包（如 `mysql-connector-java`）升级到 8.0.x 以上版本。
2. **妥协降级（兼容 5.7）**：让数据库对指定的账号降级使用老认证算法。
   ```sql
   ALTER USER 'root'@'%' IDENTIFIED WITH mysql_native_password BY '你的密码';
   FLUSH PRIVILEGES;
   ```
