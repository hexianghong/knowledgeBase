## 一、 SQL 开发与索引优化故障 (1-20)

### 1. 慢查询：大表全表扫描
- **故障现象**：SQL 执行时间极长，CPU 满载。在大并发下，线程堆积导致连接数满，页面报请求超时。
- **原因分析**：查询过滤字段上未建立任何索引，或者优化器评估全表扫描成本更低。
- **诊断排查**：在 SQL 前加上 `EXPLAIN` 观察执行计划，如看到 `type=ALL` 且 `rows` 接近表总行数，即为全表扫描。
- **解决方案**：为过滤字段添加索引：
  ```sql
  CREATE INDEX idx_user_status ON users(status);
  ```
- **防范措施**：上线新 SQL 前必须通过审核，对超十万行的数据表，涉及查询条件字段均必须有适当索引。

### 2. 慢查询：前导通配符导致索引失效
- **故障现象**：`WHERE name LIKE '%张三%'` 即使在 `name` 字段建有索引，查询依然缓慢。
- **原因分析**：B+ 树索引只能按最左前缀进行排序和搜索。如果以通配符开头，优化器无法利用索引的排序结构快速定位。
- **诊断排查**：`EXPLAIN` 执行计划中 `type` 显示为 `ALL`（全表扫描）或 `index`（全索引扫描，开销依旧很大）。
- **解决方案**：
  - 改为后导通配符：`WHERE name LIKE '张三%'`（可以正常使用索引）。
  - 若必须全匹配，引入全文索引（Fulltext Index）或使用 **Elasticsearch** 等搜索引擎。
- **防范措施**：应用代码中禁止拼接前导通配符查询。

### 3. 慢查询：隐式类型转换导致索引失效
- **故障现象**：`WHERE phone = 13800000000` 执行缓慢，但 `phone` 字段为 `VARCHAR` 并建有索引。
- **原因分析**：由于传入值为数值，而字段为字符串，MySQL 会隐式调用 `CAST(phone AS SIGNED)`，破坏了索引的原始 B+ 树排序。
- **诊断排查**：`EXPLAIN` 结果中 `key` 显示为 `NULL`，且 `rows` 扫描全表。
- **解决方案**：SQL 查询中传入类型匹配的值：
  ```sql
  SELECT * FROM users WHERE phone = '13800000000';
  ```
- **防范措施**：开发规范中严格规定，字符串类型的字段查询时，参数必须使用单引号或双引号包裹。

### 4. 慢查询：索引列使用函数计算
- **故障现象**：按日期查询 `WHERE DATE(create_time) = '2026-06-12'`，数据量并不大但耗时长。
- **原因分析**：对索引列执行函数操作后，原本排序的 B+ 树索引节点值已改变，优化器无法利用索引定位。
- **诊断排查**：`EXPLAIN` 计划显示没走索引。
- **解决方案**：改写为范围查询：
  ```sql
  WHERE create_time >= '2026-06-12 00:00:00' AND create_time <= '2026-06-12 23:59:59'
  ```
- **防范措施**：禁止在过滤条件左侧（即索引列上）包裹任何 SQL 函数或自定义函数。

### 5. 慢查询：索引列参与数学运算
- **故障现象**：`WHERE id + 1 = 1000` 无法利用 `id` 的主键索引。
- **原因分析**：算术运算符同样会改变列的估值表达式，导致优化器放弃索引。
- **诊断排查**：`EXPLAIN` 执行计划退化为全表扫描。
- **解决方案**：将计算放在常量侧：
  ```sql
  WHERE id = 999;
  ```
- **防范措施**：索引字段过滤值必须是纯粹的常量或变量，不可包含运算符号。

### 6. 慢查询：OR 条件中包含非索引列
- **故障现象**：`WHERE id = 1 OR desc = 'test'`（id 有索引，desc 无索引）执行极慢。
- **原因分析**：因为 `OR` 关系意味着只要其中一侧满足即可，而 `desc` 这一侧必须全表扫描才能确定，因而整个查询会退化为全表扫描。
- **解决方案**：对 `desc` 补充索引，或者改写为两个查询的 `UNION ALL`。
- **防范措施**：对于 `OR` 查询，必须保证两边的列都单独建立了索引。

### 7. 慢查询：联合索引最左匹配失效
- **故障现象**：建立了联合索引 `idx_col1_col2_col3`，但查询 `WHERE col2 = 'b' AND col3 = 'c'` 速度很慢。
- **原因分析**：最左前缀原则要求必须从左侧第一列 `col1` 开始匹配，越过 `col1` 直接检索后面的列无法走索引。
- **解决方案**：新增 `(col2, col3)` 联合索引，或者改写 SQL 使条件包含 `col1`。
- **防范措施**：设计联合索引时，最常用、选择性最高的列必须放在最左侧。

### 8. 慢查询：选择性低被优化器放弃索引
- **故障现象**：在 `gender` （性别）字段建了索引，但查询 `WHERE gender = 'M'` 依然走全表扫描。
- **原因分析**：当符合条件的数据在表中占比过高（通常超 30%），优化器评估回表（Look-up）的随机 I/O 成本高于全表扫描。
- **解决方案**：不对低区分度（如性别、状态值、布尔值）的字段单独建立索引；如果必须通过该列过滤，可使用**覆盖索引**（即联合索引包含查询的所有字段）避免回表。
- **防范措施**：不对低区分度（如性别、状态值、布尔值）的字段单独建立索引。

### 9. 慢查询：深分页 LIMIT Offset 导致严重随机 I/O
- **故障现象**：分页查询 `LIMIT 2000000, 10` 随着页码增加，耗时大幅攀升。
- **原因分析**：MySQL 会扫描前 2000010 条记录，回表读取整行，然后抛弃前 2000000 条，带来巨大的磁盘随机读取。
- **解决方案**：使用**子查询延迟关联**技术：
  ```sql
  SELECT u.* FROM users u JOIN (SELECT id FROM users ORDER BY create_time LIMIT 2000000, 10) tmp ON u.id = tmp.id;
  ```
- **防范措施**：控制最大分页页数，或改用“游标式分页”（如每次查询携带上一页最大的自增 ID 作为 `WHERE id > last_id` 过滤）。

### 10. 慢查询：使用 UNION 产生大量磁盘临时表
- **故障现象**：多表结果合并大并发下导致磁盘 I/O 满载，系统极慢。
- **原因分析**：`UNION` 会隐式执行去重操作，在内存或磁盘上建立临时表并做全局排序，开销极大。
- **解决方案**：如果业务数据确定不重复，或不需要去重，直接使用 `UNION ALL`。
- **防范措施**：除非有绝对的去重需求，否则开发中一律使用 `UNION ALL` 代替 `UNION`。

### 11. 慢查询：SELECT * 导致无法覆盖索引
- **故障现象**：建了联合索引 `idx_a_b`，执行 `SELECT * FROM t WHERE a = 1` 依然产生了回表。
- **原因分析**：`SELECT *` 包含了索引中不存在的列，导致无法直接在索引树上返回结果，必须回表拿取整行。
- **解决方案**：只查询需要的列：`SELECT a, b FROM t WHERE a = 1`。
- **防范措施**：禁止在生产代码中编写 `SELECT *`，一律按需声明列名。

### 12. 慢查询：IN (子查询) 性能退化为循环执行
- **故障现象**：`WHERE id IN (SELECT user_id FROM orders WHERE status = 1)` 耗时长。
- **原因分析**：在部分 MySQL 旧版本或复杂查询下，优化器会将 `IN` 改写为相关子查询 `EXISTS`，导致外表每一行都循环扫描内表。
- **解决方案**：改写为 `INNER JOIN`：
  ```sql
  SELECT u.* FROM users u JOIN orders o ON u.id = o.user_id WHERE o.status = 1;
  ```
- **防范措施**：避免复杂子查询，优先使用 `JOIN` 关联查询。

### 13. 慢查询：磁盘文件排序 (Using filesort)
- **现象**：大表进行 `ORDER BY` 时耗时长，且 `EXPLAIN` 的 Extra 列显示 `Using filesort`。
- **原因分析**：排序的数据量超出了系统分配给该连接的 `sort_buffer_size` 大小，MySQL 只能在磁盘上创建临时文件分段排序。
- **解法**：为排序字段与过滤条件字段建立联合索引，利用索引的物理顺序直接输出，消除 filesort。
- **防范**：对于高频排序字段，索引设计中必须考虑排序对齐。

### 14. 慢查询：笛卡尔积（多表无关联条件）
- **现象**：数据库执行 SQL 后，CPU 和内存瞬间被打满，连接堆积。
- **原因分析**：多表关联查询中漏写了关联条件（例如 `ON` 或 `WHERE` 条件中缺少 `t1.id = t2.t1_id`），产生了全交叉关联。
- **解法**：检查多表关联，补齐关联字段；开启安全模式限制无索引关联。
- **防范**：编写复杂的 `JOIN` 语句时，必须检查并校验表与表之间的拓扑关联路径。

### 15. 慢查询：多列排序混用 ASC/DESC 导致索引失效（8.0以下）
- **现象**：`ORDER BY col1 ASC, col2 DESC` 无法走复合索引 `(col1, col2)`。
- **原因分析**：8.0 以下版本的 B+ 树索引节点只支持单向（升序）排列，双向排序必须在内存或磁盘执行重排。
- **解法**：升级到 MySQL 8.0，使用**降序索引（Descending Indexes）**功能：
  ```sql
  CREATE INDEX idx_col1_col2 ON my_table (col1 ASC, col2 DESC);
  ```
- **防范**：低版本下尽量规避混用不同排序方向。

### 16. 慢查询：IN 列表参数过多导致 Index Dive 耗时
- **现象**：`IN (1, 2, 3 ... 50000个值)` 导致执行计划解析耗时数秒。
- **原因分析**：`IN` 中的元素过多，优化器在评估执行成本（Index Dive）时耗费了过多 CPU 进行树段扫描。
- **解法**：
  - 调小 `eq_range_index_dive_limit` 阈值，强制优化器直接使用索引统计信息估算。
  - 控制 IN 列表参数在 1000 以内，分批查询。
- **防范**：对于海量 ID 的过滤，应该将数据写入临时表通过 `JOIN` 来执行过滤。

### 17. 慢查询：使用 ORDER BY RAND() 随机获取记录
- **现象**：随机查询几条中奖用户数据，耗时长达数秒。
- **原因分析**：`ORDER BY RAND()` 会对全表的每一行都计算随机值，然后放入内存排序，表越大开销成几何倍数增加。
- **解法**：利用主键边界改写：
  ```sql
  SELECT * FROM users WHERE id >= (SELECT FLOOR(RAND() * (SELECT MAX(id) FROM users))) LIMIT 5;
  ```
- **防范**：绝对不要在生产代码中使用 `ORDER BY RAND()`。

### 18. 慢查询：空间位置数据查询未走 R-Tree 索引
- **现象**：使用 `ST_Distance` 等查询周边坐标时发生全表扫描。
- **原因分析**：未对 `GEOMETRY` 或 `POINT` 空间列建立特有的 `SPATIAL` 索引。
- **解法**：为空间坐标字段声明索引：
  ```sql
  CREATE SPATIAL INDEX idx_loc ON locations(coordinate);
  ```
- **防范**：LBS 业务的坐标字段必须使用空间索引类型。

### 19. 慢查询：大字段模糊匹配未使用全文索引
- **现象**：对大文本的 `TEXT` 字段进行 `LIKE '%keyword%'`，速度慢如牛车。
- **原因分析**：B+ 树索引对前导通配符无能为力，只能物理扫描每一行文本块。
- **解法**：创建全文索引并使用 `AGAINST`：
  ```sql
  CREATE FULLTEXT INDEX ft_idx ON articles(content) WITH PARSER ngram;
  SELECT * FROM articles WHERE MATCH(content) AGAINST('搜索词' IN NATURAL LANGUAGE MODE);
  ```
- **防范**：核心大文本全文搜索推荐走搜索引擎架构（如 Elasticsearch）。

### 20. 慢查询：JSON 字段未索引导致全表解析
- **现象**：`WHERE data->'$.name' = 'jack'` 在大数据表上执行非常慢。
- **原因分析**：JSON 列以二进制格式存放，每次查询都会对行记录执行反序列化解析。
- **解法**：创建 JSON 虚拟生成列，并在生成列上建二级索引：
  ```sql
  ALTER TABLE t ADD COLUMN name_virtual VARCHAR(64) GENERATED ALWAYS AS (data->>'$.name') STORED;
  CREATE INDEX idx_name_virtual ON t(name_virtual);
  ```
- **防范**：对于高频作为查询过滤条件的 JSON 内嵌属性，应提前将其提升为生成列索引。

### 3.1 慢查询：联合索引范围条件导致后续字段失效
- **故障现象**：复合索引为 `(col1, col2, col3)`，查询条件为 `WHERE col1 = 'a' AND col2 > 10 AND col3 = 'c'`，但通过慢日志发现查询耗时依然不理想。
- **原因分析**：在联合索引中，如果某列使用了范围查询（如 `>`, `<`, `BETWEEN`），则该列之后的字段（这里是 `col3`）将无法再参与索引检索匹配，只能退化为过滤。
- **诊断排查**：`EXPLAIN` 结果中，`key_len` 仅等于 `col1` 与 `col2` 字节长度之和，说明 `col3` 索引失效。
- **解决方案**：根据业务需要，建立专用的复合索引，或根据实际场景把 `col3` 的过滤挪到最前。
- **防范措施**：在设计联合索引和编写范围查询 SQL 时，必须清楚范围过滤字段应尽量放在联合索引的最后面。

### 3.2 慢查询：不等于 (`!=` 或 `<>`) 导致索引失效
- **故障现象**：使用非等值过滤查询 `WHERE status != 1`，数据表上建有 `status` 索引但没起作用。
- **原因分析**：不等于操作符需要排除特定值而扫描其他所有范围，优化器在大部分情况下评估回表开销过高，直接放弃索引进行全表扫描。
- **诊断排查**：在 SQL 执行计划中，`type` 显示为 `ALL`。
- **解决方案**：
  - 若检索范围小，可改写为 `WHERE status IN (2, 3, 4)` 或分段 `>` / `<`。
  - 使用覆盖索引。
- **防范措施**：避免在条件中使用不等于筛选大占比字段。

## 二、 锁、死锁与事务并发故障 (21-40)

### 21. 行锁等待超时：长事务持锁不放
- **故障现象**：接口抛出大量 `Lock wait timeout exceeded`，数据库连接数瞬间占满。
- **原因分析**：另一个事务在对该行执行 `UPDATE` 后未提交，阻塞了当前的修改。
- **诊断排查**：
  ```sql
  SELECT waiting_trx_id, waiting_pid, waiting_query, blocking_trx_id, blocking_pid, blocking_query 
  FROM sys.innodb_lock_waits;
  ```
- **解决方案**：找出源头 `blocking_pid`，在数据库执行 `KILL 线程ID;` 强制切断。
- **防范措施**：规定事务内部禁止配置和调用任何非数据库的网络资源（如 HTTP API、外部 RPC）。

### 22. 死锁：并发交叉更新记录
- **故障现象**：业务抛出死锁异常（MySQL 事务自动回滚）。
- **原因分析**：线程 1 锁定了 RowA，尝试获取 RowB 的锁；同一时刻线程 2 锁定了 RowB，尝试获取 RowA 的锁，两者循环等待对方锁释放。
- **诊断排查**：
  ```sql
  SHOW ENGINE INNODB STATUS; -- 查看 LATEST DETECTED DEADLOCK 段落
  ```
- **解决方案**：业务层统一顺序加锁，比如对需要更新的记录按照主键大小排序后再遍历加锁。
- **防范措施**：应用中涉及多表/多行并发修改时，设计上必须采用顺序规整策略。

### 23. 元数据锁等待：DDL 阻塞全表读写
- **故障现象**：对大表添加列时，DDL 被挂起，后续所有对该表的正常 `SELECT` 都显示 `Waiting for table metadata lock`，数据库被瞬间卡死。
- **原因分析**：DDL 尝试获取排他 MDL 锁，被表上的一个长查询或未提交事务所阻塞。因为 DDL 优先级高，其排队又直接阻塞了它后面的所有普通读写锁申请。
- **诊断排查**：
  ```sql
  SELECT * FROM performance_schema.metadata_locks WHERE OBJECT_NAME = '您的表名';
  ```
- **解决方案**：利用 `KILL` 命令终止最先持有该表 MDL 锁的长连接事务。
- **防范措施**：高并发表的 DDL 执行必须加上锁等待超时保护：
  ```sql
  SET lock_wait_timeout = 10;
  ALTER TABLE my_table ADD COLUMN new_col INT;
  ```

### 24. 锁范围过大：未加索引字段修改触发锁升级
- **故障现象**：`UPDATE users SET status = 2 WHERE age = 30;` 执行时锁住了整张表，导致其他非该年龄段的用户也无法写入。
- **原因分析**：`age` 字段没有索引，InnoDB 无法做精确行级锁定，被迫扫描聚簇索引所有行并全部加锁，退化为表锁。
- **解决方案**：为 `age` 字段快速补充二级索引。
- **防范措施**：任何用于 `UPDATE`/`DELETE` 的 `WHERE` 条件字段，都必须覆盖对应的二级索引。

### 25. 间隙锁冲突：Gap Lock 并发死锁
- **故障现象**：高并发插入没有连续主键的数据行时，频繁触发死锁。
- **原因分析**：在默认的 RR（可重复读）隔离级别下，针对不存在的记录进行锁定（如 `SELECT ... FOR UPDATE`）会产生间隙锁（Gap Lock）。当两个连接各自获取了间隙锁，再并发插入数据时就会因互相申请插入意向锁冲突而发生死锁。
- **解决方案**：
  - 如果业务允许，将数据库隔离级别下调为 **RC (Read Committed)**，消除间隙锁。
  - 或者优化业务逻辑，杜绝对不存在行并发调用 `FOR UPDATE`。
- **防范措施**：在高频写入表上，小心使用 RR 隔离级别下的区间排他锁定。

### 26. 共享锁阻塞：SELECT ... FOR SHARE 造成写锁饥饿
- **故障现象**：高并发写入时，写更新被频繁阻塞，行锁等待数异常高。
- **原因分析**：大量读查询使用了 `FOR SHARE`（或 `LOCK IN SHARE MODE`）共享锁。共享锁允许其他读，但会彻底阻塞任何写锁（排他锁）。
- **解决方案**：修改代码，除非是明确的强一致性防并发父子级联修改，否则一律使用普通非锁读。
- **防范措施**：应用开发中禁止无限制滥用 `FOR SHARE` 读锁。

### 27. 唯一索引冲突死锁：INSERT ON DUPLICATE KEY 死锁
- **故障现象**：并发执行批量导入并存在大量唯一键冲突时发生死锁。
- **原因分析**：插入唯一索引遇到冲突时，当前事务会要求获取这行唯一记录的共享锁（S锁）。多线程冲突下，S锁尝试升级为X锁产生死锁。
- **解决方案**：将批量导入操作改为单线程逐步写入，或者在应用层先行进行唯一性去重后，再分批做 `INSERT`。
- **防范措施**：高并发写入下，少用 ON DUPLICATE 语句处理大量冲突数据。

### 28. 自增锁死锁：AUTO_INCREMENT 高并发瓶颈
- **故障现象**：使用自增主键，当并发插入量极高时，写入吞吐无法随硬件升级线性提升，后台有自增锁竞争。
- **原因分析**：在早期的自增配置模式下，自增锁是表级的，在事务结束前不会释放，导致高并发事务卡死在主键生成排队上。
- **解决方案**：在 `/etc/my.cnf` 中配置 `innodb_autoinc_lock_mode = 2`，采用交错式无锁自增分配。
- **防范措施**：MySQL 8.0 起该配置已默认设为 2，若运行在 5.7 则需手动调整。

### 29. 隔离级别故障：长事务导致 Undo 历史版本连（History List）剧增
- **现象**：数据库 I/O 突然升高，共享表空间不断膨胀，查询变慢。
- **原因分析**：RR 级别下，一个长事务或只读长连接在运行中，导致垃圾页的清理线程（Purge Thread）无法清理被该事务 Read View 盖住的历史 Undo 版本链。
- **诊断排查**：
  ```sql
  SHOW ENGINE INNODB STATUS; -- 关注 "History list length" (若数万以上说明积压严重)
  ```
- **解法**：`KILL` 对应的长连接，将 Undo Purge 参数进行调优；在应用侧将长连接配置加上最大生命周期限制（如 `maxLifetime`）。
- **防范**：数据库运维应该设立每日定时检查，自动杀掉运行超 2 小时的长链接事务。

### 30. 长事务回滚挂起：强制杀死进程造成数据库冷启动缓慢
- **现象**：一个删除上亿数据的 `DELETE` 被误执行，中途被 `kill -9` 杀死。重启 MySQL 发现服务被卡在启动恢复状态。
- **原因分析**：杀死数据库进程并不会消除未完成事务的影响，重启时，崩溃恢复需要前滚再回滚未提交的事务，物理回滚由于是单线程，时间是删除的数倍。
- **解法**：绝对不可在回滚阶段再次重启！应使用 `sys.processlist` 观察事务状态，静待其回滚清理完成。
- **防范**：对海量删除业务，强制拆分为 `LIMIT` 分段提交。

### 31. 残留 XA 事务阻塞表结构变更
- **现象**：对表做 DDL 时一直报 MDL 锁超时，但此时 `show processlist` 显示没有任何线程在对该表做操作。
- **原因分析**：上游中间件（如 ShardingSphere、Seata）异常断开连接，留下了一个已进入 `PREPARED` 状态的 XA 分布式事务挂在 InnoDB 引擎中。
- **诊断排查**：
  ```sql
  XA RECOVER; -- 罗列残留的分布式事务 xid
  ```
- **解法**：根据返回的 XID 信息，手动提交或回滚该事务：
  ```sql
  XA COMMIT 'xid_string'; -- 或 XA ROLLBACK
  ```
- **防范**：中间件必须具备完备的残留 XA 事务轮询回收机制。

### 32. 并发扣减超卖问题：无版本控制并发写覆盖
- **现象**：商品库存数量在秒杀后为负数。
- **原因分析**：高并发扣减库存时，代码写成了先 `SELECT` 出来在内存减掉再 `UPDATE` 回去。在高并发下产生了更新覆盖。
- **解法**：
  - 使用悲观锁锁定行：`SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;`
  - 或在写时增加乐观约束：`UPDATE product SET stock = stock - 1 WHERE id = 1 AND stock >= 1;`
- **防范**：应用端严禁采用先读取再回写内存计算的无锁更新模式。

### 33. 外键更新锁级联死锁
- **现象**：单表更新时，莫名出现与另一张表的死锁警告。
- **原因分析**：表中建立了物理外键，更新子表时，InnoDB 必须对父表被引用的行自动加共享锁（S锁），当多表并发加锁交叉时极易产生死锁。
- **解法**：删除物理外键，改在业务代码层实现外键一致性校验。
- **防范**：互联网企业级规范中，严格禁止使用物理外键。

### 34. 事务大小超出 binlog 缓存容量
- **现象**：在做大批量写入时，报错 `max_binlog_cache_size` 超限。
- **原因分析**：单个事务中修改的行记录体量过大，导致其产生的 binlog cache 在内存和临时文件里都盛装不下。
- **解法**：
  - 临时调大全局参数：`SET GLOBAL max_binlog_cache_size = 8G;`
  - 减小事务规模，分批执行。
- **防范**：避免在单个事务中写入海量数据。

### 35. 事务隐式提交：ROLLBACK 失败
- **现象**：程序逻辑发生异常，调用了事务 `ROLLBACK`，但从数据库检查发现，前半段的写入居然生效了。
- **原因分析**：事务执行过程中，调用了隐式提交的语句（如 `TRUNCATE TABLE` 或 `CREATE TABLE` 等 DDL 命令），这会自动强制提交当前的活跃事务。
- **解法**：不要在带有 DML 业务的事务流程中混合使用 DDL 和行政管理命令。
- **防范**：开发代码中严格剥离交易流与管理流。

### 36. 可重复读（RR）隔离级别下的幻读
- **现象**：同一个事务内，第一次查询只有 2 条记录，执行了一次 `SELECT ... FOR UPDATE` 却变为了 3 条。
- **原因分析**：RR 级别仅对“快照读”（非锁读）提供一致性视图。当前读（`FOR UPDATE` / `FOR SHARE`）会直接读取最新版本的底层行和间隙，从而产生幻读。
- **解法**：在事务启动之初就统一使用当前读进行锁定。
- **防范**：深刻理解快照读与当前读的差异，避免交叉使用。

### 37. 事务自动提交关闭造成物理数据库连接泄露
- **现象**：服务器线程数平稳增长，连接泄漏。
- **原因分析**：Java 客户端在使用连接时调用了 `connection.setAutoCommit(false)` 开启了显式事务，但在操作完放回连接池时未调用 `commit()` 或是 `rollback()`，连接池也没有配置回收策略，导致长事务一直挂载。
- **解法**：在连接池（如 Druid）配置中开启事务漏提交自动回收策略。
- **防范**：严格规范代码，确保所有的显式事务在 `finally` 块中都有妥善的提交或回滚处理。

### 38. 组提交（Group Commit）性能瓶颈
- **现象**：大并发写时，主库出现很多处于 `waiting for group commit` 状态的会话，写吞吐下降。
- **原因分析**：每次事务提交都必须刷盘，多个事务不能合并，产生高频微小 I/O。
- **解法**：合理配置组提交参数：
  ```sql
  SET GLOBAL binlog_group_commit_sync_delay = 10000; -- 延迟 10ms
  SET GLOBAL binlog_group_commit_sync_no_delay_count = 50; -- 或达到 50 个事务时批量刷盘
  ```
- **防范**：根据磁盘 IOPS 设定组提交的延迟上限。

### 39. 多表关联更新锁范围失控
- **现象**：进行多表关联更新 `UPDATE t1 JOIN t2 ON ... SET t1.col = ... WHERE t2.col = ...` 时，很多无关行被锁定。
- **原因分析**：关联更新时，所有被关联扫描到的行都会在事务执行期间被加行锁，哪怕最终并没有修改它们。
- **解法**：将多表关联更新拆分为单表更新，或者只对需要修改的行通过主键定位再修改。
- **防范**：避免使用复杂的多表 JOIN UPDATE。

### 40. 热点数据更新高并发死锁（秒杀/红包）
- **现象**：短时间上千个连接同时修改单一商品库存，数据库直接夯死，响应延迟增加百倍。
- **原因分析**：高并发竞争同一行锁，行锁排队过长，且死锁检测（Deadlock Detector）为了评估这个上千节点的锁依赖环，占用了 100% 的 CPU，导致全部卡死。
- **解法**：
  - 在秒杀期间，临时关闭死锁检测（前提是配置了较短的锁超时参数）：
    ```sql
    SET GLOBAL innodb_deadlock_detect = OFF;
    SET GLOBAL innodb_lock_wait_timeout = 2; -- 锁超时缩短为 2 秒，超时自动断开
    ```
  - 库存预热在 Redis 中扣减，异步写入数据库。
- **防范**：此类高吞吐热点更新，架构设计上应由缓存抗压，避免直击数据库行锁。

## 三、 InnoDB 引擎、物理存储与磁盘故障 (41-60)

### 41. 空间爆满：慢日志/通用审计日志打满磁盘
- **故障现象**：物理磁盘空间 0 字节，MySQL 服务崩溃闪退，报错 `No space left on device`。
- **原因分析**：开启了慢日志或者通用日志，但没有配合系统层 Logrotate 工具进行归档截断，随着业务运行，日志体积无限制膨胀。
- **解决方案**：
  - 登录物理服务器，定位到慢日志路径。
  - 清空日志内容（**切忌直接 rm**，会导致 mysqld 的句柄不释放，空间依旧不收缩）：
    ```bash
    > /app/mysql/3306/log/slowlog/slow.log
    ```
  - 关闭通用日志：`SET GLOBAL general_log = OFF;`。
- **防范措施**：上线前配置全局日志回滚和切割脚本，并监控挂载磁盘空间。

### 42. 页空洞：大表频繁删改造成页碎片与空间浪费
- **故障现象**：表删除了大量数据，但物理 ibd 文件在磁盘上的大小完全没有变小。
- **原因分析**：删除数据后，数据页内的物理数据仅被打上了“删除”标记，该空间保留给后续新插入数据复用，不退还给操作系统。
- **解决方案**：
  - 对表执行在线重建整理碎片：
    ```sql
    ALTER TABLE users ENGINE=InnoDB; -- 8.0 默认是 Online 重建
    -- 或者
    OPTIMIZE TABLE users;
    ```
- **防范措施**：对定期清理的日志表，尽量采用按月/天分区，采用直接删除分区释放空间。

### 43. 临时表空间Ibdata共享膨胀
- **故障现象**：`/var/lib/mysql/ibtmp1` 文件暴涨至几百G，打满磁盘。
- **原因分析**：数据库在运行复杂的 `GROUP BY` 或 `ORDER BY` 时，因为内存限制放不下，在磁盘临时表空间 `ibtmp1` 中写入了海量中间结果。因为 `ibtmp1` 默认自动增长且只有重启能缩小。
- **解决方案**：
  - 重启 MySQL 服务（会重建 `ibtmp1` 归还空间）。
  - 在配置文件中设定限制：`innodb_temp_data_file_path = ibtmp1:12M:autoextend:max:20G`。
- **防范措施**：限制大 SQL 在数据库中的直接执行。

### 44. 双写缓冲区（Doublewrite）性能瓶颈
- **故障现象**：I/O 压力大，大量写线程等待在双写（Doublewrite）锁定上。
- **原因分析**：InnoDB 为了防范写文件时系统突然断电导致物理页半写损坏（Partial Page Write），会将页数据两次写盘。在传统磁盘或未做写缓存的高速 SSD 上，这会导致写吞吐折半。
- **解决方案**：如果使用的是支持原子写的文件系统（如 ZFS，或配置了带后备电池物理写缓存的 RAID 卡）以及支持原子写的高端 NVMe 企业级固态硬盘，可以安全地在 `my.cnf` 中关闭双写：`innodb_doublewrite = OFF`。
- **防范措施**：根据底层物理存储的保障级别，选择性地管理双写缓冲。

### 45. 系统表空间 `ibdata1` 无法在线回缩
- **故障现象**：系统默认共享表空间 `ibdata1` 文件极大，清空数据也不变小。
- **原因分析**：如果在建表前配置了 `innodb_file_per_table=OFF`，所有表数据和索引都会写入 `ibdata1`，且其空间和 ibtmp 一样，不能在线归还。
- **解决方案**：
  - 唯一的解决办法：使用 `mysqldump` 全库导出，清空数据库目录，重新初始化并将 `innodb_file_per_table` 设置为 `ON`，再导入数据。
- **防范措施**：新实例初始化必须严格确保开启 `innodb_file_per_table = ON`（MySQL 8.0 默认）。

### 46. 单目录文件上限限制 (Can't create table ...)
- **故障现象**：执行建表语句，报错无法创建表，但磁盘空间和 Inode 均充足。
- **原因分析**：底层操作系统使用的是旧版 EXT3 文件系统，其限制单个目录下最多只能有 31998 个子目录或文件。在分表过多的实例上直接触限。
- **解决方案**：
  - 升级系统文件系统为 **EXT4** 或 **XFS**（已无此数目限制）。
  - 优化业务库，减少不必要的散表数量。
- **防范措施**：单数据库实例下的表总数应该合理控制在万张以内。

### 47. 共享表空间写入抖动：Purge 延迟引发的 Stall
- **故障现象**：写入过程中，每隔一段时间数据库就会陷入“死顿”几秒，随后自行恢复。
- **原因分析**：Purge 线程来不及物理清理已提交事务的 Undo Log，导致 Undo 段中保留的历史页过多，触发了系统的强制减速。
- **解决方案**：在 8.0 中增设独立的 Undo 表空间，并启用在线截断参数：
  ```sql
  SET GLOBAL innodb_undo_log_truncate = ON;
  SET GLOBAL innodb_max_undo_log_size = 1G;
  ```
- **防范措施**：监控 History List Length 长度，确保其在合理阈值（如小于 10 万）。

### 48. 表损坏：Got error 127/134 from storage engine
- **故障现象**：查询某表时直接报错物理损坏，无法读取数据。
- **原因分析**：物理服务器异常掉电，硬件 RAID 卡故障，或磁盘存储出现坏块，导致文件页 Checksum 校验失败。
- **解决方案**：
  - 停止 MySQL。
  - 在 `my.cnf` 中追加 `innodb_force_recovery = 3` 启动（越过崩溃页检验）。
  - 强行捞出损坏表的数据：`mysqldump -u root -p my_db my_table > recover.sql`。
  - 注释掉参数，正常重启，删除坏表，重入数据。
- **防范措施**：生产数据库必须配备 UPS 蓄电池及配置双写缓冲区。

### 50. 自增主键溢出：主键数值耗尽导致无法写入
- **现象**：大并发写入的流水表，突然报错主键已存在或提示获取自增值失败。
- **原因分析**：主键在定义时为了节省空间使用了 `INT SIGNED`，其上限仅为 21 亿。一旦用尽，自增计数器报错，无法产生新值。
- **解决方案**：使用 Online DDL 升格主键类型：
  ```sql
  ALTER TABLE log_table MODIFY COLUMN id BIGINT UNSIGNED AUTO_INCREMENT;
  ```
- **防范措施**：设计规范中要求，所有流水表、核心交易表的主键必须直接采用 `BIGINT UNSIGNED`。

### 51. 表空间传输导入：Page Size 不匹配
- **现象**：执行表空间导入时报错 `Page size ... does not match`。
- **原因分析**：源库导出的物理 ibd 文件是在 `innodb_page_size=16K` 的实例下生成的，而导入的目标实例配置为了 `8K`。
- **解法**：修改目标实例的 page size 参数并重新初始化，使两端 page size 保持完全一致。
- **防范**：跨实例传输表空间（Transportable Tablespace）前，务必核对两端的基础页大小。

### 52. 行存储限制：Row size too large > 8126
- **现象**：创建宽表（含有大量 VARCHAR 字段）时报错 `Row size too large > 8126`。
- **原因分析**：InnoDB 要求单行所有物理数据不能超过半个数据页（8126 字节）。过多的 VARCHAR 长度即使为空，其紧凑指针也会挤占行空间。
- **解法**：
  - 将 VARCHAR 字段改用 `TEXT` 或 `BLOB`（大数据会自动溢出到行外页）。
  - 指定行的存储格式为 `DYNAMIC`：`CREATE TABLE ... ROW_FORMAT=DYNAMIC;`。
- **防范**：避免创建单表列数过多的超宽表。

### 53. 表空间恢复报错：CFG 元数据不匹配
- **现象**：执行表空间导入时提示元数据 CFG 校验失败。
- **原因分析**：表空间在导出时，没有在源端成功执行锁定动作，拷贝得到的 ibd 头部信息与目标端表定义不一致。
- **解法**：在源端重新执行 `FLUSH TABLES my_table FOR EXPORT`，获取一致的 `.cfg` 文件再做迁移。
- **防范**：规范执行表空间传输导入导出步骤。

### 54. 无序 UUID 主键导致物理页分裂
- **现象**：向大表插入数据时，磁盘写入量（I/O Write）呈指数级攀升，吞吐极低。
- **原因分析**：主键无序，导致每次新记录被随机插入到已经排好序的物理 B+ 树页中间，造成大量的物理页分裂与数据搬迁。
- **解法**：采用趋势递增的 ID，如雪花算法（Snowflake ID），或者传统的 MySQL 自增 ID。
- **防范**：严禁直接使用 Java 产生的完全随机 UUID（如 `java.util.UUID`）作为聚集索引键。

### 55. Table Cache 瓶颈：频繁物理打开/关闭表
- **现象**：`Opened_tables` 参数在状态指标中极高，系统执行慢。
- **原因分析**：系统参数 `table_open_cache` 设置偏低，表句柄频繁在缓存池中被“挤出”，不得不频繁对操作系统发出物理文件 `open/close` 系统调用。
- **解法**：
  ```sql
  SET GLOBAL table_open_cache = 8000;
  SET GLOBAL table_definition_cache = 4000;
  ```
- **防范**：单实例下不要无限制创建分库分表。

### 56. 大字段页外溢出导致二次物理 I/O
- **现象**：即使仅查询 `SELECT id, status FROM t`，但由于表中有很多几十K的大文本字段，速度也慢。
- **原因分析**：使用了 `COMPACT` 格式，部分大字段虽然放到了溢出页，但行内保留了前 768 字节，导致一个 16K 的数据页能存放的记录行数极少，扫描时依旧产生大量 I/O。
- **解法**：转换表行格式为 `DYNAMIC`，使其只保留 20 字节指针在行内：`ALTER TABLE t ROW_FORMAT=DYNAMIC;`。
- **防范**：行记录格式默认统一推荐为 `DYNAMIC`。

### 57. IOPS 达到物理磁盘上限导致事务挂起
- **现象**：数据库执行 SQL 慢，连接大量挂起在 `query end` 状态。
- **原因分析**：底层存储的物理 IOPS（每秒磁盘吞吐）已被读写流量耗尽。
- **解法**：
  - 检查并优化引起磁盘物理读写的慢查询（添加索引）。
  - 升级存储设备，如更换为 NVMe SSD。
- **防范**：设定物理磁盘 I/O 占用率监控，在达到 85% 时提前预警。

### 58. Redo Log 物理归档分区写满导致数据库停停
- **现象**：数据库写入吞吐瞬间变为 0，所有写会话阻塞。
- **原因分析**：开启了 Redo Log 的归档功能，但归档目录所在磁盘分区已写满。
- **解法**：登录服务器清理归档目录，移走旧的归档文件。
- **防范**：合理设定日志归档策略及配置独立的存储挂载点。

### 59. 分区表的分区数过多导致管理耗尽内存
- **现象**：创建了上万个分区表，导致实例内存消耗几G，系统对表的操作迟钝。
- **原因分析**：每个分区在物理上都是独立的一张表，大量的句柄和元数据加载耗尽了 table cache。
- **解法**：控制单表分区在百个以内，老旧分区合并或拆分出去。
- **防范**：分区表不可无限制创建微小分区（如按小时分区）。

### 60. 分区裁剪失效导致全表加锁
- **现象**：对分区表某个分区的数据进行小范围更新，结果全表分区都被锁住。
- **原因分析**：更新语句的过滤条件没有使用分区键，或者在分区键列上使用了函数，导致优化器无法进行分区过滤裁剪。
- **解法**：改写 SQL，使 `WHERE` 条件里精准包含分区字段的原始值。
- **防范**：对分区表的查询必须严格带有分区键条件。

## 四、 内存管理、CPU 飙高与内核性能优化 (61-75)

### 61. OOM Crash：Buffer Pool 分配过大导致系统强制杀死进程
- **故障现象**：系统日志 `/var/log/messages` 发现 `Out of memory: Kill process (mysqld)`。
- **原因分析**：`innodb_buffer_pool_size` 缓存池加上连接池所消耗的会话内存，超出了物理内存上限，被操作系统内核 OOM 机制强杀。
- **解法**：将 `innodb_buffer_pool_size` 缩减为物理内存的 60% 左右，并在运行中设置监控：
  ```ini
  # 64G 内存机器推荐配置
  innodb_buffer_pool_size = 36G
  ```
- **防范**：留有 20%~30% 的富余物理内存供操作系统与临时线程使用。

### 62. 内存泄露：第三方插件引发内存持续攀升
- **故障现象**：没有高并发写入，但 mysqld 进程内存每天平稳上涨，永不回落。
- **原因分析**：加载了不兼容的第三方安全、审计插件，存在内存指针未释放的 Bug。
- **诊断排查**：
  ```sql
  SELECT EVENT_NAME, CURRENT_NUMBER_OF_BYTES_USED FROM performance_schema.memory_summary_global_by_event_name ORDER BY CURRENT_NUMBER_OF_BYTES_USED DESC LIMIT 5;
  ```
- **解法**：定位引起泄露的组件并将其卸载，或者升级该插件版本。
- **防范**：限制引入未经全面压力测试的非官方组件。

### 63. 会话内存失控： per-thread 私有缓存设置过大
- **故障现象**：并发连接一旦冲高，数据库内存瞬间被打满挂掉。
- **原因分析**：将 `sort_buffer_size`、`join_buffer_size`、`read_rnd_buffer_size` 设为了几百M。这些参数是为**每个连接线程独占分配**的，高并发下内存消耗呈乘数级暴增。
- **解法**：将这些会话级缓存参数重置为 2M~4M。
- **防范**：禁止将单会话内存参数全局设置过高，如维系特殊大查询排序，应只在 Session 级别临时调大。

### 64. 数据库处理时间翻倍： 物理 Swap 被激活
- **故障现象**：执行所有 SQL 命令的延迟（RT）瞬间增加几倍甚至几十倍。
- **原因分析**：操作系统的物理 Swap 分区被激活，导致本来常驻内存的 MySQL 热数据被踢到了慢速磁盘上。
- **解法**：修改 Linux 内核 Swappiness 倾向度：
  ```bash
  sysctl -w vm.swappiness=1
  # 写入 /etc/sysctl.conf 永久生效
  ```
- **防范**：数据库服务器必须将 Swappiness 设置为最低以保证主内存不被移出。

### 65. NUMA 分配不均导致单节点频繁 OOM 或 Swap
- **故障现象**：系统总物理内存还有 50% 剩余，但 MySQL 运行卡死，系统依然发生了 Swap 交换。
- **原因分析**：NUMA 架构下，MySQL 所在的单一 CPU Socket 节点的本地内存分配超限，系统未将其分配给另外的节点，而是强制对其本地内存执行了 Swap 回收。
- **解法**：修改启动脚本绑定为 interleave（交错）模式：
  ```bash
  /usr/bin/numactl --interleave=all mysqld_safe ...
  ```
- **防范**：在高配置多 CPU 物理服务器部署 MySQL 时，必须在系统层关闭 NUMA 的 local 偏好。

### 66. 刷脏慢导致脏页堆积引发 Checkpoint 阻塞
- **故障现象**：`Modified db pages` 积压数万页，数据库写入经常突然掉速。
- **原因分析**：`innodb_io_capacity` 设置过低，InnoDB 物理刷脏页速率赶不上写入产生脏页的速度。
- **解法**：根据物理存储承载度，调大 IOPS 限制参数：
  ```sql
  SET GLOBAL innodb_io_capacity = 4000;
  SET GLOBAL innodb_io_capacity_max = 8000;
  ```
- **防范**：合理匹配 SSD 固态硬盘的物理极限设置。

### 67. 查询缓存失效全局锁死（低版本）
- **故障现象**：`show processlist` 大量线程卡在 `Waiting for query cache lock`。
- **原因分析**：开启了锁定的 Query Cache，只要有写入事务提交，就会清空该表所有的缓存，在清空过程中对全局缓存池加排他锁，导致并发查询被死死卡住。
- **解法**：
  ```ini
  query_cache_type = OFF
  query_cache_size = 0
  ```
- **防范**：在 8.0 中该老旧特性已被彻底移除，5.7 版本下必须坚决关闭此选项。

### 68. 统计信息采样抖动：SQL 频繁选错索引
- **现象**：同一 SQL 语句偶尔快、偶尔极慢，甚至发生索引来回翻转。
- **原因分析**：MySQL 默认只随机对 20 个页子节点（Page）进行采样来计算索引区分度，若表数据变化大，采样值发生大范围波动，误导了优化器。
- **解法**：
  - 手动增加采样页数，稳定优化器采样率：
    ```sql
    SET GLOBAL innodb_stats_transient_sample_pages = 40;
    ```
  - 使用 `FORCE INDEX` 固定索引。
- **防范**：对高变动、超大表的 SQL 进行索引绑定固定。

### 69. 优化器生成执行计划时间超长： statistics
- **现象**：短关联 SQL 耗时秒级，`show processlist` 显示一直卡在 `statistics`。
- **原因分析**：关联表多（超 8 张），且索引区分度类似，优化器不得不针对大量的路径树（Index Dive）进行精细对比计算，消耗了大量的 CPU 算力。
- **解法**：调小 `eq_range_index_dive_limit`，让优化器直接读取元数据估值，或通过 `straight_join` 强制指定关联顺序，缩短执行计划树生成耗时。
- **防范**：避免在单个 SQL 语句中关联过多的表。

### 70. 隐式类型转换发生在高频死循环查询中拖垮 CPU
- **现象**：数据库 CPU 占用率 100%，抓出来的 SQL 都是很简单的主键查询。
- **原因分析**：虽然查询极简，但由于应用开发在 `for` 循环中发起了上万次不同类型的参数隐式类型转换，使得 CPU 被强制高频执行 CAST 逻辑计算。
- **解法**：修改业务，将多次单条查询合并为批量 `IN` 查询，并严格保证参数与字段类型完全匹配。
- **防范**：禁止在开发中编写高频单条循环查询。

### 71. 复杂存储过程/自定义函数（UDF）消耗 CPU
- **现象**：数据库无慢 SQL 且无磁盘 I/O 压力，但 CPU 居高不下。
- **原因分析**：数据库中编写了极其庞大和繁重的存储过程、触发器或 UDF，在里面执行大量的逻辑计算和字符串拼接。
- **解法**：剥离数据库计算逻辑，将其转移到应用服务集群（如 Java 节点），数据库只做纯粹的读写。
- **防范**：架构设计上严格推行“数据库只做存储，不包含复杂的业务逻辑运算”的方针。

### 72. 锁冲突：InnoDB 内部自适应哈希索引 AHI 瓶颈
- **现象**：并发量极大时，CPU 100% 且等待在 `hash0itg.cc` 信号量上。
- **原因分析**：自适应哈希索引全局持有一把独占锁，等值检索非常高时，大量线程在此排队竞争。
- **解法**：直接关闭自适应哈希索引：
  ```sql
  SET GLOBAL innodb_adaptive_hash_index = OFF;
  ```
- **防范**：对于非点查询极其集中的大并发场景，AHI 带来的锁竞争通常大于性能提升，一般建议关闭。

### 73. 线程切换开销：连接数过高导致调度开销冲高
- **现象**：连接数达数千，I/O 低，但 CPU 100% 耗尽在系统内核（system）而非用户态（user）。
- **原因分析**：大量的短连接或挂起连接，导致操作系统内核在成千上万个线程上下文之间频繁执行调度与切换，CPU 效率跌谷。
- **解法**：
  - 应用端开启连接池。
  - 在 MySQL 中引入 Thread Pool（线程池插件）对并发物理线程实施限流。
- **防范**：合理限定最大连接数与并发数。

### 74. 自旋锁空转：高核数服务器上 CPU 暴增
- **现象**：服务器 CPU 逻辑核数很高（如 128 核），但一旦发生少许行锁竞争，CPU 直接瞬间占满。
- **原因分析**：并发线程在获取内部行锁等资源时，会在 CPU 中不断自旋（Spin Lock）等待锁释放而不是让出 CPU，高核数下多个线程自旋直接将所有核耗尽。
- **解法**：调低自旋等待延迟配置：
  ```sql
  SET GLOBAL innodb_spin_wait_delay = 6;
  ```
- **防范**：在高核物理服务器上，根据基准测试适当调小自旋参数。

### 75. 统计信息频繁自动收集导致性能波动
- **现象**：大并发写入表在特定时间写入速度暴跌。
- **原因分析**：频繁插入和修改数据，表发生超 10% 变化，MySQL 自动触发了统计信息重新收集（Stats Recalculation），占用了大量 CPU 和 I/O 资源。
- **解法**：
  - 更改表统计信息为手动维护（关闭自动更新）：
    ```sql
    ALTER TABLE my_table STATS_AUTO_RECALC = 0;
    ```
  - 配置定时任务在业务低峰期执行 `ANALYZE TABLE`。
- **防范**：对高变动、超大表的统计信息实施手动锁死控制。

## 五、 从库复制、MGR 与高可用集群故障 (76-90)

### 76. 复制中断：主从主键冲突（Error 1062）
- **故障现象**：`SHOW REPLICA STATUS` 提示 `Replica_SQL_Running = No`，报错行键已存在。
- **原因分析**：从库未处于只读状态（`super_read_only = OFF`），有人直接连入从库写入了占位数据，当主库同步过来包含该主键的事务时，在从库报错中断。
- **解决方案**：在从库上注入空事务，跳过该事务以恢复同步（以 GTID 模式为例）：
  ```sql
  STOP REPLICA;
  SET @@SESSION.GTID_NEXT= '主库产生冲突事务的GTID:序列号';
  BEGIN; COMMIT;
  SET @@SESSION.GTID_NEXT= 'AUTOMATIC';
  START REPLICA;
  ```
- **防范措施**：主备部署完毕后，必须对备库配置 `super_read_only = ON`，绝不允许非复制流量写入。

### 77. 复制中断：从库数据行不存在（Error 1032）
- **故障现象**：从库复制线程报错，找不到对应的行。
- **原因分析**：从库被执行了非法的 `DELETE` 或数据漂移，主库同步该行删除/更新事务时，在从库执行失败。
- **解决方案**：同上，通过注入空的 GTID 事务跳过此报错，或者使用 `pt-table-sync` 工具重新修复两端数据一致性。
- **防范措施**：严禁在从库进行任何手工数据篡改。

### 80. 磁盘爆满：从库未自动清理 Relay Log 文件
- **故障现象**：从库服务器磁盘剩余空间为 0，大量 relay log 堆积。
- **原因分析**：系统参数 `relay_log_purge` 被意外设置为 `OFF`，导致 SQL 回放完成后物理文件不会被自动清除。
- **解决方案**：
  - 在从库开启自动清理：
    ```sql
    SET GLOBAL relay_log_purge = ON;
    ```
  - 系统会自动根据回放进度秒级删除已回放完毕的物理文件，释放空间。
- **防范措施**：生产默认必须开启 `relay_log_purge`。

### 81. 复制中断：主从数据不一致（Error 1049）
- **现象**：同步因数据不一致中断。
- **原因分析**：使用了 `STATEMENT` 复制格式，但主库执行了类似 `UPDATE t SET col = UUID()` 等非确定性函数的 SQL 语句，导致备库回放产生完全不同的值。
- **解法**：在主库配置文件中将 binlog 复制格式强行指定为 `ROW`：
  ```ini
  binlog_format = ROW
  ```
- **防范**：现代 MySQL 生产环境必须统一使用行级复制格式（ROW）。

### 82. 复制中断：主库 Binlog 物理文件丢失
- **现象**：备库报错找不到主库上的 `bin-log.000XXX` 文件，主从彻底断开。
- **原因分析**：由于磁盘空间紧张，主库上的 binlog 被人为删除或者其保留期限设置得极短，而备库刚好因维护原因断开较久，重连时找不到历史点位。
- **解法**：
  - 调大主库保留时长：`binlog_expire_logs_seconds = 604800`（保留 7 天）。
  - 如果文件已经丢失，备库必须重新执行 Clone 物理全量重构。
- **防范**：设立完备的备份存储和保留监控。

### 84. MGR 故障：流控频繁触发主库写 Stall
- **现象**：MGR 集群写入性能出现周期性的彻底掉速为零。
- **原因分析**：MGR 自带的流控机制发现有从节点回放缓慢，为了防止节点间延迟无限拉大，主节点被强制暂停写入。
- **解法**：
  - 调高流控回放等待队列参数 `group_replication_flow_control_applier_threshold`。
  - 关闭流控（全集群均需配置）：
    ```sql
    SET GLOBAL group_replication_flow_control_mode = 'DISABLED';
    ```
- **防范**：集群内物理服务器硬件（尤其是 CPU 与磁盘 I/O 吞吐）配置必须严格保持对称一致。

### 85. MGR 故障：网络分区导致脑裂
- **现象**：数据库集群不可读写，所有成员状态异常。
- **原因分析**：网络链路割裂，导致 3 节点分裂为单节点，没有一个节点能凑够多数派共识，集体锁定自我保护。
- **解法**：在数据最新的存活节点上强组群组解除锁定：
  ```sql
  STOP GROUP_REPLICATION;
  SET GLOBAL group_replication_force_members="存活IP:33061";
  START GROUP_REPLICATION;
  SET GLOBAL group_replication_force_members=""; -- 恢复后必须立即清空
  ```
- **防范**：部署高可用集群，尽量跨机架和交换机双线互联。

### 86. MGR 故障：新加节点失败提示本地事务不一致
- **现象**：节点在重新加入 MGR 组复制时报错，状态卡在 `OFFLINE`。
- **原因分析**：该节点在退出集群期间，曾经被人为本地写入了特有事务，GTID 与组内不匹配。
- **解法**：
  ```sql
  STOP GROUP_REPLICATION;
  RESET REPLICA ALL; -- 清除复制通道的 GTID 记录
  START GROUP_REPLICATION;
  ```
- **防范**：任何时候都不能让复制节点处于非只读状态。

### 87. MGR 克隆故障：自动克隆时报错缺少 Donor 权限
- **现象**：新节点加入时，克隆命令报错 `clone_valid_donor_list` 或权限不足。
- **原因分析**：未配置克隆供体白名单，或者是克隆用户没有授权 `BACKUP_ADMIN` 权限。
- **解法**：
  - 在 Donor 节点授权：`GRANT BACKUP_ADMIN ON *.* TO 'mgr_user'@'%';`。
  - 在新加节点追加白名单：`SET GLOBAL clone_valid_donor_list = 'Donor_IP:3306';`。
- **防范**：按照标准文档，预先配齐克隆所需的各项权限和白名单。

### 88. MGR 故障：多写模式下写事务冲突回滚严重
- **现象**：开启了多主（Multi-Primary）模式，但业务大吞吐写入时，经常报错失败。
- **原因分析**：两个节点并发更新同一行，MGR 认证线程检测到严重的加锁冲突，后来的事务会被直接抛弃回滚。
- **解法**：将 MGR 更改为**单主模式（Single-Primary）**，读写流量只打向唯一的主节点，从根本上杜绝多写冲突。
- **防范**：企业级高可用架构中，不建议采用多主写模式。

### 89. MGR 故障：大量写操作导致认证队列暴涨 OOM
- **现象**：主节点物理内存暴涨。
- **原因分析**：瞬间写入千万级数据，MGR 认证线程来不及评估，认证队列（`certifier`）迅速积压，挤爆内存。
- **解法**：对批量导入进行分流和限速，每次提交不要超过 5000 行。
- **防范**：大规模数据初始化禁止在 MGR 运行期间大并发直写。

### 90. Keepalived 双主冲突引发的 VIP 脑裂
- **现象**：VIP IP 在两台 mysql-router 上同时绑定，客户端连接错乱。
- **原因分析**：网络抖动或防火墙关闭了 VRRP 心跳通信，两个 Keepalived 均认为对方已死。
- **解法**：
  - 在网络层开放 VRRP 协议。
  - 修改 `keepalived.conf` 为单播通信：
    ```ini
    unicast_src_ip 172.16.255.194  # 本机
    unicast_peer {
        172.16.255.195              # 对端
    }
    ```
- **防范**：高可用架构中推荐使用单播（Unicast）对射心跳心跳，规避组播广播风暴或拦截。

## 六、 数据库连接、网络、参数配置与备份恢复 (91-100)

### 91. 连接延时：DNS 反向解析阻塞登录握手
- **故障现象**：客户端通过 IP 远程登录数据库时，在输完密码到建立连接之间耗时 2~10 秒。
- **原因分析**：MySQL 收到连接后，默认会尝试反向域名解析客户端 IP。如果 DNS 服务器响应慢或不可达，就会卡在解析等待超时。
- **解决方案**：在 `/etc/my.cnf` 中关闭此功能：
  ```ini
  [mysqld]
  skip-name-resolve = ON
  ```
- **防范措施**：所有生产实例初始化时，一律默认开启此参数。

### 92. 网络数据溢成：Packet bigger than max_allowed_packet
- **故障现象**：导入大批量 SQL 文件或存入带有大图片的文本时，报错 `Got a packet bigger than 'max_allowed_packet' bytes`。
- **原因分析**：单次发送给 MySQL 的 TCP 报文数据包体积超出了数据库允许接收的安全上限。
- **解决方案**：调大限制参数：
  ```sql
  SET GLOBAL max_allowed_packet = 128 * 1024 * 1024; -- 设为 128M
  ```
- **防范措施**：对于高频大容量流水的系统，参数初始设定不小于 64M。

### 93. MySQL Router 连接挂起拒绝服务
- **故障现象**：大并发访问下，Router 路由经常拒绝连接，报错 `Connection limit reached`。
- **原因分析**：Router 所在的操作系统对 mysqlrouter 进程的最大文件句柄限制（LimitNOFILE）过低，无法同时保持过多 Socket 链路。
- **解决方案**：在 Router 服务器上，编辑 `/etc/systemd/system/mysqlrouter.service.d/override.conf`（没有则创建），加入系统限制限制：
  ```ini
  [Service]
  LimitNOFILE=65535
  ```
  重刷系统守护进程并重启 Router：
  ```bash
  systemctl daemon-reload && systemctl restart mysqlrouter
  ```
- **防范措施**：Router 节点上线必须进行最大描述符和连接数调优。

### 94. 连接池长连接时断时续 (The last packet successfully received...)
- **故障现象**：应用系统在夜间无访问后，清晨第一次点击时接口全部报错，随后操作又恢复。
- **原因分析**：MySQL 服务端对空闲连接的最大等待存活时长（`wait_timeout`/`interactive_timeout`）默认为 8 小时。超时后会强制切断网络连接，但应用连接池没有感知，第二天仍将死连接派发给前端。
- **解决方案**：
  - 调大数据库端超时设定（如设为 24 小时）：
    ```sql
    SET GLOBAL wait_timeout = 86400;
    SET GLOBAL interactive_timeout = 86400;
    ```
  - 应用端连接池（如 Druid / HikariCP）必须配置活性自检与探活机制（如 `testOnBorrow=true` 或 `keepAlive` 参数）。
- **防范措施**：应用端与服务端超时参数合理对齐。

### 95. 物理大页无法分配：Large Pages Failed
- **故障现象**：配置文件中配置了 `large-pages=ON`，但 MySQL 闪退报错。
- **原因分析**：Linux 系统的内核大页分配严重不足，无法满足 InnoDB Buffer Pool 的大内存一次性分配锁定空间。
- **解决方案**：
  - 调大 Linux 内核大页数：
    ```bash
    sysctl -w vm.nr_hugepages=16384
    # 写入 /etc/sysctl.conf 永久保留
    ```
- **防范措施**：如果要开启物理内存大页锁定，必须在启动 MySQL 前调整好 Linux 大页设置。

### 96. 参数冲突：lower_case_table_names 初始化错误
- **故障现象**：修改了 `lower_case_table_names=1` 并重启，MySQL 报错拒绝运行。
- **原因分析**：在 MySQL 8.0 中，大小写敏感规则被固化在数据字典的系统 Schema 中，必须在实例初始化阶段（`mysqld --initialize`）指定。初始化完成后的数据库后期不允许改写此参数。
- **解决方案**：
  - 必须清空数据目录重新执行初始化，在初始化参数中指定 `--lower-case-table-names=1`。
- **防范措施**：在自动化安装部署脚本中，初始化必须一步到位指定好该参数。

### 97. 物理备份卡死：xtrabackup 长事务阻塞
- **故障现象**：执行物理备份脚本，备份流程在最后锁表阶段长时间挂起。
- **原因分析**：Xtrabackup 在完成数据备份进入非 InnoDB 结构锁表同步时，其执行的 `FTWRL` 锁表命令被主库上的某个长事务或慢查询阻塞。
- **解决方案**：
  - 在备份工具配置中设置加锁超时判定参数 `--lock-ddl-timeout=120`。
  - 人为清除主库上的阻塞长会话。
- **防范措施**：物理备份尽量避开业务繁忙期，在夜间自动调度运行。

### 98. 崩溃恢复挂起：数据库因损坏重启慢
- **故障现象**：MySQL 在异常宕机后，重启耗时数十分钟甚至数小时。
- **原因分析**：宕机前有大量的脏数据未刷盘，或者由于物理介质损坏，导致 MySQL 必须花费极高的时间成本去重做 redo 和撤销 undo 历史。
- **解决方案**：设备启动过程中耐心等待崩溃恢复跑完。如确需紧急上线捞数据，且物理文件基本完好，可使用 `innodb_force_recovery=3` 强制启动并导出数据。
- **防范措施**：保证高频写入实例的 redo log 容量足够，并严密监控磁盘物理健康度。

### 99. 升级不兼容：复制因密码认证失败中断
- **故障现象**：备库升级到 MySQL 8.0 后，主从复制中断并报错密码认证拒绝。
- **原因分析**：8.0 默认认证改为了 `caching_sha2_password`，而旧版主库仍使用的是 `mysql_native_password`，认证机制不匹配。
- **解决方案**：在备库配置连接时，指定认证兼容性：
  ```sql
  CHANGE REPLICATION SOURCE TO SOURCE_USER='mgr_user', SOURCE_PASSWORD='...', GET_SOURCE_PUBLIC_KEY=1;
  ```
- **防范措施**：高可用或复制集群进行版本升级时，必须仔细评估两端密码校验插件的差异。

### 100. 远程登录受限：Access Denied for 'root'@'%'
- **故障现象**：本地通过 socket 登录数据库正常，但是从另一台机器或应用服务上使用 VIP 连接时报错 `Access Denied`。
- **原因分析**：`root` 账户在创建或授权时，被限制为了 `localhost`，没有对所有 IP 主机 `%` 进行允许。
- **解决方案**：登录本地执行远程安全放行：
  ```sql
  RENAME USER 'root'@'localhost' TO 'root'@'%';
  FLUSH PRIVILEGES;
  ```
- **防范措施**：规划好运维管理网网段，非必要不将管理员暴露给公网。
