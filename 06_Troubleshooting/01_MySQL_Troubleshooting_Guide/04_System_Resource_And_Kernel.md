# 🖥️ 第四部分：系统资源与内核调优篇

数据库跑得慢，很多时候不仅是 SQL 的问题，而是 MySQL 跟底层操作系统（Linux）“八字不合”。在这一篇，我们将带你解决 MySQL 把 CPU 跑满、把内存榨干、被操作系统无情击杀的高阶问题。

---

## 1. 离奇死亡：MySQL 进程突然消失 (OOM)

**🌟 小白秒懂**
你的服务器（电脑）总共只有 16GB 内存。MySQL 是个贪吃蛇，你让它一口气吃 14GB（Buffer Pool）。结果操作系统自己也要吃饭，还要留一点给其他小软件。当内存彻底被吃光时，操作系统的“城管”（OOM Killer）就会出动，直接把最胖的那个胖子（MySQL）一刀捅死，释放内存。

**🚩 故障现象**
数据库服务突然宕机，客户端连不上。去 Linux 服务器里查日志发现 MySQL 被强杀：
```bash
dmesg -T | grep -i oom
# 输出：Out of memory: Kill process 1234 (mysqld)
```

**🕵️ 根本原因**
配置的全局内存（`innodb_buffer_pool_size`）加上高并发时每个连接单独分配的私有内存（`sort_buffer_size` 等），超出了服务器的物理总内存。

**💊 解决方案**
- **核心公式**：`InnoDB Buffer Pool + (max_connections * 每线程会话内存) < 物理总内存 * 80%`。
- 如果你的机器是 64G 内存，推荐把 Buffer Pool 设为 `36G ~ 40G`，绝不要超过 48G。留够 20% 给 Linux 内核！

---

## 2. 龟速响应：致命的 Swap 交换区

**🌟 小白秒懂**
如果内存是你的书桌，硬盘就是你的大书柜。书桌上拿书（读内存）只要一秒，去书柜拿书（读硬盘）要一分钟。当书桌放满时，Linux 会聪明地把你暂时不看的书搬回书柜（这叫 Swap）。但问题是，MySQL 以为这些数据还在书桌上，一读，结果要去书柜拿，速度瞬间慢了 100 倍！

**🚩 故障现象**
平常执行只要 10 毫秒的 SQL，突然全部变成需要 1000 毫秒，系统变得极其卡顿，但 CPU 占用并不高。

**🕵️ 排查与解决方案**
1. 用 `free -m` 看看系统的 Swap 区是不是被占用了。
2. 强制要求 Linux **“除非万不得已，否则绝对不把内存里的东西搬回硬盘”**：
   ```bash
   sysctl -w vm.swappiness=1
   ```
   *（把这个倾向值设为极低，默认为 60 是给桌面系统用的，数据库服务器一定要设为 1 或者 10）。*

## 3. CPU 飙升 100% 的三大元凶

很多时候，老板看着监控屏幕上一条横在 100% 的 CPU 红线陷入了沉思。以下是三大常见元凶及通俗解法：

### 😈 元凶 A：没建索引的大表查询（瞎找）
**🌟 小白秒懂**：让一个瞎子去几千万人的操场找人，他只能一个一个摸，CPU 全被“摸人”这个动作耗尽了。
- **解法**：`show processlist` 抓出正在 `Executing` 的烂 SQL，马上 `KILL` 掉，并赶紧加索引！

### 😈 元凶 B：死循环中的隐式转换
**🌟 小白秒懂**：虽然是个根据主键查数据的好 SQL，但开发人员用 `for` 循环调了它 5 万次。而且每次传进去的都是字符串，但数据库字段是数字，每次 CPU 都要做一次字符串转数字的数学计算。5 万次乘以并发量，CPU 当场冒烟。
- **解法**：应用端代码整改。禁止高频单条循环，改为 `IN (1, 2, 3...)` 批量查询，并且传入正确的数据类型。

### 😈 元凶 C：并发太多导致的“线程切换摩擦”
**🌟 小白秒懂**：CPU 是一个只有 8 只手的章鱼厨师。如果你同时派了 5000 个服务员（连接线程）去厨房催菜。厨师根本没法做菜了，他的 8 只手全在跟 5000 个服务员吵架交接（上下文切换）。
- **解法**：
  - 应用端配置连接池，不要无限新建连接。
  - MySQL 端开启线程池（Thread Pool）插件，在门外搞个叫号机，厨房里最多只放几十个线程进去。

## 4. 隐藏的陷阱：会话内存（sort_buffer）设得太大

**🌟 小白秒懂**
为了让每个来酒店的客人都舒服，你给每个客房都配了 1000 平米的超大阳台（`sort_buffer_size = 100M`）。平时客人少没问题，一到节假日来了 2000 个客人，酒店地皮瞬间被撑爆垮塌。

**🚩 故障现象**
并发一上来，内存瞬间打满 OOM。

**🕵️ 根本原因**
有很多参数（如 `sort_buffer_size`、`join_buffer_size`）是**每一个连接独享**的。如果你全局设为 100M，1000 个并发连接瞬间就会吃掉 100GB 内存！

**💊 解决方案**
- 把这些会话级别的参数全部改回默认的极小值（2M~4M 足矣）！
  ```sql
  SET GLOBAL sort_buffer_size = 2097152; -- 2MB
  SET GLOBAL join_buffer_size = 2097152; -- 2MB
  ```
- 如果某一个报表查询确实需要极大的排序内存，请在这个查询执行前，**在当前 Session 会话级别单独调大**，查完即毁，绝不要改全局变量。

## 5. 多核 CPU 的魔咒：NUMA 分配不均

**🌟 小白秒懂**
服务器有两个 CPU 大脑，左脑和右脑，各自管着一半的内存。MySQL 这个程序全跑在左脑上，把左脑的内存吃光了。虽然右脑还有很多空闲内存，但左脑很固执，宁可把数据挪到硬盘（Swap），也不肯借用右脑的内存。

**🚩 故障现象**
用 `free -m` 发现系统还有几十 G 的可用物理内存，但 MySQL 运行依然卡死，并且系统已经发生了 Swap 交换！

**💊 解决方案**
在 MySQL 的启动脚本中，使用 `numactl` 强制要求 MySQL 交错地向两个大脑申请内存：
```bash
/usr/bin/numactl --interleave=all mysqld_safe &
```
