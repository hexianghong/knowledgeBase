# 📘 第一部分：SQL 性能与索引优化篇

欢迎来到最常遇到、也是最立竿见影的“SQL性能优化篇”。这部分的故障占了日常开发中 80% 的性能问题。只要弄懂这几个场景，你写出的代码就能抗住绝大多数的高并发流量。

---

## 1. 致命的全表扫描：为啥查询这么慢？

**🌟 小白秒懂**
把数据库的表想象成一本厚厚的字典。你想找“张三”，如果字典有拼音侧边栏（这就是**索引**），你一下就能翻到对应页。如果没有侧边栏，你就得从第一页一页页往后翻，这就叫**全表扫描**（Full Table Scan）。数据量小的时候没事，一旦有上千万条数据，全表扫描足以把系统 CPU 瞬间拉满跑死。

**🚩 故障现象**
接口调用超时（Timeout），系统 CPU 利用率长时间处于 100%。在大并发下，线程堆积导致 MySQL 连接数直接打满。

**🕵️ 根本原因**
在 `WHERE` 条件的过滤字段上，没有建立任何索引。或者优化器觉得走索引还不如直接扫全表来得快（比如你要查的数据占了全表的绝大多数）。

**🛠️ 排查步骤**
使用最强大的魔法咒语 `EXPLAIN`。在你觉得慢的 SQL 前面加上它：
```sql
EXPLAIN SELECT * FROM users WHERE status = 1;
```
**怎么看结果：**
- 看 `type` 列：如果是 `ALL`，恭喜你，中奖了，绝对是全表扫描。
- 看 `rows` 列：这显示了 MySQL 估算要扫描多少行数据。

**💊 解决方案**
- **立刻止血**：给高频查询条件加上索引。
  ```sql
  ALTER TABLE users ADD INDEX idx_status (status);
  ```

**🛡️ 避坑指南**
不要在生产环境直接跑未经验证的复杂查询。核心原则：凡是出现在 `WHERE`、`ORDER BY`、`GROUP BY` 中的字段，通常都需要仔细评估是否要加索引。

## 2. 隐形的杀手：索引失效的 6 大天坑

明明建了索引，为什么 MySQL 偏偏不用？因为你无意中破坏了索引的“形状”。下面列出最容易踩坑的 6 种死法：

### 💣 天坑 1：前缀模糊匹配（`LIKE '%张三'`）
**🌟 小白秒懂**：如果在字典里找“张开头”的名字，你很容易找；但如果要找“中间包含张”的名字，字典目录就废了，只能一页页翻。
- **错误写法**：`WHERE name LIKE '%张三'` 或 `LIKE '%张三%'`
- **正确写法**：`WHERE name LIKE '张三%'`（这叫最左前缀匹配，可以走索引）
- **根除方案**：如果是全文检索需求，请使用 MySQL 的全文索引（Fulltext Index）或专门引入 Elasticsearch。

### 💣 天坑 2：隐式类型转换（张冠李戴）
**🌟 小白秒懂**：明明是字符串的手机号，你却把它当成了数字传进去。MySQL 觉得“哎呀，类型不对”，于是只好把每行数据的手机号都先偷偷转换成数字再比较，这个动作瞬间让索引作废。
- **错误写法**：`WHERE phone = 13800000000` （假设 phone 是 VARCHAR）
- **正确写法**：`WHERE phone = '13800000000'` （必须加上单引号！）

### 💣 天坑 3：在索引上做数学运算或函数套壳
**🌟 小白秒懂**：字典本来是按原词排序的，你偏偏要求把每个词都加上“你好”再去找，目录瞬间就废了。
- **错误写法**：`WHERE DATE(create_time) = '2026-06-12'` 或者 `WHERE id + 1 = 100`
- **正确写法**：把计算放在等号右边常量一侧。
  ```sql
  WHERE create_time >= '2026-06-12 00:00:00' AND create_time <= '2026-06-12 23:59:59'
  WHERE id = 99;
  ```

### 💣 天坑 4：OR 条件左右不对齐
**🌟 小白秒懂**：你想找“姓张的人”或者“年龄25岁的人”。如果“姓名”有索引但“年龄”没索引，为了找齐年龄25的人，系统依然得把全表翻一遍。
- **错误写法**：`WHERE name = '张三' OR age = 25` （只有 name 有索引）
- **正确写法**：确保 `OR` 左右两边的字段**都有**单独的索引。否则干脆用 `UNION ALL` 拆分查询。

### 💣 天坑 5：联合索引未遵守“最左前缀法则”
**🌟 小白秒懂**：联合索引就像“省-市-区”的三级目录。你可以只按“省”找，也可以按“省-市”找；但如果你直接跨过省，要求按“市-区”找，目录是帮不上忙的。
- **场景**：建了联合索引 `(col1, col2, col3)`
- **错误写法**：`WHERE col2 = 'b' AND col3 = 'c'` （跳过了 col1，索引失效）
- **正确写法**：带上 col1：`WHERE col1 = 'a' AND col2 = 'b'`

### 💣 天坑 6：范围查询切断了后续索引
**🌟 小白秒懂**：在“省-市-区”目录中，如果你找“广东省”到“湖南省”之间所有的“广州市”，这是无理取闹，因为跨省之后，市的排序早就乱了。
- **场景**：联合索引 `(col1, col2, col3)`
- **错误写法**：`WHERE col1 = 'a' AND col2 > 10 AND col3 = 'c'`
  （`col2` 用了范围 `>` 之后，后面的 `col3` 彻底失效，只能做遍历过滤）
- **正确写法**：尽量把等值匹配的字段放在联合索引的最前面，把范围过滤（`<, >, BETWEEN`）放在联合索引的最后面。

## 3. 深分页灾难：LIMIT 2000000, 10 为什么卡死？

**🌟 小白秒懂**
你要看一本书的第 200 万页。普通做法是：从第 1 页开始数，数够了 200 万页，然后翻过它们，给你看接下来那 10 页。前面 200 万页的心血全部白费！这就是深分页带来的恐怖随机磁盘 I/O。

**🚩 故障现象**
随着页码增大，翻页请求的响应时间从几十毫秒飙升到几秒甚至十几秒。

**🕵️ 根本原因**
MySQL 执行 `LIMIT offset, N` 时，必须先查出 `offset + N` 条数据，执行庞大的回表动作拿取完整数据，最后再抛弃掉前面的 `offset` 行。

**🛠️ 解决方案**
利用**子查询延迟关联（Deferred Join）**技术，利用覆盖索引的超快速度！
- **改造前**：
  ```sql
  SELECT * FROM orders ORDER BY create_time LIMIT 2000000, 10;
  ```
- **改造后**（起飞版）：先利用覆盖索引快速定位那 10 个 ID，然后再用这 10 个 ID 回表拿真实数据。
  ```sql
  SELECT o.* FROM orders o
  INNER JOIN (
      SELECT id FROM orders ORDER BY create_time LIMIT 2000000, 10
  ) tmp ON o.id = tmp.id;
  ```

**🛡️ 避坑指南**
对于海量数据的翻页，最好的设计是“游标翻页”（Cursor-based Pagination）。即每次请求带上上一页最后一条记录的 ID：
`WHERE id > 上次最大的ID LIMIT 10;`，彻底消灭 Offset。

## 4. `SELECT *` 带来的回表灾难

**🌟 小白秒懂**
你去快递站找包裹（表）。如果你只看包裹外面的标签（索引列），速度极快；但如果你偏要把所有包裹都拆开看里面的具体物品（`SELECT *` 获取全列），耗时就指数级增加。

**🕵️ 根本原因**
在二级索引（非主键索引）上找到满足条件的 ID 后，如果要获取索引上不存在的其他字段，MySQL 就必须带着 ID 回到主键的树上去做一次随机磁盘查询，这叫“回表”。`SELECT *` 强制发生最严重的回表。

**💊 解决方案**
需要什么列，就写什么列。如果某个查询极其高频且只查固定的 2~3 个字段，可以建立**覆盖索引**（Covering Index），将这几个字段全部纳入索引，实现“无需回表，直接返回”。
```sql
-- 比如高频查用户名和状态
CREATE INDEX idx_name_status ON users (name, status);
SELECT name, status FROM users WHERE name = '张三'; -- 这时 Extra 里会显示 Using index (光速完成)
```

## 5. 危险的 ORDER BY RAND() 随机取样

**🌟 小白秒懂**
你想随机挑 5 个幸运观众，结果你让全中国 14 亿人每人都报一个随机数，然后给这 14 亿个随机数排序，最后挑前 5 个。这不疯了吗？

**🚩 故障现象**
随机抽奖、推流池等接口耗时长达数秒，大量临时文件产生。

**🕵️ 根本原因**
`ORDER BY RAND()` 会强制要求 MySQL 对所有符合条件的记录进行内部的随机数分配，并在内存（或磁盘）中进行一次无比沉重的全局大排序。

**🛠️ 解决方案**
在应用层生成随机 ID 或者在 SQL 中利用数学计算。
**平替写法**（通过主键的最大最小值范围随机）：
```sql
SELECT * FROM articles 
WHERE id >= (SELECT FLOOR(RAND() * (SELECT MAX(id) FROM articles))) 
LIMIT 5;
```
