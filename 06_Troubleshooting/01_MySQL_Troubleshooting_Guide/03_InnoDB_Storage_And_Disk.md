# 💾 第三部分：InnoDB 存储引擎与物理磁盘篇

数据库说到底是一个帮我们把数据安全写进硬盘里的软件。在这部分，我们将探讨那些让磁盘空间瞬间清零、让系统读写慢成蜗牛的底层存储隐患。掌握这些，你就能在运维救火时做到成竹在胸。

---

## 1. 怎么删数据磁盘空间都不变小？（页空洞与碎片）

**🌟 小白秒懂**
你在书架（磁盘）上拿走了一本书（删了一行数据），但是你在这个空位上贴了个条子写着“已废弃”，并没有把后面的书往前推。这就导致书架上全是一个个的空隙（碎片/空洞），新买的大书放不进去，但整个书架看起来还是满的。

**🚩 故障现象**
使用 `DELETE` 删除了几千万条历史数据，但是去服务器上一看，数据文件 `.ibd` 的体积一 KB 都没有变小，磁盘依然报警。

**🕵️ 根本原因**
InnoDB 引擎为了性能，在执行 `DELETE` 时，仅仅是在底层数据页上打了一个“删除标记”（Tombstone），并不会立刻进行物理空间的收缩。这个空间只会保留给以后插入的同行大小的新数据复用。

**🛠️ 排查步骤**
查看表的“数据碎片”大小：
```sql
SELECT TABLE_NAME, DATA_FREE / 1024 / 1024 AS '碎片大小(MB)' 
FROM information_schema.tables 
WHERE TABLE_SCHEMA = '你的库名' AND DATA_FREE > 0;
```

**💊 解决方案**
- **手动整理碎片（重建表）**：
  把书架上的书全部拿下来，紧凑地重新摆放一次。
  ```sql
  -- MySQL 8.0 默认是在线整理，不阻塞读写
  ALTER TABLE users ENGINE=InnoDB; 
  -- 或者
  OPTIMIZE TABLE users;
  ```

**🛡️ 避坑指南**
大表清理历史数据，千万不要用 `DELETE`。最佳实践是使用**表分区（Partition）**，每个月一个分区。要清理历史数据时，直接把那个月的分区 `DROP` 掉，磁盘空间瞬间物理释放！

## 2. 共享表空间无限膨胀：Undo Log 无法收缩

**🌟 小白秒懂**
数据库里有一个“后悔药仓库”（Undo Log），专门存放每次修改前的数据，为了让别人能看到老数据（MVCC）或者让你撤销操作（Rollback）。如果有一个人发呆了一整个星期（一个长连接长事务一星期都没提交），为了保证他还能看到一星期前的数据，数据库就不敢把这一星期的后悔药扔掉，导致仓库直接被撑爆。

**🚩 故障现象**
磁盘剩余空间不足，查看发现 `ibdata1` 或者独立的 undo 物理文件（如 `undo_001`）体积膨胀到了几百 GB，且完全不回缩。

**🕵️ 根本原因**
长事务导致 InnoDB 的 Purge 线程无法回收旧版本的 Undo Log，引发严重积压。

**🛠️ 排查步骤**
看一眼“后悔药积压长度”：
```sql
SHOW ENGINE INNODB STATUS;
-- 查看 TRANSACTIONS 段落，找到 "History list length"
-- 如果这个值超过几万，说明积压严重！
```
揪出那个最老的未提交事务：
```sql
SELECT trx_id, trx_started, trx_mysql_thread_id 
FROM information_schema.innodb_trx 
ORDER BY trx_started ASC LIMIT 1;
```

**💊 解决方案与版本差异 (5.7 vs 8.0)**
1. **彻底拔除病根**：毫不留情地 `KILL` 掉那个长连接（trx_mysql_thread_id），掐断积压源头。
2. **MySQL 8.0 (自动自愈)**：8.0 的 Undo Log 默认已经剥离为独立的表空间，且默认开启了在线收缩。如果依然膨胀，可主动触发：
   ```sql
   SET GLOBAL innodb_undo_log_truncate = ON;
   SET GLOBAL innodb_max_undo_log_size = 1073741824; -- 设为 1G 时触发自动截断
   ```
3. **MySQL 5.7 (历史遗留巨坑)**：默认情况下 5.7 的 Undo Log 混杂在全局共享表空间 `ibdata1` 里面，**一旦撑大，永远无法缩小！** 唯一的解决办法是导出所有数据库、删掉整个实例、重新初始化再导入（极其惨烈）。
   > 💡 **5.7 避坑指南**：在 5.7 首次安装初始化时，务必在 `my.cnf` 配置 `innodb_undo_tablespaces=2` 强制其独立存放，只有独立的 Undo 表空间才能被截断回收！

## 3. 为什么 UUID 当主键会让硬盘“疯掉”？

**🌟 小白秒懂**
假设我们要给班里的同学按学号（主键）排座。如果学号是 1,2,3 顺序排，新来的同学只要往最后一排坐就行，非常快。但如果学号是一串乱码（UUID），新来的同学一会插在第一排，一会插在第三排。为了给他腾位置，整个班级的座位全得挪动（物理页分裂），场面极度混乱！

**🚩 故障现象**
向大表高频插入数据时，磁盘 I/O Write 呈指数级攀升，吞吐极低，CPU 浪费严重。

**🕵️ 根本原因**
InnoDB 的主键是“聚簇索引”，数据行是按照主键的顺序物理存放在磁盘页上的。如果使用无序的 UUID 作为主键，每次插入记录大概率会落在已经排好序的中间位置，导致原本装满的数据页被迫分裂成两半（Page Split），产生大量的碎页和额外的磁盘读写。

**💊 解决方案 / 避坑指南**
**核心表绝对禁止使用无序的 UUID 作为主键！** 
推荐做法：
1. 采用趋势递增的 ID，如推特的雪花算法（Snowflake ID）。
2. 使用 MySQL 原生的 `BIGINT UNSIGNED AUTO_INCREMENT` 自增主键。

## 4. 磁盘的瓶颈：Redo Log 疯狂刷盘

**🌟 小白秒懂**
你在账本（磁盘）上记账，为了绝对安全，每次写一笔账，你都必须立刻把账本锁进保险箱（物理刷盘）。如果一秒钟有 1 万笔账，你光开关保险箱门的时间就把你耗死了。

**🚩 故障现象**
并发批处理导入时，系统吞吐量卡在一个天花板上，磁盘 IOPS 报警，大量连接在等待事务提交。

**🕵️ 根本原因**
MySQL 配置了“双一原则”（`innodb_flush_log_at_trx_commit = 1`），每次事务提交都强制进行底层物理磁盘刷写。如果你的存储不是高速的 NVMe SSD，传统磁盘根本扛不住这种高频微小的写请求。

**💊 解决方案**
1. **降级为安全模式 2（吞吐量暴增 5~10 倍）**：
   ```sql
   -- 将写盘模式改为 2：写到操作系统的缓存，每秒由操作系统自动刷盘
   SET GLOBAL innodb_flush_log_at_trx_commit = 2;
   ```
   *注意：这种模式下，如果服务器突然断电（拔电源），最多会丢失最后 1 秒钟已提交的事务。如果只是 MySQL 进程崩溃，操作系统没挂，则完全不丢数据。*
2. **合并小事务**：不要在代码里用 for 循环单条 INSERT，改成批量插入。

## 5. 大字段外溢引发的“慢性毒药”

**🌟 小白秒懂**
你的记录本（数据页）一页只能写这么多字。如果你在其中一行里塞了一篇几万字的长文章（`TEXT/BLOB` 大字段），这一页根本装不下，只好在这行留个“地址条”，把文章扔到另一个仓库（溢出页）。下次你要查这行数据，哪怕你只看名字不看文章，数据库也得多跑一次仓库，慢得要死。

**🚩 故障现象**
即使只查询普通字段：`SELECT id, name FROM table;`，一旦表中包含很多存了几十 KB 数据的 `TEXT` 字段，速度依然很慢。

**🕵️ 根本原因**
低版本或不当格式下，溢出字段仍然会在行内保留一部分数据，极大地占用了当前物理页的空间，导致一个 16KB 的页装不下几行数据，迫使 MySQL 扫描更多物理页。

**💊 解决方案**
1. 将表的行格式调整为 `DYNAMIC`（8.0 默认），这会让大字段全部滚出主页，只留 20 字节的指针。
   ```sql
   ALTER TABLE articles ROW_FORMAT=DYNAMIC;
   ```
2. **避坑指南**：如果有经常要查询的大文本字段，强烈建议把它拆分出去，单独建一张附属表，通过主键关联。主表只留短小精悍的核心字段！
