# 🛡️ 第二部分：锁机制与并发控制篇

当你发现数据库平时跑得好好的，但一到晚上大促或者流量高峰期就莫名其妙地卡死、报错，那十有八九是遇到了“锁”的问题。把这部分吃透，你就能从容应对高并发下的各种疑难杂症。

---

## 1. 苦苦等待的行锁：Lock wait timeout exceeded

**🌟 小白秒懂**
假设数据库是一排公共厕所，每一行数据是一个坑位。事务A进去占了坑（拿到了行锁），但他在里面一边刷手机一边拉肚子，迟迟不出来（没提交事务）。事务B也想进这个坑位，只能在外面苦苦排队，等了 50 秒实在憋不住了，直接崩溃报错“等待超时”。

**🚩 故障现象**
业务接口大面积报错，核心错误信息：
`ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction`

**🕵️ 根本原因**
另一个事务对某行数据执行了 `UPDATE` / `DELETE` 等修改操作并持有了排他锁（X锁），但在代码里迟迟没有调用 `COMMIT` 提交，或者事务中间夹杂了非常慢的网络请求（比如发邮件、调用外部 API）。

**🛠️ 排查步骤**
1. 找出谁在等谁（查看锁等待队列）：
   ```sql
   SELECT waiting_trx_id, waiting_pid, waiting_query, 
          blocking_trx_id, blocking_pid, blocking_query 
   FROM sys.innodb_lock_waits;
   ```
2. 找出那个占着坑不拉屎的线程 ID（`blocking_pid`），然后干掉它！
   ```sql
   KILL 1234; -- 把 1234 换成查出来的 blocking_pid
   ```

**🛡️ 避坑指南**
- 事务必须“短小精悍”。**绝对禁止**在事务包裹的代码块中发起第三方接口的 HTTP 请求或耗时的 RPC 调用。
- 确保所有事务在 `try-catch` 的 `finally` 块中都有保底的 rollback 或 commit。

## 2. 僵局与同归于尽：死锁 (Deadlock found)

**🌟 小白秒懂**
过独木桥，张三从左往右走，李四从右往左走，两人在桥中间顶牛了。张三等李四让步，李四等张三让步，谁也过不去，这叫死锁。MySQL 的裁判（死锁检测器）看到这情况，会直接把其中一个人一脚踹下河（强行回滚一个事务），让另一个人先过去。

**🚩 故障现象**
应用后台日志频繁出现异常：
`ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction`

**🕵️ 根本原因**
事务 A 锁定了数据行 1，试图去锁行 2；同时事务 B 锁定了数据行 2，试图去锁行 1。两者形成循环等待。或者是两个事务在争抢同一段区间的“间隙锁”（Gap Lock）。

**🛠️ 排查步骤**
看一眼案发现场的回放（打印最近一次死锁日志）：
```sql
SHOW ENGINE INNODB STATUS;
-- 找到 LATEST DETECTED DEADLOCK 段落
-- 你会清楚地看到 Transaction 1 拿着什么锁在等什么锁，Transaction 2 又在干什么。
```

**💊 解决方案**
死锁是由业务层代码的逻辑顺序导致的，必须从代码层面解决。
- **规定统一的加锁顺序**：如果业务要同时修改多行记录，必须先在内存里按主键 ID 从小到大排序，然后再去数据库执行更新，这样所有人都是从左往右走，绝不会顶牛。

## 3. 全局卡死之母：元数据锁 (Metadata Lock)

**🌟 小白秒懂**
行锁只是锁坑位，**元数据锁（MDL）**是给整个公共厕所换大门！如果里面哪怕有一个人（哪怕他只是在安安静静地看报纸查数据，即执行了 `SELECT` 但是事务没提交），包工头（执行 `ALTER TABLE` 的操作）就不能换门，只能在门口等。更惨的是，由于包工头在门口排队，后面所有想上厕所的人（正常的增删改查）全被包工头堵在了门外，整个系统瞬间瘫痪！

**🚩 故障现象**
对表加个字段或建个索引（DDL），然后数据库瞬间卡死，随后的所有普通查询都挂起，连接数爆表。状态显示：`Waiting for table metadata lock`。

**🛠️ 排查步骤**
找出那个卡在表里没出来的旧事务：
```sql
SELECT * FROM performance_schema.metadata_locks WHERE OBJECT_NAME = '你的表名';
```
一旦找到持有该锁的最老事务的 Thread ID，立刻 `KILL` 掉。

**🛡️ 避坑指南与大表 DDL 的致命差异 (5.7 vs 8.0)**
- **防范 MDL 堵死**：大白天流量高峰期，执行 DDL 前必须检查 `information_schema.innodb_trx` 看是否有长事务！任何 DDL 操作必须带上超时时间，一旦等不到就自己退出，不要堵路：
  ```sql
  SET lock_wait_timeout = 5; -- 只等5秒
  ALTER TABLE users ADD COLUMN age INT;
  ```
- **MySQL 8.0 (秒级加字段)**：MySQL 8.0.12 引入了 `ALGORITHM=INSTANT`，无论是几千万还是上亿的表，加字段/删字段**只需修改表头（元数据），全程不碰表数据，耗时几毫秒！** 强烈建议显式指定：
  ```sql
  ALTER TABLE users ADD COLUMN age INT, ALGORITHM=INSTANT;
  ```
- **MySQL 5.7 (性能黑洞)**：在 5.7 中，大表加字段会退化使用 `Inplace` 算法。虽然不锁表（允许读写），但它会在底层把这上亿条数据重新复制构建一遍！可能长达数小时，直接把 CPU 和磁盘 I/O 100% 打满。
  > 💡 **最佳实践**：在 MySQL 5.7 环境，遇到千万级大表修改字段，**绝不要**直接用 `ALTER TABLE`，必须使用 `pt-online-schema-change (pt-osc)` 或 `gh-ost` 等影子表工具无感平滑迁移！

## 4. 锁升级：未加索引导致“屠城”

**🌟 小白秒懂**
警察（数据库）去抓一个罪犯（更新一行数据）。如果罪犯有身份证号（索引），警察直接去他家抓人（行锁）。如果罪犯没身份证号，警察只好把整个城市封锁（退化为表锁），全城搜捕，导致所有市民（其他事务）都没法出门。

**🚩 故障现象**
执行了一个简单的 `UPDATE` 语句，居然把整张表其他不相干的数据也给锁住了。

**🕵️ 根本原因**
你在 `UPDATE t SET status = 1 WHERE age = 30` 时，`age` 字段没有索引。InnoDB 只能对所有的行全部扫描并加锁（扫描到的都会加锁），虽然最后不符合的行会解锁，但在这个瞬间相当于把表给锁了。

**💊 解决方案**
任何用于 `UPDATE` 或 `DELETE` 的 `WHERE` 条件，必须有二级索引支撑！

## 5. 高并发超卖危机：热点数据与乐观锁

**🌟 小白秒懂**
抢红包或者秒杀商品。商品库存还剩 1 个，同时来了 10 个人，大家都看到库存是 1，然后在内存里计算 `1 - 1 = 0`，接着把 0 写回数据库。结果库存不减反增，或者扣成了负数。

**🕵️ 根本原因**
典型的并发覆盖更新（Lost Update），因为读取和写入之间存在时间差，没有进行并发版本控制。

**💊 解决方案**
- **悲观锁（强硬派）**：读取时直接锁死这行，别人连看都不许看最新状态。
  ```sql
  SELECT stock FROM products WHERE id = 1 FOR UPDATE;
  ```
  > 🆕 **MySQL 8.0 秒杀新特性**：在 8.0 中，如果不希望排队干等，可以追加 `NOWAIT`（拿不到锁立刻报错返回，适合高并发秒杀快速抛弃）或者 `SKIP LOCKED`（跳过被锁的行直接拿下一行，适合高并发任务队列分发）：
  > `SELECT stock FROM products WHERE id = 1 FOR UPDATE NOWAIT;`
- **乐观锁（机智派，强烈推荐）**：在写回数据库的瞬间，加上条件校验：
  ```sql
  -- 只有当库存大于等于这次要扣减的数量时，才允许扣减
  UPDATE products SET stock = stock - 1 WHERE id = 1 AND stock >= 1;
  ```
通过数据库自身对行锁的原子性保障，完美解决超卖问题。
