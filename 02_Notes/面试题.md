### 1.说下k8s的各个组件及其作用呢?

> 📖 深度参考：[API Server 详解](../01_Inbox/03-K8S/01-组件原理/01-API_Server.md) | [Controller Manager](../01_Inbox/03-K8S/01-组件原理/02-Controller_Manager.md) | [Scheduler](../01_Inbox/03-K8S/01-组件原理/03-Scheduler.md) | [Kubelet](../01_Inbox/03-K8S/01-组件原理/04-Kubelet.md) | [Kube-Proxy](../01_Inbox/03-K8S/01-组件原理/05-Kube_Proxy.md)
**master节点组件：**

+ api servre : 整个集群的资源操作入口，负责认证、授权、访问控制，所有组件都通过它交互
+ Kube-controller-manager: 负责维护集群的期望状态，比如副本数保持、故障检测 自动扩展 滚动更新等
+ Kube-scheduler: 负责资源调度，根据节点资源情况和调度策略，把Pod分配到最合适的节点上。
+ Ectd: 分布式键值存储，存放集群所有的配置、状态数据，一般用3/5奇数节点部署，通过Raft协议保证数据一致性。

**node 节点组件：**

+ Kubelet : 运行在每个节点上，负责本节点Pod的生命周期管理（创建、启停、健康检查），定期和apiserver同步节点状态。
+ Kube-proxy: 运行在每个节点上，负责Service的负载均衡和网络规则配置，实现ClusterIP、NodePort等Service类型的网络转发。
+ Cordns: 集群的DNS服务，负责集群内部域名解析，比如Service域名、Pod域名的解析。
+ 网络插件（比如Calico/Flannel）：实现Pod跨主机网络通信，Calico还支持网络策略做细粒度的访问控制。

### 2.说下K8S的组件是如何实现高可用的?

> 📖 深度参考：[etcd 高可用运维](../01_Inbox/03-K8S/01-组件原理/08-etcd底层架构MVCC与高可用运维.md) | [etcd 备份与恢复实战](../01_Inbox/03-K8S/06-集群运维/11-etcd备份与恢复实战指南.md)
**Master节点高可用：**  
Kubernetes的控制平面（Master节点）通常由多个实例组成（至少3个），利用**etcd**（分布式键值存储）同步集群状态，确保单点故障时集群可以继续运行。  
控制平面组件（如API Server、Controller Manager、Scheduler）通过负载均衡器进行分发，避免单个实例宕机影响整个集群管理。

**etcd高可用：**  
etcd是K8S的核心存储系统，它采用分布式复制机制，保持多个节点副本（通常是奇数个，如3、5个），保证数据一致性和容错能力。  
通过Raft协议实现数据同步，即使部分节点宕机，集群仍然可以维持一致性。

**节点高可用：**  
Kubelet和**Kube Proxy**运行在各个工作节点上，通过自动调度和健康检查机制，保证Pod的持续运行。  
集群中的多个节点相互冗余，当某个节点失效时，Pod会被重新调度到其他健康节点上。

**Pod高可用：**  
K8S通过副本集（ReplicaSet）和部署（Deployment）确保Pod的高可用。多个副本分布在不同节点上，确保服务不受单点故障影响。

**网络高可用：**  
K8S支持多种网络插件和Service类型（如ClusterIP、NodePort、LoadBalancer）来实现负载均衡，确保服务的高可用性。

### 3.说下Pod的几种探针?

> 📖 深度参考：[健康检查与可用性检查](../01_Inbox/03-K8S/02-集群负载/01-Pod/健康检查与可用性检查.md) | [应用的无损上线与下线](../01_Inbox/03-K8S/08-应用与实战/02-云原生应用无损上下线实践.md)
+ 存活探针（livenessProbe）：用于检测Pod内容器是否存活，若探测失败，kubelet会根据配置策略重启容器，保障应用的可用性。
+ 就绪探针（readinessProbe）：判断容器是否准备好接收请求，就绪后才会将其加入到服务的后端，避免请求发送到未就绪的容器。
+ 启动探针（startupProbe）：专门针对启动慢的容器，可避免存活和就绪探针在容器启动时过早探测而导致失败，待其通过启动探针后，才会进行存活和就绪探测。

### 4.说一下Pod的创建过程?

> 📖 深度参考：[组件通信与原理概述（Pod 创建全生命周期）](../01_Inbox/03-K8S/01-组件原理/00-组件通信与原理概述.md) | [请求在各组件间的流转详细流程](../01_Inbox/03-K8S/01-组件原理/07-请求在各组件间的流转详细流程.md)
1. 提交Pod定义：用户通过kubectl apply -f pod.yaml或其他方式提交Pod的配置文件（YAML/JSON）。
2. API服务器接收请求：Kubernetes API服务器接收到创建Pod的请求，并验证配置文件的合法性。
3. 调度决策（Scheduler）：API服务器将Pod交给调度器（Scheduler），根据集群资源（CPU、内存等）和调度策略选择一个合适的节点。
4. Kubelet创建容器：调度器将Pod分配到节点后，节点上的Kubelet会根据Pod的定义拉取镜像，并创建容器。
5. 容器启动：Kubelet启动容器，Pod内的容器开始运行。
6. Pod的生命周期管理：Kubelet会持续监控容器的健康状况，确保Pod正常运行，如有需要，会根据设置重启容器。

### 5.删除一个Pod会发生什么事情?

> 📖 深度参考：[资源更新与优雅关闭](../01_Inbox/03-K8S/02-集群负载/06-资源更新与优雅关闭.md) | [优雅关闭服务](../01_Inbox/03-K8S/02-集群负载/06-资源更新/优雅关闭服务.md)
1. 请求删除：用户通过 kubectl delete pod 或 API 请求删除 Pod。
2. API Server 处理：API Server 接收请求，标记 Pod 为"Terminating"状态，并更新到 etcd。
3. kubelet 处理：节点上的 kubelet 检测到 Pod 状态变化，开始停止容器，kubelet会向容器运行时（docker或者containerd）发出停止容器的请求，容器运行时这时会向容器发送优雅关闭进程的SIGTERM信号（信号编号为15），这时容器会优雅的方式关闭内部进程，执行比如关闭数据库网络连接，保存数据等，然后正常退出。如果超时30秒，会发出一个SIGKILL的（信号编号为9）信号，强制终止容器进程。
4. Endpoint 移除：如果 Pod 属于 Service，Endpoint Controller 会将其从 Service 的端点列表中移除。
5. 资源清理：kubelet 清理 Pod 的资源（如存储卷、网络等）。
6. API Server 更新：kubelet 通知 API Server Pod 已终止，API Server 从 etcd 中删除 Pod 记录。  
如果pod是deploy或者sts等工作负载管理的动态pod，kube-controller-manager会根据副本数保证期望机制，重新创建对应数量的pod，维持预期状态。

### 6.说一下Pod的重启策略?

> 📖 深度参考：[Pod 详解](../01_Inbox/03-K8S/02-集群负载/01-Pod.md)
+ Always：默认策略，无论容器如何退出都会重启。
+ OnFailure：仅在容器非正常退出（非0状态码）时重启。
+ Never：无论容器如何退出都不重启。

### 7.说一下镜像的更新策略？
+ IfNotPresent：默认策略，本地已存在镜像则不拉取，否则拉取。
+ Always：每次创建Pod时都拉取最新镜像。
+ 通过imagePullPolicy字段设置，确保使用所需版本的镜像。

### 8.说一下Pod的生命周期中有哪些状态?

> 📖 深度参考：[Pod 详解](../01_Inbox/03-K8S/02-集群负载/01-Pod.md) | [conditions 资源状态](../01_Inbox/03-K8S/02-集群负载/06-资源更新/conditions资源状态.md)
+ Pending：Pod已被系统接受，但容器未完全创建。
+ Running：Pod已绑定到节点，所有容器已创建，至少一个在运行。
+ Succeeded：所有容器成功终止，不会重启。
+ Failed：所有容器终止，至少一个容器非正常退出（非0状态码）。
+ Unknown：无法获取Pod状态，通常由于节点通信失败。  
这些状态反映了Pod从创建到终止的不同阶段。

### 9.什么是静态Pod、自主式Pod、动态Pod?

> 📖 深度参考：[Kubelet 详解](../01_Inbox/03-K8S/01-组件原理/04-Kubelet.md)
+ 静态Pod：由kubelet直接管理，无需API服务器参与，通常用于系统组件。配置文件存放在节点特定目录，kubelet定期检查并创建/更新Pod。
+ 自主式Pod：直接由用户创建和管理的Pod，不依赖于ReplicaSet、Deployment等控制器。删除后不会自动重建。
+ 动态Pod：通过控制器（如Deployment、StatefulSet）管理的Pod。控制器根据配置动态创建、更新和删除Pod，确保实际状态与期望状态一致。  
静态Pod适用于特定节点，自主式Pod适合临时任务，动态Pod常用于生产环境。

### 10.谈-下apiserver的高可用是如何实现的?

> 📖 深度参考：[API Server 详解](../01_Inbox/03-K8S/01-组件原理/01-API_Server.md)
+ 冗余部署：部署多个API Server实例，这些实例之间是无状态的，可以在不同的物理或虚拟节点上运行，从而降低单点故障的风险。
+ 负载均衡：使用负载均衡器（如HAProxy、Nginx或云服务提供商的负载均衡器）将客户端请求均匀地分发到各个API Server实例。
+ 共享存储：所有API Server实例需要访问同一个etcd集群，以确保数据的一致性和持久化。
+ 健康检查与自动恢复：通过Liveness Probe和Readiness Probe进行健康检查，当API Server实例出现问题时，自动重启不健康的实例。  
这些策略共同确保了API Server在面对节点故障、网络问题或其他潜在系统问题时，仍能维持对外服务的连续性和稳定性.

### 12.说下一个deployment的创建过程呢?

> 📖 深度参考：[Deployment 详解](../01_Inbox/03-K8S/02-集群负载/03-Deployment.md) | [请求在各组件间的流转详细流程](../01_Inbox/03-K8S/01-组件原理/07-请求在各组件间的流转详细流程.md)
1. 定义YAML文件：编写Deployment的YAML配置文件，指定副本数、容器镜像、标签等。
2. 应用配置：使用kubectl apply -f 命令提交YAML文件给Kubernetes API Server。
3. API Server处理：API Server接收请求并验证配置，将Deployment对象存储到etcd。
4. 控制器管理：Deployment控制器检测到新对象，根据配置创建ReplicaSet。
5. ReplicaSet创建Pod：ReplicaSet控制器根据副本数创建Pod，调度器将Pod分配到合适节点。
6. kubelet运行Pod：节点上的kubelet拉取镜像并启动容器。
7. 状态更新：Pod状态更新反馈给API Server，最终反映在Deployment状态中。

### 13.说-下Deployment的升级过程?

> 📖 深度参考：[Deployment 高级用法（滚动更新）](../01_Inbox/03-K8S/02-集群负载/03-Deployment/高级用法.md) | [资源更新与优雅关闭](../01_Inbox/03-K8S/02-集群负载/06-资源更新与优雅关闭.md)
1. 更新配置：修改Deployment的YAML文件（如镜像版本），使用kubectl apply -f 提交更新。
2. 创建新ReplicaSet：Deployment控制器检测到变更，创建新的ReplicaSet，逐步启动新版本的Pod。
3. 逐步替换：根据滚动更新策略（RollingUpdate），逐步增加新版本Pod并减少旧版本Pod，确保服务不中断。
4. 健康检查：新Pod启动后，通过就绪探针（Readiness Probe）确认其可用性。
5. 完成升级：所有旧版本Pod被替换为新版本Pod，升级完成。
6. 回滚（可选）：如果升级失败，可使用kubectl rollout undo回滚到上一版本。

### 14.Deployment和Statefulset有什么区别?

> 📖 深度参考：[Deployment 详解](../01_Inbox/03-K8S/02-集群负载/03-Deployment.md) | [StatefulSet 详解](../01_Inbox/03-K8S/02-集群负载/04-StatefulSet.md)
| 维度 | Deployment | StatefulSet |
| --- | --- | --- |
| Pod标识 | Pod是无状态的，名称随机且可互换 | Pod有唯一且稳定的网络标识（如pod-0、pod-1），适合有状态应用 |
| 存储 | 通常使用共享存储或无持久化存储 | 每个Pod有独立的持久化存储（如PVC），数据与Pod绑定 |
| 部署顺序 | Pod并行创建，无固定顺序 | Pod按顺序创建和删除（如pod-0先于pod-1），确保有序性 |
| 网络 | Pod通过Service负载均衡访问 | 每个Pod有稳定的网络标识，可通过.直接访问 |
| 适用场景 | 适用于无状态应用（如Web服务器） | 适用于有状态应用（如数据库、Zookeeper） |

### 17.K8S是怎么实现数据持久化的?

> 📖 深度参考：[存储基础与持久化](../01_Inbox/03-K8S/05-集群存储/01-存储基础与持久化.md) | [CSI 架构与存储挂载全链路机制](../01_Inbox/03-K8S/05-集群存储/01-CSI架构与存储挂载全链路机制.md)
+ PersistentVolume (PV)：集群中的一块网络存储，由管理员预先配置，独立于Pod生命周期。
+ PersistentVolumeClaim (PVC)：用户对存储资源的请求，Pod通过PVC使用PV。
+ StorageClass：动态配置PV的模板，支持按需创建PV。
+ Volume：Pod中挂载的存储卷，可以是PV、主机目录或临时存储。
+ StatefulSet：为有状态应用提供稳定的存储和网络标识，确保Pod与存储的绑定关系。

### 18.PV的生命周期状态有哪些?

> 📖 深度参考：[存储基础与持久化](../01_Inbox/03-K8S/05-集群存储/01-存储基础与持久化.md)
+ Available：PV已创建，尚未绑定到任何PVC。
+ Bound：PV已绑定到某个PVC。
+ Released：PVC已删除，但PV资源尚未被集群回收。
+ Failed：PV自动回收失败，通常由于存储系统问题。

### 19.简述-下Daemonset类型的资源特性?

> 📖 深度参考：[其他负载类型（DaemonSet/Job）](../01_Inbox/03-K8S/02-集群负载/05-其他负载类型.md)
+ 节点级部署：确保每个节点（或符合特定条件的节点）上运行一个Pod副本。
+ 自动扩展：当新节点加入集群时，自动在新节点上创建Pod。
+ 系统服务：常用于部署系统级服务，如日志收集（Fluentd）、监控（Node Exporter）等。

+ 节点亲和性：可通过节点标签选择特定节点部署Pod。

### 20.什么是有状态应用和无状态应用?
**有状态应用：**

+ 特点：依赖持久化存储，保存会话、数据或状态。
+ 示例：数据库（MySQL、PostgreSQL）、消息队列（Kafka）、分布式存储（Zookeeper）。
+ 需求：需要稳定的网络标识和持久化存储，Pod重启后状态不变。

**无状态应用：**

+ 特点：不依赖持久化存储，每次请求独立处理。
+ 示例：Web服务器（Nginx、Apache）、API服务、静态网站。
+ 需求：Pod可随时替换，无需保存状态。  
有状态应用需要稳定的存储和网络标识，无状态应用则更易于扩展和管理。

### 21.说下flannel的几种模式?

> 📖 深度参考：[Flannel 网络模式深度解析与对比（新增）](../01_Inbox/03-K8S/04-集群网络/07-Flannel网络模式深度解析与对比.md) | [Kubernetes 集群网络](../01_Inbox/03-K8S/04-集群网络/02-Kubernetes集群网络.md)
+ **VXLAN**：使用VXLAN封装数据包，跨节点通信。优点：支持大规模集群，配置简单。缺点：性能开销较大。
+ **host-gateway**：使用主机作为网关，直接路由数据包。优点：性能高，延迟低。缺点：要求节点在同一二层网络。
+ **UDP**：通过UDP封装数据包，跨节点通信。优点：兼容性好，适用于所有网络环境。缺点：性能最差，通常不推荐使用。
+ **Alloc**：仅用于IP地址分配，不提供网络通信。适用场景：与其他网络插件配合使用。  
这些模式根据网络环境和性能需求选择，VXLAN和host-gw最常用。

### 22.flannel可以固定节点IP和Pod的IP地址吗?

> 📖 深度参考：[Flannel 网络模式深度解析与对比（新增）](../01_Inbox/03-K8S/04-集群网络/07-Flannel网络模式深度解析与对比.md)
Flannel **不能**直接固定节点IP和Pod的IP地址，原因如下：

+ 节点IP：由主机网络配置决定，Flannel不管理节点IP。
+ Pod IP：Flannel通过CNI插件分配IP，通常从配置的子网中动态分配，无法固定。

**解决方案：**

+ 节点IP：通过主机网络配置或云平台固定。
+ Pod IP：使用StatefulSet或自定义CNI插件（如Calico）实现IP固定。  
Flannel主要用于提供跨节点通信，IP固定需借助其他工具或配置。

### 23.说下你对Pod亲和性的理解?

> 📖 深度参考：[调度策略（污点、亲和、驱逐、抢占）](../01_Inbox/03-K8S/01-组件原理/03-Scheduler/调度策略(污点、亲和、驱逐、抢占).md) | [Pod 调度](../01_Inbox/03-K8S/02-集群负载/01-Pod/Pod调度.md)
**Node Affinity：节点亲和性**  
作用：将 Pod 调度到符合特定标签的节点上。

**Pod Affinity/Anti-Affinity：Pod亲和性和反亲和性**

+ Pod Affinity：将 Pod 调度到与指定 Pod 在同一拓扑域（如节点、区域）的节点上。
+ Pod Anti-Affinity：避免将 Pod 调度到与指定 Pod 在同一拓扑域的节点上。

**应用场景：**

+ Node Affinity：硬件或区域特定的调度。
+ Pod Affinity：提高服务间的通信效率。
+ Pod Anti-Affinity：提高高可用性，避免单点故障。  
亲和性策略帮助优化 Pod 的调度和分布，提升集群性能和可靠性。

### 24.说下你对Pod污点与容忍的理解?

> 📖 深度参考：[调度策略（污点、亲和、驱逐、抢占）](../01_Inbox/03-K8S/01-组件原理/03-Scheduler/调度策略(污点、亲和、驱逐、抢占).md)
Pod 污点（Taint）与容忍（Toleration）用于控制 Pod 在节点上的调度，主要机制如下：

**污点（Taint）：**  
作用：标记节点，阻止不符合条件的 Pod 调度到该节点。  
组成：

+ key：污点的键。
+ value：污点的值（可选）。
+ effect：污点的影响，如 NoSchedule（禁止调度）、PreferNoSchedule（尽量避免调度）、NoExecute（驱逐已调度的 Pod）。

**容忍（Toleration）：**  
作用：允许 Pod 调度到带有特定污点的节点。  
组成：

+ key：匹配污点的键。
+ value：匹配污点的值（可选）。
+ operator：匹配操作符，如 Equal、Exists。
+ effect：匹配污点的影响（可选）。

**应用场景：**

+ 污点：专用节点（如 GPU 节点）、维护模式。
+ 容忍：关键服务（如监控、日志收集）调度到专用节点。  
污点与容忍机制帮助实现精细化的 Pod 调度策略，优化资源利用和集群管理。

### 26.为什么要配置Pod的启动超时时间？
配置 Pod 的启动超时时间（initialDelaySeconds）的主要原因如下：

+ 避免误报：某些应用启动较慢，立即进行健康检查可能导致误判为不健康。设置超时时间可确保应用完全启动后再检查。
+ 资源初始化：应用可能需要时间初始化资源（如数据库连接、缓存加载），超时时间确保这些操作完成后再接受流量。
+ 稳定性：防止因启动延迟导致的频繁重启，提升系统稳定性。
+ 调试与诊断：超时时间有助于识别启动问题，提供调试和优化的时间窗口。  
通过合理配置启动超时时间，可以确保应用在完全就绪后再提供服务，提升系统的可靠性和用户体验。

### 32.kube-proxy有哪些工作模式？

> 📖 深度参考：[Kube-Proxy 详解（iptables/IPVS）](../01_Inbox/03-K8S/01-组件原理/05-Kube_Proxy.md)
**userspace 模式：**

+ 工作原理：kube-proxy 在用户空间监听 Service 的端口，将请求转发到后端 Pod。
+ 优点：兼容性好。
+ 缺点：性能较低，数据包需经过用户空间处理。

**iptables 模式：**

+ 工作原理：kube-proxy 通过 iptables 规则直接转发请求到后端 Pod。
+ 优点：性能较高，数据包在内核空间处理。
+ 缺点：规则数量多时，管理和性能可能受影响。

**ipvs 模式：**

+ 工作原理：kube-proxy 使用 IPVS（IP Virtual Server）实现负载均衡，支持更多调度算法。
+ 优点：性能最优，支持更多负载均衡算法（如轮询、最小连接）。
+ 缺点：需要内核支持 IPVS 模块。

**选择建议：**

+ userspace：适用于旧版本或兼容性要求高的环境。
+ iptables：适用于大多数场景，性能较好。
+ ipvs：适用于高性能需求和大规模集群。  
根据集群规模和性能需求选择合适的模式，ipvs 是推荐的高性能方案。

### 41. ETCD如何实现高可用性和负载均衡？确保ETCD集群的节点数达到奇数？

> 📖 深度参考：[etcd 底层架构 MVCC 与高可用运维](../01_Inbox/03-K8S/01-组件原理/08-etcd底层架构MVCC与高可用运维.md) | [etcd 备份与恢复实战指南（新增）](../01_Inbox/03-K8S/06-集群运维/11-etcd备份与恢复实战指南.md)
**ETCD实现高可用性和负载均衡主要通过以下方式：**

+ 集群模式：ETCD以集群模式运行，集群中的每个节点都存储着完整的数据副本。当某个节点出现故障时，其他节点可以继续提供服务，从而实现高可用性。
+ Raft一致性算法：ETCD使用Raft一致性算法来保证集群中数据的一致性。Raft算法通过选举领导者和日志复制机制，确保集群中的数据在不同节点之间保持一致。
+ 负载均衡：在ETCD集群前配置负载均衡器，将客户端的请求均匀地分发到各个ETCD节点上，从而实现负载均衡，提高集群的处理能力和稳定性。

**确保ETCD集群的节点数达到奇数的原因是：**

+ 提高容错能力：在Raft算法中，集群的容错能力与节点数有关。当集群中有超过一半的节点存活时，集群就可以正常工作。奇数个节点能在保证容错能力的同时，减少不必要的资源浪费。
+ 避免脑裂问题：在集群节点数为偶数时，如果出现网络分区或其他故障，可能会导致集群分裂成两个相等的部分，每个部分都认为自己是多数派，从而引发脑裂问题。奇数节点在 Raft 选举时，更容易形成多数派，能快速确定主节点，提高选举效率和集群稳定性。

> 📖 深度参考：[RBAC 权限控制实战指南（新增）](../01_Inbox/03-K8S/03-安全与资源/04-RBAC权限控制实战指南.md) | [安全认证与准入控制](../01_Inbox/03-K8S/03-安全与资源/02-安全认证与准入控制.md)
K8s的RBAC（基于角色的访问控制）鉴权是K8s中重要的安全机制，以下是相关介绍：

+ 基本概念：通过定义角色（Role）和集群角色（ClusterRole）来规定权限集合，再通过角色绑定（RoleBinding）和集群角色绑定（ClusterRoleBinding）将角色与用户、组或服务账号关联，实现对K8s资源的访问控制。
+ 主要作用：可精确控制不同用户或服务对K8s资源的操作权限，如创建、读取、更新、删除等，保障集群资源安全，避免未授权访问和误操作。
+ 实现方式：通过K8s API进行配置和管理，可使用YAML或JSON文件定义角色和绑定等对象，也可通过命令行工具操作。

## 二.状态码
### 1.301和302有什么区别？
+ 301是永久重定向，而302是临时重定向。
+ 301这意味着请求的资源已经被分配了一个新的URI，以后的引用应该使用资源现在所指的URI。
+ 302它告诉客户端在此次请求中，应临时地从不同的URI响应请求，但客户端应继续使用原有的URI以便于以后的请求。

### 2.网页502的原因
**502 Bad Gateway 的常见原因：**

+ 后端服务不可用：后端服务崩溃或未启动。
+ 网络问题：网关与后端服务之间的网络连接失败。
+ 负载均衡配置错误：负载均衡器配置错误，无法正确转发请求。
+ 超时：后端服务响应超时，网关返回 502。
+ DNS 解析失败：网关无法解析后端服务的域名。

**排查步骤：**

1. 检查后端服务状态和日志。
2. 检查网络连接和防火墙配置。
3. 检查负载均衡器配置。
4. 检查 DNS 解析。

**总结：**502 通常由后端服务不可用或网络问题引起，需逐一排查。

### 3.Pod突然挂掉，K8S有什么机制或功能自动处理挂掉的Pod?
Kubernetes 提供以下机制自动处理挂掉的 Pod：  
**重启策略（RestartPolicy）：**

+ Always：默认策略，Pod 挂掉后自动重启。
+ OnFailure：仅在 Pod 非正常退出时重启。
+ Never：不重启。

**存活探针（Liveness Probe）：**  
检测容器是否健康，失败时重启容器。

**ReplicaSet/Deployment：**  
确保指定数量的 Pod 副本运行，Pod 挂掉后自动创建新 Pod。

**节点故障处理：**  
节点不可用时，Pod 会被重新调度到其他节点。

**总结：**通过重启策略、存活探针、ReplicaSet/Deployment 和节点故障处理，Kubernetes 自动恢复挂掉的 Pod。

### 5.我想把Pod调度到某个节点，有哪些方法?

> 📖 深度参考：[调度策略（污点、亲和、驱逐、抢占）](../01_Inbox/03-K8S/01-组件原理/03-Scheduler/调度策略(污点、亲和、驱逐、抢占).md) | [Pod 调度](../01_Inbox/03-K8S/02-集群负载/01-Pod/Pod调度.md)
将 Pod 调度到特定节点的方法：  
**节点选择器（nodeSelector）：**  
在 Pod 配置中指定节点标签。  
示例：

```yaml
spec:
  nodeSelector:
    disktype: ssd
```

**节点亲和性（nodeAffinity）：**  
更灵活的节点选择，支持硬性和软性要求。  
示例：

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: disktype
            operator: In
            values:
            - ssd
```

**污点和容忍（Taint and Toleration）：**  
在节点上设置污点，Pod配置容忍以调度到该节点。  
示例：

```bash
# 节点污点
kubectl taint nodes <node-name> key=value:NoSchedule
```

```yaml
# Pod 容忍
spec:
  tolerations:
  - key: "key"
    operator: "Equal"
    value: "value"
    effect: "NoSchedule"
```

**直接指定节点名称（nodeName）：**  
直接在 Pod 配置中指定节点名称。  
示例：

```yaml
spec:
  nodeName: <node-name>
```

**总结：**通过节点选择器、节点亲和性、污点和容忍、直接指定节点名称，将 Pod 调度到特定节点。

### 8.平时遇到的故障？
**故障示例1：MySQL 进程 CPU 占用过高**  
**故障现象：**  
使用 top 命令发现 MySQL 进程 CPU 占用过高。  
**排查步骤：**

1. 检查 MySQL 进程：登录 MySQL，执行 SHOW FULL PROCESSLIST; 查看进程信息，发现大量睡眠进程。
2. 检查 MySQL 配置文件，发现 wait_timeout 和 interactive_timeout 为默认值（8小时），导致大量 TCP 连接未关闭。
3. 调整配置：将 wait_timeout 和 interactive_timeout 设置为 120 秒，减少睡眠连接。
4. 检查磁盘 I/O：使用 atop 命令查看磁盘 I/O 使用情况，确认 innodb_buffer 配置合理。
5. 分析慢查询日志：开启慢查询日志，将日志下载到本地分析，发现耗时较多的 SQL 语句。将耗时 SQL 语句整理后交给开发优化。  
**解决结果：**调整 MySQL 配置后，CPU 占用恢复正常。

**其他故障：Zabbix Server 自动重启**  
**故障现象2：**Zabbix Server 频繁重启，日志显示内存不足。  
**排查步骤：**

1. 查看日志，发现 __zbx_mem_realloc(): out of memory 错误。
2. 调整 CacheSize 参数，从默认的 8M 增加到 256M。  
**解决结果：**重启 Zabbix Server 后，问题解决。

**总结：**通过调整 MySQL 配置和 Zabbix Server 参数，解决 CPU 占用过高和内存不足问题。

### 4. 了解linux的inode吗？

> 📖 深度参考：[Linux 文件系统 VFS 与 Ext4/XFS 底层剖析指南](../01_Inbox/02-Linux/04-存储与文件系统/03-Linux文件系统VFS与Ext4_XFS底层剖析指南.md)
inode（索引节点）是 Linux 和类 Unix 文件系统中用于存储文件元数据的重要数据结构。

+ **inode**：是一个数据结构，存储有关文件的信息，而不是文件的内容。每个文件和目录在文件系统中都有一个唯一的 inode
+ 数据结构：存储文件**元数据**的系统结构（大小、权限、时间戳等），每个文件/目录对应唯一的 Inode。
+ 存储位置：位于磁盘分区的 **Inode 表**中，文件系统初始化时固定分配一定数量的 Inode（如 Ext4 默认每16KB空间分配一个 Inode）。
+ 标识符：通过 **Inode 号**（整数）唯一标识文件（可通过 `ls -i` 或 `stat` 查看）。
+ 表面上，用户通过文件名，打开文件。实际上，系统内部这个过程分成三步：首先，系统找到这个文件名对应的inode号码；其次，通过inode号码，获取inode信息；最后，根据inode信息，找到文件数据所在的block，读出数据。

示例：

```bash
[root@kafka-pro test]# ls -i redis-key.sh
49134499 redis-key.sh
```

```bash
[root@kafka-pro face]# stat inode
 File: 'inode'
 Size: 219 Blocks: 0 IO Block: 4096 directory
Device: 803h/2051d Inode: 154115910 Links: 3
Access: (0755/drwxr-xr-x) Uid: ( 0/ root) Gid: ( 0/ root)
Access: 2025-02-28 15:17:32.866992355 +0800
Modify: 2025-02-28 15:17:32.229993620 +0800
Change: 2025-02-28 15:17:32.229993620 +0800
 Birth: -
```

### 5. 软连接和硬链接的区别？
**硬链接：**  
是指向文件数据的直接引用。它创建一个新的目录项，指向相同的 inode。  
文件的多个名称共享同一个 inode，删除任何一个链接不会影响其他链接。  
只能给文件做硬链接，不能给目录做硬链接

**软连接（符号链接）：**  
是指向另一个文件路径的引用。它创建一个新的文件，包含目标文件的路径。  
如果目标文件被删除，软连接会失效（变成"悬挂链接"）。

| 特性 | 硬链接 | 软连接 |
| --- | --- | --- |
| 指向 | 指向同一inode，指向的是文件的inode，而不是文件名称 | 指向目标文件或者目录名称 |
| 创建命令 | `ln <target_file> <link>` | `ln -s <target_file> <link>` |
| 跨文件系统 | 不支持 | 支持 |
| 目录链接 | 不能对目录创建 | 可以对文件和目录创建 |
| 删除行为 | 删除所有链接后数据才被移除 | 删除后软连接失效 |
| 面试官问区别，总结一句话回答：硬链接指向的是文件的inode，删除源文件数据不会被删除，需要删除所有的链接数据才被移除，软连接指向的是文件或者目录名称，删除源文件后数据就被移除，软链接失效。 |  |  |

### 8. http有哪些版本，有什么区别？

### 9. 一个tcp连接可以发起多少个http请求？
+ 在 **HTTP/1.0** 中，一个 TCP 连接只能发起一个 HTTP 请求。
+ 在 **HTTP/1.1** 中，多个请求可以在同一 TCP 连接上发起，但通常是顺序处理。
+ 在 **HTTP/2** 中，可以在一个 TCP 连接上并行发起多个 HTTP 请求，显著提高了效率和性能。

### 2.CMD和ENTRYPOINT定义启动命令有什么区别？
+ CMD：默认命令和参数，可被 docker run 覆盖。
+ ENTRYPOINT：主命令，参数可追加，不可覆盖。

**示例**  
**CMD：**

```dockerfile
CMD ["nginx", "-g", "daemon off;"]
```

**ENTRYPOINT：**

```dockerfile
ENTRYPOINT ["nginx"]
CMD ["-g", "daemon off;"]
```

**总结**

+ CMD：可覆盖，适合默认参数。
+ ENTRYPOINT：不可覆盖，适合主命令。

#### 2.mysql的查询你了解多少？
增删改查：select关键字；`select name,id from t1;`

+ ORDER BY：排序查询：`SELECT * FROM student ORDER BY age ASC`（升序，DESC倒序）
+ GROUP BY：分组查询：`select color,sum(price) from car group by color;`（从名为car的表中按照汽车的颜色（color）进行分组，并计算每种颜色汽车的总价格）

+ JOIN：连表查询：

    - `SELECT * FROM 表1 LEFT JOIN 表2 ON 连接条件` -- 左连接，以左表为基准，左表的数据都会显示
    - `SELECT * FROM 表1 RIGHT JOIN 表2 ON 连接条件` -- 右连接，以右表为基准，右表的数据都会显示

#### 3.MYSQL集群一主多从，主库宕机，如何合理切换到从库，其它从库如何处理？
**切换从库**

1. 确认主库宕机：通过监控工具、命令行等方式检查主库的连接状态、数据库进程是否正常运行，如尝试使用`mysql -u root -p -e 'SHOW SLAVE STATUS\G'`命令查看从库的状态和主库的连接是否正常。
2. 选择新主库：登录所有从库查看master.info文件或执行`SHOW SLAVE STATUS\G`命令，对比Relay_Master_Log_File和Exec_Master_Log_Pos等字段，选择pos最大、数据最完整且硬件资源和容量能够满足业务需求的从库作为新的主库。
3. 配置新主库：登录选定的从库（新的主库）执行`STOP SLAVE`命令停止从库复制。修改my.cnf配置文件，开启log-bin，并重启数据库服务。登录数据库执行`RESET MASTER`，使用`SHOW MASTER STATUS\G`查看主库信息。创建授权同步用户与权限和网站使用数据库的用户与权限。
4. 修改连接信息：修改应用程序连接主库的配置文件，将原来指向主库的连接信息改为新主库的连接信息。

**处理其他从库**

1. 重新配置同步：登录其他从库，执行`STOP SLAVE`停止复制，使用`CHANGE MASTER TO`命令修改主库连接信息，指向新的主库，并指定正确的MASTER_LOG_FILE和MASTER_LOG_POS等参数，最后执行`START SLAVE`启动从库复制进程，查看同步状态。
2. 检查复制状态：密切关注所有从库与新主库之间的复制进程是否正常，可通过`SHOW SLAVE STATUS\G`命令查看Slave_IO_Running和Slave_SQL_Running等字段的值是否为Yes，如果有异常，需要及时进行修复。
3. 调整从库策略：根据业务需求，可对部分从库进行特殊处理。如将一些从库设置为延迟从库，用于数据恢复或审计等特殊用途；若某个从库硬件资源紧张或对系统整体性能影响较大，可暂时关闭其复制进程或调整复制频率以减轻新主库的负担。

#### 4.MySQL怎么保证高可用，断电怎么办？
**高可用方案**

1. **主从复制**：配置主从，主库写，从库读，分散压力。
2. **双主复制**：双向同步，两个主库互相复制，任一主库宕机，另一主库继续服务。
3. **集群方案**：MySQL Group Replication：基于Paxos协议，自动故障转移。
4. **中间件**：ProxySQL（读写分离、故障转移）、MHA（Master High Availability，自动主从切换）。

**断电处理**

1. **UPS（不间断电源）**：部署UPS，确保短暂断电时系统正常运行。
2. **数据持久化**：配置`innodb_flush_log_at_trx_commit=1`和`sync_binlog=1`，保证数据不丢失。
3. **备份与恢复**：定期备份，使用`mysqldump`或`Percona XtraBackup`定期备份，定期测试备份恢复流程，确保数据可恢复。

#### 5.MySQL的1主2从高可用，网络抖动造成从库1 ping不通主库，如何防止脑裂
1. **超时机制**：配置合理的复制超时时间，避免短暂网络抖动导致从库断开。`CHANGE MASTER TO MASTER_HEARTBEAT_PERIOD=2;`
2. **仲裁机制**：引入仲裁节点（如ZooKeeper、Consul）判断主库状态，多数派决策，确保主库和从库之间的决策基于多数派，避免单点故障。
3. **半同步复制**：配置半同步，确保至少一个从库确认写入后才返回成功。
4. **监控与告警**：使用监控工具（如Prometheus、Zabbix）实时监控网络状态和复制延迟，设置告警规则，及时发现和处理网络抖动。
5. **手动干预**：在网络抖动时，手动确认主库状态并决定是否切换。

#### 6.MySQL故障切换后，为什么VIP不生效?
VIP漂移后不生效的常见原因：

1. **ARP缓存问题**：VIP漂移后，ARP缓存未及时更新，导致流量仍指向旧主库。
2. **网络配置问题**：网络设备（如交换机、路由器）配置未及时同步，导致流量未正确路由。
3. **应用连接池问题**：应用连接池未刷新，仍保持与旧主库的连接，且未配置自动重连机制。
4. **DNS缓存问题**：DNS缓存未更新，导致应用仍解析到旧主库的IP。

#### 9.mysql主从原理，搭建主从的流程说一下？
**主从复制原理**

1. 主库：记录数据变更到二进制日志。
2. 从库：通过I/O线程读取主库的二进制日志，保存到中继日志，SQL线程执行中继日志中的操作以同步数据。

**搭建流程**

1. 配置主库：启用二进制日志，设置唯一服务器ID，创建复制账号并授权，获取二进制日志文件名和位置。
2. 配置从库：设置唯一服务器ID，使用`CHANGE MASTER TO`命令配置复制参数，指定主库信息和二进制日志位置，执行`START SLAVE;`启动复制进程。
3. 验证复制状态：使用`SHOW SLAVE STATUS\G`检查，确保Slave_IO_Running和Slave_SQL_Running都为Yes。

#### 10.主从切换流程说一下，如何保证主从切换数据一致性？
**主从切换流程**

1. 确认当前主从状态：查看主从复制状态，记录主服务器的二进制日志文件名和位置。
2. 停止写操作：在原主服务器上执行`FLUSH TABLES WITH READ LOCK;`锁定所有表，停止写操作。
3. 等待数据同步：等待从服务器同步完成，当Seconds_Behind_Master为0时表示数据已同步。
4. 提升从服务器为主服务器：在要提升的从库上执行`STOP SLAVE; RESET MASTER;`。
5. 配置其他从服务器指向新主库：在其他从库上执行`CHANGE MASTER TO`指向新主库，启动复制。
6. 恢复原主服务器写操作：如果原主服务器后续作为从库使用，先`UNLOCK TABLES;`，再配置为新主库的从库。

**保证数据一致性的方法**

1. 使用GTID：全局事务标识符，确保每个事务在主从之间具有唯一标识，避免数据丢失或重复。
2. 设置参数：`sync_binlog=1`和`innodb_flush_log_at_trx_commit=1`，确保二进制日志和InnoDB事务日志及时持久化。
3. 监控主从延迟：主从切换前确保延迟为0。
4. 数据校验：切换完成后使用`pt-table-checksum`校验数据一致性。

#### 12.慢日志如何设置，以及分析？

2. 使用mysqldumpslow：`mysqldumpslow /var/log/mysql/mysql-slow.log`

4. 使用EXPLAIN：对慢查询SQL使用EXPLAIN分析执行计划，找出优化点。

#### 13.binlog，redolog和undolog有什么区别？
| 特征 | Binlog | Redolog | Undolog |
| --- | --- | --- | --- |
| 日志形式 | 二进制日志（逻辑日志） | 重做日志（物理日志） | 回滚日志（逻辑日志） |
| 主要用途 | 数据复制、备份和恢复 | 确保事务持久性和恢复 | 支持事务回滚 |
| 存储内容 | 数据更改操作，读操作不记录 | 修改后的数据 | 修改前的状态 |
| 是否必选 | 可选（需开启log_bin配置） | InnoDB必选（事务持久化的核心机制） | InnoDB必选(事务原子性和MVCC的基础) |
| 写入顺序 | 后写入数据文件 | 先写入日志再写数据 | 记录历史以支持回滚 |
| 与事务关系 | 记录已提交的事务 | 记录未提交和已提交的事物修改 | 记录未提交事务的旧数据版本 |
| 恢复机制 | 用于数据恢复和复制 | 用于恢复未写入的数据 | 用于撤销未提交的事务 |

#### 15.mysql的b+树索引了解么?
B+树是一种广泛用于数据库系统中的索引数据结构：

+ 节点：B+树的每个节点可以包含多个键和指针。内部节点存储键（用于导航），而叶子节点存储实际的数据记录或指向数据记录的位置。
+ 叶子节点：所有的叶子节点在同一层级，且通过指针相连，形成一个链表，方便范围查询。
+ 总结：B+树是MySQL中一种高效的索引结构，具有平衡性、多路性和顺序访问的特点。它的设计使得查找、插入和删除操作都能在对数时间内完成，并且在执行范围查询时表现出色，因此广泛应用于数据库索引中。

#### 16.mysql集群模式你们有哪些，MGR,MHA搭建过么？
**MGR（MySQL Group Replication）**

+ 简介：MySQL官方提供的集群方案，基于Paxos协议，实现分布式下数据最终一致性。
+ 特点：高一致性、高容错性、高扩展性、支持单主/多主模式。
+ 搭建：准备3台以上服务器，安装MySQL 8.0+，配置MGR参数，安装插件，启动MGR。

**MHA（Master High Availability）**

+ 简介：一套优秀的MySQL高可用故障切换和主从复制软件，解决MySQL单点故障问题。
+ 特点：自动故障切换、数据一致性保障、支持一主多从架构。
+ 搭建：准备至少3台服务器（一主两从），配置主从复制，配置SSH免密登录，安装MHA Manager和Node组件，配置MHA并验证。

#### 17.mysql主从复制数据延迟怎么解决？
延迟常见原因和解决方案：

1. 从库硬件差：升级从库硬件配置。
2. 主库写并发大：使用MySQL多线程复制（高版本支持）。
3. 慢SQL过多：优化慢查询SQL。
4. 网络延迟：优化网络，调整`slave-net-timeout`和`master-connect-retry`参数。
5. 主库/从库负载过高：使用多台从库分摊读压力，避免从库进行其他高负载操作。

#### 18.mysql主从复制过程中数据丢失怎么办？
1. 检查复制状态：`show slave status\G`检查Last_SQL_Error和Last_IO_Error，检查主库状态`SHOW MASTER STATUS`。
2. 停止从库复制，重置从库，重新同步。
3. 检查主从库数据的一致性：使用`CHECKSUM TABLE`或Percona Toolkit工具校验。
4. 预防：配置半同步复制，定期检查主从数据一致性。

### redis相关
#### 1.redis是单线程还是多线程，多线程用在哪些场景？
**单线程**

+ 特点：Redis核心网络IO和命令处理是单线程的。
+ 优点：简单高效，避免多线程竞争和锁的开销。
+ 缺点：无法充分利用多核CPU，性能受限于单线程。

**多线程**

+ 特点：Redis 6.0引入多线程，主要用于处理网络IO。
+ 优点：提高网络IO性能，适合高并发场景。
+ 缺点：命令处理仍为单线程，复杂命令可能阻塞。
+ 配置：

```properties
io-threads 4
io-threads-do-reads yes
```

**多线程使用场景**

+ 高并发读写：大量客户端连接，网络IO成为瓶颈。
+ 大流量应用：需要处理大量并发请求的应用。
+ 高吞吐需求：需要高吞吐量的数据处理场景。

#### 2.redis集群你们有哪些优化策略?
1. **数据分片**：哈希槽：将数据均匀分布到16384个哈希槽中，预分片避免数据倾斜。
2. **读写分离**：主从复制，主节点写，从节点读，分散读压力，配置`replica-read-only yes`。
3. **持久化优化**：
    - RDB：定时生成快照，适合备份：`save 900 1; save 300 10; save 60 10000`
    - AOF：记录写操作，适合数据恢复：`appendonly yes; appendfsync everysec`
4. **内存优化**：
    - 淘汰策略：根据业务需求选择合适的淘汰策略：`maxmemory-policy volatile-lru`
    - 压缩存储：使用压缩算法减少内存占用：`rdbcompression yes`
5. **网络优化**：使用连接池，Redis 6.0+启用多线程IO：`io-threads 4`
6. **监控与告警**：使用Prometheus等监控工具，设置性能指标告警。

#### 3.redis模式有几种，什么情况下用什么模式?
1. **单机模式**：单个Redis实例，简单易用，部署维护方便，缺点是单点故障，性能受限。适合小规模应用、开发测试环境。
2. **主从复制模式**：主节点写，从节点读，数据同步，优点是读写分离，提高读性能，缺点是主节点单点故障，写性能受限。适合读写分离场景，读多写少的应用。
3. **哨兵模式（Sentinel）**：主从复制加哨兵监控，自动故障转移，优点是高可用，自动主从切换，缺点是写操作集中在主节点，扩展性有限。适合需要高可用的生产环境，中小规模应用。
4. **集群模式（Cluster）**：分布式存储，数据分片，自动故障转移，优点是高可用，高性能，支持水平扩展，缺点是配置复杂，维护成本高。适合大规模应用，需要水平扩展和高性能的生产环境。

#### 4.redis的淘汰算法是什么？
+ **noeviction**：当内存达到限制时，Redis不会自动淘汰任何键，新写入操作会返回错误。
+ **volatile-lru**：仅对设置了过期时间的键使用LRU算法，淘汰最近最少使用的过期键。
+ **allkeys-lru**：使用LRU算法从所有键中淘汰最久未被访问的键。
+ **volatile-ttl**：根据键的剩余生存时间（TTL）进行淘汰，优先删除即将过期的键。
+ **volatile-random**：仅对设置了过期时间的键随机淘汰一个键。
+ **allkeys-random**：从所有键中随机淘汰一个键。  
配置：在redis.conf中设置：`maxmemory-policy volatile-lru`

### 4.kafka如何保证数据不丢失，重复消费？
**保证数据不丢失的策略**

+ **生产者端**：设置`acks=all`，确保生产者在收到所有副本的确认后才认为消息发送成功；配置retries参数，发送失败自动重试。
+ **Broker端**：副本机制，每个分区有多个副本（ISR），当Leader宕机时，Follower可以接管；持久化存储，数据写入磁盘并持久化，即使Broker重启数据也不会丢失。
+ **消费者端**：偏移量管理，消费者在处理完消息后再提交偏移量，避免重复消费；使用消费者组，确保每个分区的消息只被一个消费者实例消费。

**避免重复消费的策略**

+ 消费者组机制：通过消费者组确保每个分区的消息只被一个消费者实例消费。
+ 手动提交偏移量：消费者在处理完消息后手动提交偏移量，避免因故障导致的重复消费。
+ 幂等性处理：在业务逻辑中实现幂等性，确保即使消息被重复处理也不会产生错误。

### 5.kafka（Producer）、消费者（Consumer）、代理节点（Broker）、主题（Topic）、分区（Partition）和副本（Replica)分别是什么？
+ **生产者（Producer）**：消息的生产者，将消息发布到 Kafka 的 Topic 中。
+ **消费者（Consumer）**：消息的消费者，从 Kafka 的 Topic 订阅并消费消息。
+ **代理节点（Broker）**：Kafka 集群中的单个服务器节点，负责消息的存储和传输，处理生产者和消费者的请求。
+ **主题（Topic）**：消息的分类，生产者将消息发送到特定 Topic，消费者从 Topic 订阅消息。
+ **分区（Partition）**：Topic 的物理分片，提高并发处理能力，每个分区可以在不同的 Broker 上。
+ **副本（Replica）**：分区的备份，确保数据冗余和高可用性，Leader 副本处理读写请求，Follower 副本同步数据。

### 2.zabbix主动模式被动模式的区别，以及proxy的作用？
**主动模式**

+ 数据采集方式：Zabbix Agent主动采集数据并发送到Zabbix Server或Proxy。
+ 优点：减轻Zabbix Server的压力，适合大规模监控环境。
+ 适用场景：监控设备数量较多或网络不稳定时使用。

**被动模式**

+ 数据采集方式：Zabbix Server或Proxy主动向Zabbix Agent请求数据。
+ 优点：配置简单，是Zabbix的默认工作模式。
+ 缺点：在大规模环境中会增加Zabbix Server的工作量。

**Zabbix Proxy的作用**

+ 分担负载：代替Zabbix Server收集监控数据，减轻Server的负载。
+ 分布式监控：支持分布式监控架构，适用于跨地域或大规模的监控环境。
+ 数据缓存：Proxy可以缓存数据，当与Server连接中断时，可以继续收集数据并在连接恢复后发送。
+ 简化管理：简化了分布式监控的维护，使得监控系统的扩展和管理更加方便。

### 3.zabbix自动发现以及监控的流程说一下？
**自动发现流程**

1. 配置自动发现规则：在Zabbix Web界面的"Configuration" -> "Discovery"中创建自动发现规则，指定要扫描的IP地址范围和端口，以及用于发现主机的条件。
2. 执行发现任务：Zabbix Server根据配置的规则定期扫描网络，检测符合规则的主机。
3. 执行动作：根据发现事件，执行预定义的动作，如自动将新主机添加到监控中，关联到相应的模板，添加到指定主机组。

**监控流程**

1. 数据采集：Zabbix Agent安装在被监控的主机上，负责收集主机的性能数据，可以通过主动或被动模式传输。
2. 数据存储：Zabbix Server接收数据并存储在数据库中。
3. 数据处理与展示：Server对数据进行处理和分析，触发器根据预设条件评估数据，生成事件，通过Web界面展示监控数据、图表、报表。
4. 告警与通知：当触发器检测到异常时，触发动作，如发送告警通知给管理员。

### 4.zabbix报警如何触发，报警级别有哪些？
**报警触发机制**

+ 触发器（Trigger）：定义一个或多个条件，当这些条件满足时，触发器会被触发，生成一个事件。
+ 动作（Action）：触发器触发后，会执行预定义的动作，如发送通知、执行脚本等。

**报警级别**

+ Not classified：未分类
+ Information：信息
+ Warning：警告
+ Average：一般
+ High：高危
+ Disaster：灾难

### 7.prometheus报警策略，分级报警，静默？
**报警策略**

+ 规则配置：在Prometheus的配置文件中定义报警规则，由条件表达式和持续时间组成，如CPU使用率超过80%并持续5分钟触发报警。
+ 评估与触发：Prometheus按设定的时间间隔评估报警规则，条件满足持续时间后触发报警。

**分级报警**

+ 定义级别：根据报警的严重程度定义不同的级别（如严重、重要、次要），如CPU超过90%为严重，80%-90%为重要，70%-80%为次要。
+ 关联规则与动作：不同级别报警关联不同的通知方式，严重级别发短信，重要发邮件，次要显示在监控平台，同时设置不同的通知频率。

**静默**

+ 作用：在特定时间段内暂停对某些报警的通知，如计划性维护时避免发送无关报警。
+ 设置方式：通过Prometheus的Web界面或API设置静默规则，可根据标签、时间段等条件定义。

+ Master节点监控：使用kube-state-metrics插件采集apiserver、controller-manager等组件指标。
+ 所有指标由Prometheus存储，通过Grafana进行可视化展示。

### 9.Prometheus是如何获取数据并展示的？以及如何推送到微信或者钉钉？
**数据获取与展示**

1. prometheus.yml中定义要监控的目标（targets），可以是各种exporter，支持静态配置和服务发现。
2. 抓取到的数据存储在Prometheus的本地时间序列数据库（TSDB）中。
3. 可以通过Prometheus自带的Web控制台输入PromQL查询，也可以使用Grafana进行可视化展示。

**推送到微信/钉钉**

1. 使用Alertmanager组件处理报警，配置报警规则。
2. 使用开源工具如prometheus-webhook-dingtalk/prometheus-webhook-wechat将Alertmanager的告警转发。

### 3.流量从客户端到后端的过程是什么，假设客户使用CDN访问你们业务，如何获取客户的真实IP？
**流量过程**

1. 客户端发起请求。
2. DNS解析：客户端通过 DNS 解析获取 CDN 节点 IP。
3. CDN节点：请求到达最近的 CDN 节点，CDN 节点缓存静态资源或转发动态请求到源站。
4. 负载均衡：请求到达负载均衡器，分发到后端服务器。
5. 后端服务器：处理请求并返回响应。

**获取客户真实IP**

+ CDN 会在 HTTP 头中添加客户真实 IP：`X-Forwarded-For`（包含客户端和所有代理服务器的IP列表）、`X-Real-IP`（包含客户端的真实IP）。
+ Nginx配置：

```nginx
real_ip_header X-Forwarded-For;
set_real_ip_from 0.0.0.0/0;
```

+ 应用层获取：Python示例：`client_ip = request.headers.get('X-Forwarded-For', request.remote_addr)`；Java示例：`String clientIp = request.getHeader("X-Forwarded-For");`

### 4.混合云部署有么？
**混合云部署架构**

1. **架构设计**
    - 公有云：用于弹性扩展、高可用性和全球分发。
    - 私有云：用于敏感数据处理和合规性要求。
    - 网络连接：使用 VPN 或专线连接公有云和私有云。
2. **部署策略**
    - 公有云部署前端应用、无状态服务和需要弹性扩展的服务。
    - 私有云部署核心业务系统、敏感数据处理和合规性要求的服务。
    - 数据同步：使用数据同步工具同步公有云和私有云的数据。
    - 负载均衡：使用全局负载均衡器分发流量。
3. **监控与管理**
    - 统一监控：使用Prometheus、Grafana监控公有云和私有云的资源和服务。
    - 统一管理：使用混合云管理平台管理公有云和私有云的资源。
