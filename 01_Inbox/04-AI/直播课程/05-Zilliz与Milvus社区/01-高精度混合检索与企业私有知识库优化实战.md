## 1. 为什么纯向量检索在企业知识库中会失效？

传统仅依赖 Embedding 语义检索的 RAG 经常在以下关键业务场景中遭遇“灾难性漏召”：

```mermaid
graph TD
    UserQuery[用户精确查询: 错误码 ERR-502 / 货号 SKU-9908 / 员工身份证号] --> FailCase1[纯向量检索: 语义平滑导致精准代号被忽略，召回一堆不相干的错误解释]
    UserQuery --> FailCase2[纯关键词检索: 无法理解用户同义词与意图变换]
    
    FailCase1 & FailCase2 ==> HybridSolution[必须采用: 密集向量 (Dense) + 稀疏关键词 (Sparse/BM25) 混合检索 + RRF 融合]
```

1. **精准代号与专有名词**：零件编号、API 接口名、法规文号在 Embedding 空间中往往向量距离接近，缺乏关键词绝对匹配能力。
2. **长尾与生僻字词**：通用预训练模型未见过特定行业内部缩写词，导致向量投影失真。

## 3. 核心算法与代码实现

### 3.1 RRF（Reciprocal Rank Fusion）倒数排名融合公式

对于任一文档 $d$，其在多路检索中的最终 RRF 得分为：

$$RRF\_Score(d) = \sum_{m \in M} \frac{1}{k + rank_m(d)}$$

> **参数说明**：$M$ 为检索通路集合（如 Dense 向量路与 Sparse 关键词路），$rank_m(d)$ 为文档在第 $m$ 路中的排名（1-indexed），$k$ 为平滑常数（工业界通常取值 $k = 60$）。

---

### 3.2 基于 PyMilvus 的企业级混合检索代码

```python
from pymilvus import (
    connections, FieldSchema, CollectionSchema, DataType, 
    Collection, AnnSearchRequest, RRFRanker, WeightedRanker
)

# 1. 连接 Milvus 生产集群
connections.connect("default", host="milvus-cluster.internal", port="19530")

collection_name = "enterprise_knowledge_base"
collection = Collection(collection_name)

# 2. 构造 Dense 与 Sparse 的多路 AnnSearchRequest
def hybrid_search_knowledge(dense_vector, sparse_dict, top_k=5):
    # 密集向量搜索请求 (HNSW 索引)
    dense_req = AnnSearchRequest(
        data=[dense_vector],
        anns_field="dense_vector",
        param={"metric_type": "COSINE", "params": {"ef": 64}},
        limit=50
    )
    
    # 稀疏关键词搜索请求 (SPARSE_INVERTED_INDEX)
    sparse_req = AnnSearchRequest(
        data=[sparse_dict],
        anns_field="sparse_vector",
        param={"metric_type": "IP", "params": {"drop_ratio_search": 0.2}},
        limit=50
    )

    # 3. 使用 RRF 算法进行多路融合打分
    ranker = RRFRanker(k=60)
    
    # 执行混合搜索
    results = collection.hybrid_search(
        reqs=[dense_req, sparse_req],
        rerank=ranker,
        limit=top_k,
        output_fields=["doc_id", "content", "department", "source_url"]
    )
    
    return results[0]
```

## 4. 生产级向量库调优与多租户隔离指南

1. **索引选型黄金策略**：
   - **内存充足、追求极速响应**：选用 `HNSW`（配置 `M=16~32, efConstruction=200~500`），QPS 极高且召回率在 98% 以上。
   - **海量数据（亿级以上）、预算受限**：选用 `IVF_PQ` 或 `SCANN`，配合 SQ8 量化压缩显存与内存开销 70%。
2. **多租户与权限隔离（Multi-Tenancy）**：
   - ❌ 错误做法：为每个企业客户单独建一个 Collection，导致 Metadata 膨胀、Milvus 协调节点（RootCoord）崩溃。
   - ✅ 正确做法：单 Collection 内设计 `Partition Key`（如按 `tenant_id` 或 `dept_id` 分区），检索时在底层引擎物理过滤，兼具高隔离性与资源复用。

## 5. 讲座 Q&A 互动精华

- **Q：在混合检索中，RRF 和加权打分（Weighted Scoring）哪种更优？**
  - **讲师解答**：**推荐默认首选 RRF**。因为 Dense（Cosine）和 Sparse（BM25 分数）的数值分布基准完全不同，加权打分需要大量人工调权重（例如 0.7 向量 + 0.3 关键词）且容易过拟合。RRF 仅依赖相对排名（Rank），对跨通路分数的鲁棒性极高。
