# 🧭 K8S 调度策略：亲和力、污点与节点平滑维护实战

Kubernetes 提供了丰富的调度配置规则，允许用户基于业务属性、高可用拓扑和物理隔离等需求，控制 Pod 的节点流向。同时，也为节点升级维护提供了一套平滑的隔离与驱逐工作流。

---

## 一、 Pod 指派与节点亲和性 (Node Affinity)

### 1. 基础指派：nodeSelector 与 nodeName
*   **nodeName**（强指派）：
    直接指定运行的节点名称。这会绕过 `kube-scheduler` 调度器的过滤与打分流程，Kubelet 直接接管并创建。
    ```yaml
    spec:
      nodeName: k8s-node01  # 直接调度到指定节点
    ```
*   **nodeSelector**（标签过滤）：
    简单的键值对匹配。只有拥有对应 Label 的节点才可以运行该 Pod。
    ```yaml
    spec:
      nodeSelector:
        disktype: ssd       # 节点必须有 disktype=ssd 的标签
    ```

---

### 2. 节点亲和性 (Node Affinity)
节点亲和性是 `nodeSelector` 的增强版，支持复杂的布尔表达式，并分为“硬限制”与“软限制”。

*   **硬亲和性 (requiredDuringSchedulingIgnoredDuringExecution)**：
    *   **特点**：必须满足。如果找不到符合条件的节点，Pod 调度失败，处于 Pending 状态。
*   **软亲和性 (preferredDuringSchedulingIgnoredDuringExecution)**：
    *   **特点**：尽量满足。条件不满足时，Pod 可被编排到其他不合规节点。支持为每个条件定义 `weight`（权重，1~100），调度器会将各项权重打分累加，选择得分最高的节点。

#### 节点亲和配置示例
```yaml
spec:
  affinity:
    nodeAffinity:
      # 1. 硬亲和规则：必须拥有 gpu 标签，且不能是 master 节点
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: gpu
            operator: Exists
          - key: node-role.kubernetes.io/master
            operator: DoesNotExist
      # 2. 软亲和规则：优先调度到 disktype=ssd 的节点
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 80
          preference:
            matchExpressions:
            - key: disktype
              operator: In
              values:
              - ssd
```

> [!NOTE]
> **操作符 (Operators)**：
> 亲和性计算支持 `In` (在列表中)、`NotIn` (不在列表中)、`Exists` (存在此键)、`DoesNotExist` (不存在此键)、`Gt` (大于)、`Lt` (小于)。

## 二、 Pod 亲和与反亲和性 (Pod Affinity & Anti-Affinity)

Pod 间的亲和与反亲和控制的是 **Pod 与 Pod 之间的空间局部性**（即：让相关联的 Pod 靠拢，或让互斥的 Pod 散开）。

*   **Pod 亲和性 (podAffinity)**：
    将相关的 Pod 调度到同一“物理范围”内。如将 Web 前端与 Redis 缓存放置在同一个机架/可用区，以减少网络延迟。
*   **Pod 反亲和性 (podAntiAffinity)**：
    防止相同的 Pod 堆叠在同一个节点/机架上。如将同一个服务的 3 个副本分散在不同的物理机上，实现真正的高可用，避免单点物理故障。

### 拓扑域的概念 (topologyKey)
亲和性判定不是基于抽象的物理位置，而是基于节点上的 Label（通常是 `topologyKey`）。
*   若以节点名作拓扑域：`topologyKey: kubernetes.io/hostname`
*   若以机房作拓扑域：`topologyKey: topology.kubernetes.io/zone`

#### Pod 间反亲和配置示例 (高可用多节点打散)
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 3
  template:
    spec:
      affinity:
        podAntiAffinity:
          # 强制将相同的 Pod 在主机维度打散，同一台物理机上不能跑两个此 Web Pod
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchExpressions:
              - key: app
                operator: In
                values:
                - web-app
            topologyKey: kubernetes.io/hostname
```

> [!CAUTION]
> **性能开销警告**：
> Pod 亲和/反亲和性计算需要遍历集群内已存在的 Pod 以及它们的标签。在大规模集群（500+ 节点，上万 Pod）中，**过多使用 Pod 亲和/反亲和性会导致调度器的吞吐性能出现显著下降**。

## 三、 节点污点与 Pod 容忍度 (Taints & Tolerations)

亲和性是 Pod “倾向/必须去”某些节点，而**污点 (Taint)** 是节点“主动拒绝”不符合条件的 Pod。

### 1. 污点效用标识 (Effect)
Taint 的格式为 `key=value:effect`。共有三种效用类型：
1.  **NoSchedule**（硬限制，不调度）：
    不能容忍此污点的 Pod 绝不会被调度到该节点。已运行在节点上的 Pod 不受影响。
2.  **PreferNoSchedule**（软限制，尽量不调度）：
    调度器会尽量避免调度无容忍的 Pod 到此节点，除非整个集群没有其他可用节点。
3.  **NoExecute**（强驱逐）：
    不能容忍此污点的新 Pod 不能调度，且**节点上现存的 Pod 如果无法容忍该污点，会被立即驱逐**。

### 2. 命令操作
```bash
# 设置节点污点 (例如标记节点为专用 GPU 节点)
kubectl taint nodes k8s-node01 node-type=gpu:NoSchedule

# 查看节点上的污点
kubectl get nodes k8s-node01 -o jsonpath='{.spec.taints}'

# 删除节点上指定键名的污点
kubectl taint nodes k8s-node01 node-type:NoSchedule-
```

### 3. Pod 容忍度 (Tolerations) 配置
Pod 可以声明 `tolerations` 来接纳节点的污点：
```yaml
spec:
  tolerations:
  - key: "node-type"
    operator: "Equal"
    value: "gpu"
    effect: "NoSchedule"
  # 针对 NoExecute 污点，可以配置容忍宽限期
  - key: "node-type"
    operator: "Exists"
    effect: "NoExecute"
    tolerationSeconds: 3600  # 如果节点被打了此 NoExecute 污点，Pod 仍可在该节点上额外运行 1 小时再被驱逐
```

## 四、 节点平滑维护工作流 (Cordon & Drain)

在集群日常维护中，如需对某节点进行系统升级（重启、重装、更新内核等），必须采用 **不可调度 (Cordon) -> 排干 (Drain) -> 维护 -> 恢复 (Uncordon)** 的标准生产工作流，以保障业务流量无感知。

```text
               ┌───────────────────────┐
               │    1. Cordon 隔离     │ (节点标记为不可调度)
               └───────────┬───────────┘
                           │
                           ▼
               ┌───────────────────────┐
               │     2. Drain 驱逐     │ (驱逐已有业务 Pod 到其他节点)
               └───────────┬───────────┘
                           │
                           ▼
               ┌───────────────────────┐
               │    3. 物理系统维护    │ (系统升级/重装/重启)
               └───────────┬───────────┘
                           │
                           ▼
               ┌───────────────────────┐
               │   4. Uncordon 恢复    │ (恢复可调度状态，接纳新 Pod)
               └───────────────────────┘
```

### 1. 详细步骤与命令执行

#### 步骤 1：Cordon 隔离
将节点标记为不可调度状态（`SchedulingDisabled`）。此操作**不影响正在运行的 Pod**，仅阻止新 Pod 被调度过来。
```bash
kubectl cordon k8s-node02
```

#### 步骤 2：Drain 驱逐 (排干)
安全地把该节点上的 Pod 驱逐（Evicted）到其他节点上运行。
```bash
# 忽略 DaemonSet (因为它们由 DaemonSet 控制器管理且必须运行在每台机器上)
# 允许删除本地数据卷临时存储的 Pod
kubectl drain k8s-node02 --ignore-daemonsets --delete-emptydir-data --force
```

#### 步骤 3：展开节点物理维护
此时节点已无业务负载，可安全执行关机、系统重装或重启。

#### 步骤 4：Uncordon 恢复
维护结束后，将节点恢复为可调度状态，重新接收集群流量。
```bash
kubectl uncordon k8s-node02
```

---

### 2. 生产环境无损驱逐的三大红线条件

如果直接执行 `kubectl drain`，在没有配置保护的前提下，可能会导致部分业务因副本数不够发生短时中断。必须满足以下三条红线：

1.  **副本数红线**：
    被驱逐的 Pod 所属的 Deployment 副本数（`replicas`）**必须大于 1**。如果是单副本应用，驱逐必然引发业务中断。
2.  **反亲和红线**：
    必须为 Deployment 配置 **Pod 反亲和性 (PodAntiAffinity)**，将多个副本强制打散在不同的物理节点上。否则，多个副本若在同一个节点上，驱逐时依然会全军覆没。
3.  **发布限制红线**：
    滚动更新的 maxUnavailable 限制。同时，建议配置 **PodDisruptionBudget (PDB, Pod 中断预算)** 限制驱逐时的最大不可用副本数，强行迫使调度器分批进行驱逐：
    ```yaml
    apiVersion: policy/v1
    kind: PodDisruptionBudget
    metadata:
      name: web-pdb
    spec:
      minAvailable: 2  # 强制保证即使在驱逐/中断期间，最少也有 2 个副本处于健康运行状态
      selector:
        matchLabels:
          app: web-app
    ```
