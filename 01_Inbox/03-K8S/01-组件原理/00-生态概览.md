# 🌐 Kubernetes 生态与分层架构概览

Kubernetes 不仅仅是一个容器编排工具，而是一个庞大的云原生操作系统级生态体系。理解其分层架构与核心 API 设计原则，对于设计高可用、可扩展的分布式系统至关重要。

---

## 一、 Kubernetes 分层架构

Kubernetes 系统整体呈现清晰的层级划分，每一层为上层提供标准抽象：

```text
┌────────────────────────────────────────────────────────┐
│             接口层 (Kubectl / client-go SDK)            │
├────────────────────────────────────────────────────────┤
│           管理层 (度量监控 / 自动扩缩 / RBAC 策略)       │
├────────────────────────────────────────────────────────┤
│             应用层 (Deploy / StatefulSet / Service)    │
├────────────────────────────────────────────────────────┤
│           核心层 (API Server / 声明式控制面驱动)       │
└────────────────────────────────────────────────────────┘
```

*   **核心层 (Core Layer)**：
    *   **职责**：提供 Kubernetes 最基础的控制与执行机制。
    *   **组件**：对外暴露 RESTful API 构建高层应用，对内提供核心插件式的对象执行环境。
*   **应用层 (Application Layer)**：
    *   **工作负载**：无状态应用 (Deployment, ReplicaSet)、有状态应用 (StatefulSet)、批处理任务 (Job, CronJob)、守护进程 (DaemonSet) 等。
    *   **路由发现**：服务发现与流量路由 (Service, Ingress, CoreDNS)。
*   **管理层 (Governance Layer)**：
    *   **系统度量**：基础设施、容器状态和网络通信度量 (Metrics API, kube-state-metrics)。
    *   **自动化控制**：水平自动扩缩 (HPA)、动态存储卷分配 (Dynamic Volume Provisioning)。
    *   **策略管控**：权限治理与网络安全 (RBAC、ResourceQuota、LimitRange、NetworkPolicy)。
*   **接口层 (Interface Layer)**：
    *   提供与集群交互的入口，包含命令行工具 `kubectl`、多语言客户端 SDK (`client-go` 等) 以及多集群管理联邦。

---

## 二、 内部与外部生态范畴

在接口层之上是庞大的容器编排管理生态，其边界可以划分为集群内部与外部：

| 生态范畴 | 包含的领域与组件 |
| :--- | :--- |
| **Kubernetes 内部** | CRI (容器运行时接口)、CNI (网络插件接口)、CSI (存储插件接口)、Cloud Provider (云厂商适配)、私有/公共镜像仓库等。 |
| **Kubernetes 外部** | 日志收集系统 (EFK/Loki)、监控指标系统 (Prometheus/Grafana)、配置与密钥管理、CI/CD 流水线 (Tekton/Argo)、微服务网格 (Istio) 等。 |

## 三、 核心 API 设计原则

Kubernetes API 的稳定性与水平伸缩性来自于其严苛的系统设计规范：

1.  **所有 API 必须是声明式的 (Declarative)**：
    *   相较于传统命令式操作（如“创建容器”），声明式操作（如“期望状态为 3 个 Pod”）对于重复操作是天然幂等的。这在不稳定的分布式网络中至关重要。
    *   API 对象通常都是**名词性质**的（如 Service、Volume），代表用户所期望得到的最终目标状态。
2.  **API 对象彼此互补且可组合 (Combinable)**：
    *   遵循“高内聚、松耦合”的原则。将大概念分解为职责单一、高重用性的微小对象（如 Pod 负责运行容器，Service 负责流量代理，它们通过 Label 灵活组合）。
3.  **高层 API 隐藏技术实现，以操作意图为基础**：
    *   API 设计从业务需求出发（例如“Deployment 强调应用发布”），而不是过早地从底层技术实现出发。
4.  **尽量避免简单封装，不要引入不可见的隐藏机制**：
    *   简单的封装仅会增加系统的多级依赖。对于不同的 Pod 集合需求，Kubernetes 使用完全不同的对象进行定义（例如用 StatefulSet 处理有状态，用 ReplicaSet 处理无状态），而非在同一个 ReplicaSet 内部使用隐藏算法来做硬区分。
5.  **API 操作复杂度与对象数量成正比 ($O(N)$)**：
    *   确保任何 API 检索与控制器计算的时间复杂度不超过 $O(N)$，以保证集群具备良好的水平伸缩性。
6.  **对象状态不依赖网络连接状态**：
    *   在分布式系统中，网络抖动是常态。API 对象的状态必须依靠主动重试与缓存进行最终一致性收敛，而不能在网络连接断开时发生错乱。
7.  **避免操作机制依赖全局状态**：
    *   依赖全局状态同步在大规模分布式集群中是极其昂贵的。

## 四、 核心结构设计原则

*   **唯一存储入口**：只有 `kube-apiserver` 可以直接读写 `etcd` 存储，其他所有集群内部/外部服务必须通过 API Server 进行状态变更，确保数据并发的一致性与安全管控。
*   **无状态控制面**：控制面组件（API Server、Scheduler、Controller Manager）本身是不持久化状态的，可以非常容易地通过多实例部署实现高可用。
*   **断网自愈能力**：当网络分区或组件重启恢复后，组件必须基于 [etcd](./08-etcd底层架构MVCC与高可用运维.md) 中的最新期望状态，继续执行未完成的逻辑，而不需要人工干预。
*   **事件监听机制 (Watch)**：所有组件都维护内存状态。组件优先使用 API Server 的 **HTTP 长连接事件监听 (Watch)** 机制来接收对象增删改的实时推送，避免使用开销极大的定期轮询 (Polling)。
