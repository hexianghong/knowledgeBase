# 💾 PersistentVolume、PVC 与 StorageClass 持久化存储架构

在 Kubernetes 中，由于容器的生命周期短暂，容器销毁重建后其内部可写层的数据会永久丢失。为了解决有状态应用的数据持久化以及跨节点共享问题，Kubernetes 引入了精妙的存储抽象模型：`Volume` (数据卷)、`PersistentVolume` (PV，持久化卷)、`PersistentVolumeClaim` (PVC，持久化卷声明) 和 `StorageClass` (存储类)。

---

## 一、 存储系统核心拓扑与关系

Kubernetes 存储架构采用了**“声明与实现相解耦”**的分层设计：

```text
┌──────────────────────────────────────┐
│                 Pod                  │
└──────────────────┬───────────────────┘
                   │ 引用卷声明 (PVC)
                   ▼
┌──────────────────────────────────────┐
│     PersistentVolumeClaim (PVC)      │ ──▶ 1. 开发人员的“资源声明”(大小、读写权限)
└──────────────────┬───────────────────┘
                   │ 自动 / 手动绑定 (Bind)
                   ▼
┌──────────────────────────────────────┐
│       PersistentVolume (PV)          │ ──▶ 2. 运维人员对“底层物理存储”的抽象资源
└──────────────────▲───────────────────┘
                   │ 动态预制创建 (Provision)
┌──────────────────┴───────────────────┐
│        StorageClass (SC模板)         │ ──▶ 3. 存储类：PV 的模板，定义底层存储插件与回收策略
└──────────────────────────────────────┘
```

### 💡 架构关键辨析：为什么要有 PVC 和 PV 两个概念？直接在 Pod 里写 PV 不行吗？

> **核心结论**：PV 是运维管的“物理硬资源”，PVC 是开发写的“资源意向单”，StorageClass 是“自动化中介工厂”。两层解耦实现了**云原生应用在不同云厂商之间的 100% 无缝移植**。

#### 1. 现实物理比喻：租客、房源与中介
* **PV (房东的物理房源)**：真实存在的底层物理磁盘（如 AWS 100GB EBS、Ceph 500GB RBD）。它包含了具体的物理设备 ID、存储服务器 IP、格式化文件系统等死板细节。
* **PVC (租客的租房意向单)**：开发工程师填写的需求声明（如“我要一个至少 20GB 容量、支持多节点读写的存储”）。**不包含任何底层存储技术细节！**
* **StorageClass (自动化中介模板)**：当租客提交 PVC 意向单且没有现成 PV 房子时，自动化中介立刻在云端**“现场盖出符合要求的 PV 房子”**。

#### 2. 3 大核心设计决策

1. **研发与运维职责彻底隔离**：
   业务开发人员不需要、也不应该知道私有云 [Ceph](./02-Ceph_RBD与CephFS在K8s的高性能挂载与IOPS调优.md) 存储服务器的 IP 地址或访问 Token。开发只管提交 PVC，存储安全的死板细节全部交由 SRE 运维在 PV/StorageClass 中配置。
2. **集群跨云环境 100% 可移植性 (Cloud Agnostic)**：
   如果 Pod 内硬编码了 `awsElasticBlockStore`，这份 YAML 搬到阿里云或私有云时将完全无法运行。换成 PVC 声明后，同一份 YAML 可以零修改直接部署在 AWS、阿里云、腾讯云或 Bare-metal 物理机上！
3. **动态按需供给 (Dynamic Provisioning)**：
   若没有 PVC/StorageClass 抽象，运维必须每天人工手写几百份 PV YAML 放在集群里备用；有了 PVC，存储根据业务申请**按需即时创建 (Just-In-Time)**，避免了大量的物理存储空间浪费。

## 二、 基础临时与本地存储卷

### 1. emptyDir (临时共享卷)
*   **物理机制**：当 Pod 分配到节点时创建，其初始内容为空。数据保存在**工作节点的内存或磁盘**中。
*   **生命周期**：与 Pod 绑定。当 Pod 被删除或重新调度时，emptyDir 中的数据会被**永久清除**。
*   **使用场景**：多容器共享临时缓存目录、大数据流式处理的中间临时分区等。

### 2. hostPath (本地宿主机卷)
*   **物理机制**：直接将宿主机节点上的某个特定目录或文件挂载进容器内部。
*   **优缺点**：
    *   **优点**：读写性能高，无需网络存储开销。
    *   **缺点**：**强耦合特定节点**。如果 Pod 重建被调度到 Node-B 上，将无法访问之前在 Node-A 上的 hostPath 数据。
*   **常用类型 (Type)**：
    *   `DirectoryOrCreate`：若宿主机目录不存在，自动创建（权限 0755）。
    *   `FileOrCreate`：若宿主机文件不存在，自动创建（权限 0644）。

## 三、 持久化卷 (PV) 与卷声明 (PVC) 核心概念

### 1. PV 的访问模式 (Access Modes)
不同底层物理存储设备支持的读写并发能力各不相同：
*   **`ReadWriteOnce (RWO)`**：读写单挂。该卷仅能以读写模式被**单个节点**挂载绑定。
*   **`ReadOnlyMany (ROX)`**：只读多挂。该卷可以以只读模式被**多个节点**共享挂载。
*   **`ReadWriteMany (RWX)`**：读写多挂。该卷可以以读写模式被**多个节点**共享挂载（常用于 NFS 或是 [Ceph](./02-Ceph_RBD与CephFS在K8s的高性能挂载与IOPS调优.md) FS 等网络文件系统）。

### 2. PV 的回收策略 (Reclaim Policy)
当用户删除了绑定的 PVC，对应的 PV 数据与物理存储如何处置：

> 💡 **核心结论**：在现行 K8S 版本中，标准的 PV 回收策略**实际上仅剩 2 种生产可用策略**（`Retain` 和 `Delete`）。旧版的 `Recycle` 已被彻底废弃！

| 回收策略 | 物理行为 | 安全性与适用场景 |
| :--- | :--- | :--- |
| **`Retain` (保留 - 静态卷默认)** | PVC 被删后，PV 变为 `Released` 状态。**底层物理数据与磁盘原封不动保留**，不自动删除，也不会被新 PVC 误绑定。 | 绝对安全！用于 MySQL/Oracle 等核心数据库，需要管理员人工核对数据后手动清理与重新分配。 |
| **`Delete` (删除 - 动态卷默认)** | PVC 被删后，绑定关联的 PV 以及**底层云物理存储（如 AWS EBS、阿里云 ESSD、Ceph RBD）会被底层 CSI 自动物理销毁抹除**。 | 自动化极高！适用于无状态辅助存储、日志临时卷或云原生按需动态创建的存储。 |
| ~~**`Recycle`**~~ *(已废弃 Deprecated)* | 旧版在宿主机执行 `rm -rf /volume/*` 清空数据，将 PV 重置为 `Available`。 | **已废弃！** 存在极高误删宿主机风险，现已被基于 StorageClass 的动态创建/删除机制完全替代。 |

## 四、 CSI 存储卷挂载的物理生命周期阶段

当一个 Pod 声明了 PVC 并成功调度到 Node-A 时，底层 CSI（Container Storage Interface）驱动会依次执行以下三个阶段将存储卷挂载进容器：

```text
  [ 阶段 ①: Attach ]           [ 阶段 ②: Mount ]          [ 阶段 ③: Bind Mount ]
  (云盘挂载到 Node-A 机器)    (将设备分区格式化挂载到宿主机目录)  (CRI 将目录挂载进容器文件系统)
  - 触发者: KCM 卷控制器      - 触发者: Kubelet VolumeMgr   - 触发者: Container Runtime
```

## 五、 NFS 存储静态挂载实战案例

### 1. 物理环境准备 (NFS 服务端安装)
在存储服务器上部署 NFS 服务端：
```bash
# 安装 NFS 包
yum -y install nfs-utils
# 创建共享物理目录并赋权
mkdir -p /nfs/data/nginx
chmod -R 777 /nfs/data
# 编辑导出配置
echo "/nfs/data *(rw,no_root_squash,sync)" >> /etc/exports
# 重启服务使之生效
systemctl restart rpcbind && systemctl restart nfs
```

---

### 2. 创建持久化卷 (PV)
声明物理存储路径，并定义回收策略为 `Retain`：

```yaml
# pv.yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: nfs-pv
  labels:
    pv: nfs-pv                            # 设置 Label 用于 PVC 精确过滤匹配
spec:
  capacity:
    storage: 100Mi                        # 声明该 PV 容量为 100Mi
  accessModes:
    - ReadWriteMany                       # 支持多节点读写共享 (NFS 专属)
  persistentVolumeReclaimPolicy: Retain   # 回收策略设为保留
  storageClassName: nfs-storage-class     # 定义存储类分类标识 (静态挂载下仅为纯字符串标记)
  nfs:
    server: 192.168.0.66                  # NFS 服务器 IP
    path: "/nfs/data/nginx"               # 共享物理目录
```

> 💡 **架构关键辨析：静态挂载 vs 动态挂载，`storageClassName` 到底需不需要部署真实的 StorageClass 资源对象？**
> 
> * **在“静态 PV 挂载”中（如本例）**：**【不需要】**部署真正的 StorageClass 对象！此时 `storageClassName: nfs-storage-class` 仅仅充当一个**纯字符串逻辑标签（Category Tag）**。只要 PV 和 PVC 中的字符串拼写一模一样，K8s 就会强行把它们匹配 Bind 在一起，即使集群里根本没有 `nfs-storage-class` 这个资源也完全没影响。
> * **在“动态 PV 供给 (Dynamic Provisioning)”中**：**【必须】**提前部署真实的 `StorageClass` YAML 资源及对应的 `Provisioner` 驱动 Pod！因为 PVC 会根据这个名称寻找真实的 StorageClass 对象，从而驱动后台的 Provisioner 自动创建物理目录与 PV。如果没部署，PVC 会报错 `storageclass.storage.k8s.io "nfs-storage-class" not found` 并永远卡在 `Pending`！
> * **如何完全禁用 StorageClass 匹配**：若想让 PVC 只匹配没有指定 StorageClass 的旧静态 PV，必须显式写成 `storageClassName: ""`（空字符串）。

---

### 3. 创建持久化卷声明 (PVC)
开发人员根据业务需求申请 50Mi 空间：

```yaml
# pvc.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: nfs-pvc
spec:
  accessModes:
    - ReadWriteMany                       # 访问模式必须与目标 PV 一致
  resources:
    requests:
      storage: 50Mi                       # 申请 50Mi 空间 (PV 的 100Mi 满足此要求)
  storageClassName: nfs-storage-class     # 存储类必须一致
  selector:
    matchLabels:
      pv: nfs-pv                          # 精确匹配 PV 的标签
```

*执行 `kubectl apply -f pvc.yaml` 后，PV 与 PVC 的状态会自动由 `Available` 变为 `Bound`。*

---

### 4. 部署应用容器挂载 PVC
```yaml
# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nfs-nginx
spec:
  replicas: 2
  selector:
    matchLabels:
      app: nfs-nginx
  template:
    metadata:
      labels:
        app: nfs-nginx
    spec:
      containers:
      - name: nginx-web
        image: nginx:1.25
        ports:
        - containerPort: 80
        volumeMounts:
        # 将名为 html-volume 的卷挂载进容器的网页根目录
        - mountPath: /usr/share/nginx/html
          name: html-volume
      volumes:
      # 声明 html-volume 数据卷引用自 nfs-pvc 卷声明
      - name: html-volume
        persistentVolumeClaim:
          claimName: nfs-pvc
```

## 六、 动态 HostPath 本地存储实战案例 (Rancher Local Path Provisioner)

原生 Kubernetes 支持静态 `hostPath`，但原生**不支持直接动态创建 hostPath 卷**。在单节点测试、边缘计算或高性能本地存储场景下，社区官方标准做法是使用 **Rancher `local-path-provisioner`**（或 CNCF sigs `hostpath-provisioner`）。

它可以监听 PVC，在 Pod 被调度到的目标宿主机物理路径上（如 `/opt/local-path-provisioner`），**自动动态创建专属子目录并自动注入 PV**！

---

### 1. 部署动态 HostPath 存储类 (StorageClass)

创建 `StorageClass` 并指定 Provisioner 驱动与**延迟绑定模式**：

```yaml
# local-path-storageclass.yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: local-path                      # 定义动态 StorageClass 名称
  annotations:
    storageclass.kubernetes.io/is-default-class: "false"
provisioner: rancher.io/local-path      # 指定驱动标识
volumeBindingMode: WaitForFirstConsumer # 核心：延迟绑定！等 Pod 调度节点确定后再建目录
reclaimPolicy: Delete                   # 删除 PVC 时自动清空宿主机对应目录
```

> 💡 **核心原理：为什么必须设置 `volumeBindingMode: WaitForFirstConsumer`？**
> 
> 如果设置为 `Immediate`（立即绑定），当用户创建 PVC 时，存储驱动可能会随机选择 Node-1 在其本地宿主机上创建目录并生成 PV；但随后 Pod 启动时，调度器可能因为 Node-1 资源不足将 Pod 调度到了 Node-2！这会导致 Pod 无法访问 Node-1 上的目录而**永远卡在 `ContainerCreating` 状态**！
> 设置 `WaitForFirstConsumer` 可以**强制让存储驱动等待 Pod 调度节点确定后，再去那个确定的物理 Node 上建目录生成 PV**。

---

### 2. 创建动态 PVC 声明 (无需手写 PV)

开发人员直接申领存储，无需手动部署任何 `pv.yaml`：

```yaml
# dynamic-hostpath-pvc.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: dynamic-hostpath-pvc
spec:
  accessModes:
    - ReadWriteOnce                     # 本地存储仅支持单节点读写
  storageClassName: local-path          # 指向上面创建的动态存储类
  resources:
    requests:
      storage: 2Gi                      # 动态申领 2Gi 容量
```

---

### 3. 部署 Pod 并验证宿主机物理目录自动生成

```yaml
# pod-dynamic-hostpath.yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-with-dynamic-hostpath
spec:
  containers:
  - name: app
    image: nginx:alpine
    volumeMounts:
    - name: data-volume
      mountPath: /usr/share/nginx/html  # 挂载进容器内部
  volumes:
  - name: data-volume
    persistentVolumeClaim:
      claimName: dynamic-hostpath-pvc   # 引用上面的动态 PVC
```

#### 验证步骤：
1. 执行 `kubectl apply -f .` 部署上述资源。
2. 查看系统自动生成的 PV：
   ```bash
   kubectl get pv,pvc
   ```
   *此时可以看到系统自动动态创建了一个名为 `pvc-xxxx-xxxx` 的 PV 并成功绑定！*
3. 登录 Pod 所在的目标宿主机，查看自动创建的物理路径：
   ```bash
   ls -la /opt/local-path-provisioner/pvc-xxxx-xxxx_default_dynamic-hostpath-pvc/
   ```
   *可以看到在宿主机本地目录下，存储驱动已成功自动建好了隔离的持久化存储分区！*
