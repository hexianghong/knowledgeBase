# 🎛️ DaemonSet、Job 与 CronJob 核心控制器

除了最常使用的 Deployment 和 StatefulSet，Kubernetes 还针对特定应用场景提供了另外三种核心工作负载控制器：**DaemonSet (守护进程集)**、**Job (单次任务)** 以及 **CronJob (定时任务)**。

---

## 一、 DaemonSet (守护进程集)

`DaemonSet` 确保在集群的**全部（或指定）工作节点**上都仅运行一个 Pod 副本。当有新节点加入集群时，该 Pod 会自动在新节点上启动；当节点被移除时，对应的 Pod 会被垃圾回收。

### 1. 典型应用场景
*   **网络插件**：如 `calico-node`、`flannel`。
*   **日志收集代理**：如 `fluentd`、`filebeat`、`logstash`。
*   **系统指标监控**：如 `prometheus-node-exporter`。

### 2. 调度机制的演进 (关键考点)
*   **早期设计**：由 DaemonSet Controller 直接绕过调度器，向 Pod 写入 `spec.nodeName` 绑定节点。
    *   *弊端*：无法应用 Kube-Scheduler 的高级调度特性（如 Pod 优先级、抢占机制、资源调度亲和性等）。
*   **现代设计 (v1.18+ 默认)**：所有的 DaemonSet Pod 均由 **Kube-Scheduler 统一调度**。
    *   *实现原理*：DaemonSet Controller 会在创建 Pod 时，自动为其注入对目标节点的 **NodeAffinity (硬亲和性)**，并且自动注入对系统核心污点（如节点不可达、磁盘压力等）的 **Tolerations (容忍度)**，从而保证它们能强行绑定在所有 Node 上跑起来，同时共享调度器的调度管道。

### 3. DaemonSet 生产 YAML 模板
```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-exporter
  namespace: monitoring
spec:
  selector:
    matchLabels:
      app: node-exporter
  template:
    metadata:
      labels:
        app: node-exporter
    spec:
      # 容忍控制面的污点，以便在 Master/Control-Plane 节点上同样运行监控 Agent
      tolerations:
      - key: node-role.kubernetes.io/master
        operator: Exists
        effect: NoSchedule
      - key: node-role.kubernetes.io/control-plane
        operator: Exists
        effect: NoSchedule
      containers:
      - name: node-exporter
        image: prom/node-exporter:v1.6.0
        ports:
        - containerPort: 9100
          hostPort: 9100                        # 绑定物理宿主机 9100 端口
```

## 二、 Job (一次性批处理任务)

`Job` 控制器负责管理**一次性任务**。它会启动一个或多个 Pod，并确保指定数量的 Pod 成功终止（退出状态码为 0）后，整个 Job 才宣告结束。

```text
Deployment ──▶ 【 期望状态：永远运行 】 ──▶ RestartPolicy: Always
Job        ──▶ 【 期望状态：运行成功并退出 】 ──▶ RestartPolicy: Never / OnFailure
```

### 1. 核心参数与控制策略
*   **`restartPolicy` 限制**：**只允许配置为 `Never` 或 `OnFailure`**。绝对不允许设为 `Always`，因为这与 Job “执行完毕即退出”的初衷相违背。
*   **`completions` (完成数)**：Job 结束需要累计成功运行的 Pod 个数。默认为 1。
*   **`parallelism` (并发数)**：Job 运行期间，最多同时有几个 Pod 在并发执行。默认为 1。
*   **`backoffLimit` (重试次数)**：Job 失败后的重试阈值，默认值为 `6`。若重试 6 次仍未成功，该 Job 状态置为 Failed，不再重试。

### 2. Job 生产 YAML 示例 (计算圆周率)
```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: pi-calculator
spec:
  completions: 3                          # 必须有 3 个 Pod 运行成功才算 Job 完成
  parallelism: 2                          # 最大允许 2 个 Pod 并发执行
  backoffLimit: 4                         # 失败重试上限 4 次
  template:
    spec:
      containers:
      - name: pi
        image: perl:5.34
        command: ["perl",  "-Mbignum=bpi", "-wle", "print bpi(1000)"]
      restartPolicy: Never                # 必须为 Never 或 OnFailure
```

## 三、 CronJob (定时任务)

`CronJob` 基于时间计划周期性地创建 `Job` 对象运行任务，类似于 Linux 系统中的 `crontab`。

### 1. 核心参数详解
*   **`schedule` (定时规则)**：支持标准 Linux crontab 格式，如 `*/5 * * * *` (每5分钟执行一次)。
*   **`concurrencyPolicy` (并发冲突策略)**：当上一次的 Job 还没运行完，下一次的运行时间又到了，该如何处理？
    *   `Allow` (默认)：允许并发运行，两个 Job 会同时重叠跑。
    *   `Forbid`：禁止并发。新的一轮会被直接跳过。
    *   `Replace`：取消当前正在运行的 Job，用新创建的 Job 进行替换。
*   **`suspend` (挂起)**：设为 `true` 可以暂停后续所有定时触发，对正在运行的 Job 无效。
*   **`successfulJobsHistoryLimit` / `failedJobsHistoryLimit`**：保留历史已完成/失败 Job 记录的数量上限（默认分别保留 3 个和 1 个），便于查看日志。

### 2. CronJob 生产 YAML 示例
```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: database-backup
  namespace: production
spec:
  schedule: "0 2 * * *"                   # 每天凌晨 2 点执行备份
  concurrencyPolicy: Forbid               # 如果上一天备份没跑完，禁止新备份并发跑
  successfulJobsHistoryLimit: 3           # 保留最后 3 次成功的历史记录
  failedJobsHistoryLimit: 1               # 保留最后 1 次失败的历史记录
  jobTemplate:                            # 定义要执行的 Job 模板
    spec:
      template:
        spec:
          containers:
          - name: backup-agent
            image: my-registry/db-backup:v1.2
            command: ["/bin/sh", "-c", "/usr/local/bin/backup.sh"]
          restartPolicy: OnFailure
```
