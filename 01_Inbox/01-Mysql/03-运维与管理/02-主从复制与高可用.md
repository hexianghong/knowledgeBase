## 1. 经典主从复制与 GTID 机制

主从复制是构建数据库读写分离、容灾高可用（HA）以及跨地域异地多活的物理基石。

### 1.1 GTID (Global Transaction Identifier) 物理机制

GTID 是对集群中每一个已提交事务在全球范围内的唯一身份标识：

$$\text{GTID} = \text{source\_uuid} : \text{transaction\_seq\_no}$$

```sql
-- 开启 GTID (my.cnf 生产推荐)
[mysqld]
gtid_mode = ON
enforce_gtid_consistency = ON

-- MySQL 8.0+ 现代化基于 GTID 自动定位构建复制 (Auto-positioning)
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST = '192.168.10.101',
  SOURCE_PORT = 3306,
  SOURCE_USER = 'repl_slave',
  SOURCE_PASSWORD = 'ReplPass#2026_Secure',
  SOURCE_AUTO_POSITION = 1;

START REPLICA;
```

#### GTID 三大生产核心价值：
1. **零人工位点计算**：彻底替代传统基于 `binlog.00000x` 文件名和物理 `Position` 偏移量的脆弱对齐方式。
2. **故障倒换零错位**：主库 Crash 时，高可用组件（Orchestrator）可直接比对从库的 `GTID_EXECUTED` 集合，毫秒级选出包含最新事务的从库进行无缝升主。
3. **空事务注入 (Empty Transaction Injection)**：快速修复从库由于主键冲突或非幂等操作导致的中断：
   ```sql
   -- 生产从库跳过报错 GTID 标准操作
   SET GTID_NEXT = '3E11FA47-71CA-11E1-9E33-C80AA9429562:105';
   BEGIN; COMMIT;
   SET GTID_NEXT = 'AUTOMATIC';
   START REPLICA;
   ```

## 2. MySQL 5.7 vs MySQL 8.0 复制与高可用全景对比矩阵

| 特性维度 | MySQL 5.7 | MySQL 8.0+ | 生产收益与演进价值 |
| :--- | :--- | :--- | :--- |
| **复制术语标准化** | 使用传统 `Master` / `Slave` 术语（如 `CHANGE MASTER TO`, `START SLAVE`） | **废弃旧术语，全面重构为 `Source` / `Replica`**（如 `CHANGE REPLICATION SOURCE TO`, `START REPLICA`） | 语义更现代且符合国际开源标准，8.4 LTS 彻底移除旧指令 |
| **MTS 默认依赖追踪** | 默认采用 `COMMIT_ORDER`（仅同一组提交的事务在从库并行） | **推荐并默认引入 `WRITESET` 依赖追踪** | 从库并行回放性能**提升 5~10 倍**，高写入压力下从库复制延迟几乎降为 0 |
| **新副本秒级开通** | 依赖外部工具（`mysqldump` 逻辑导入或 `XtraBackup` 物理拷贝后启动） | **引入内置 Clone Plugin (克隆插件)** | 支持在 SQL 层面执行 `CLONE INSTANCE FROM`，**分钟级/秒级物理克隆搭建全新从库** |
| **半同步复制 (Semi-Sync)** | 支持 AFTER_SYNC 与 AFTER_COMMIT（早期版本默认 AFTER_COMMIT 存在幽灵读幻象） | **默认且全面强化 AFTER_SYNC（无损半同步 Lossless Semi-Sync）** | 彻底消除主库崩溃后客户端先读到数据但从库未接收导致的数据回滚幻象 |
| **MGR 组复制能力** | 仅基础版 MGR，大事务网络易拥塞崩溃 | **支持单主/多主自动选举、流控机制 (Message Throttling)、自动故障节点剔除与版本兼容保护** | 具备真正的分布式金融级 Paxos 强一致多副本能力 |

## 3. 复制延迟根因与 MTS (多线程并行复制) 演进

从库复制延迟的物理本质是：**主库多连接并发写入，而早期从库仅靠单 SQL 线程串行重放**。

### 3.1 MTS 并行重放三代演进历程

```
从库多线程并行复制 (MTS) 演进
1. Schema 级别并行 (MySQL 5.6)
   - 按 Database 数据库库名分流到不同 Worker 线程。若系统为单库，退化为单线程串行。

2. Commit-Parent 组提交并行 (MySQL 5.7)
   - 依赖主库 Group Commit。同一批次完成 fsync 的事务必定没有行锁冲突，从库可并行重放。

3. Writeset 逻辑并行 (MySQL 8.0 核心标配)
   - 提取事务修改行记录的主键与唯一键计算 Hash (Writeset)。
   - 只要两条事务修改的行无 Hash 碰撞，即使在主库不同时间提交，在从库也全部并行回放！
```

```sql
-- MySQL 8.0+ 生产级无延迟 MTS 配置 (my.cnf)
[mysqld]
replica_parallel_type = LOGICAL_CLOCK
replica_parallel_workers = 16
binlog_transaction_dependency_tracking = WRITESET
binlog_transaction_dependency_history_size = 25000
```

## 4. 半同步复制与无损半同步 (Lossless Semi-Sync)

```
半同步复制模式对比 (After-Commit vs After-Sync)
1. 传统 After-Commit 模式 (可能产生幻读脏数据):
   InnoDB Commit ──► 写入 Binlog ──► 发送从库 ──► 等待 ACK (若此时主库宕机，其他会话已读到未同步的数据!)

2. 现代 After-Sync 模式 (无损半同步 - 8.0 标配):
   写入 Binlog ──► 发送从库 ──► 等待从库 ACK ──► InnoDB 最终 Commit (主库崩溃时，外部绝对读不到未同步数据!)
```

## 5. MGR (MySQL Group Replication) 组复制与 Paxos 共识

MGR 是基于 Paxos（Group Communication System, GCS）分布式共识协议的多副本状态机高可用方案。

```
MGR 事务冲突认证与 Paxos 提交流程
发起事务节点 (Primary)                           Secondary 节点 1              Secondary 节点 2
         │                                             │                             │
  1. 本地执行 (不 Commit)                               │                             │
  2. 提取 Writeset Hash                                │                             │
  3. 广播 Paxos 提案 ──────────────────────────────────►│                             │
         │ ◄────────────────── Paxos 多数派 Quorum 确认 ────┤                             │
  4. 全网事务确定物理全局序列                           │                             │
  5. 冲突认证 (Certification Pass)                     │                             │
  6. 本地真实 COMMIT                             7. 写入 Relay Log 并行重放    7. 写入 Relay Log 并行重放
```

## 6. 企业级 Orchestrator + ProxySQL 自动化高可用架构

```
生产级 Orchestrator + ProxySQL 自动容灾拓扑
                     +---------------------------+
                     | Orchestrator 探测中心     |
                     | (Raft 共识集群 + 拓扑自愈) |
                     +---------------------------+
                                   │ (触发故障倒换 Hook)
                                   ▼
+---------------+        +--------------------+        +--------------------+
| Client 应用侧  | ─────► | ProxySQL 流量网关  | ─────► | MySQL 主库 (Source)|
+---------------+        +--------------------+        +--------------------+
                                                        │
                                                        ▼ (GTID 复制)
                                                       +--------------------+
                                                       | MySQL 从库 (Replica|
                                                       +--------------------+
```

1. **Orchestrator**：2 秒内高频探活检测到 Source 宕机，通过拓扑分析避免网络脑裂，自动将 GTID 进度最全的 Replica 升为主库，并重置复制拓扑。
2. **ProxySQL**：应用层流量网关，动态接收 Orchestrator 的切换通知，无缝将 SQL 写流量切至新主库，应用连接无报错无感。

## 7. 现代分布式与云原生数据库对比矩阵 (架构选型)

| 架构维度 | 传统 MySQL MGR | TiDB (分布式 NewSQL) | PolarDB (云原生 DB) |
| :--- | :--- | :--- | :--- |
| **物理存储架构** | 单机独立存储，计算与存储紧密绑定 | **计算与存储彻底解耦** (TiDB Server + TiKV) | **共享分布式存储** (PolarStore 存算分离) |
| **高可用共识协议** | Paxos 组复制冲突认证 | **Multi-Raft 分布式共识** | 底层共享存储 RDMA 物理块复制 (< 1ms) |
| **水平扩容能力** | 扩展受单机磁盘限制 | **几乎无限水平弹性扩容** (自动 Region 分裂) | **只读计算节点秒级水平扩容** |
| **最佳生产场景** | 传统核心金融业务、中小型高并发 | **海量数据 HTAP、超高并发写入吞吐** | 高并发读多写少、需要弹性极速扩容场景 |
