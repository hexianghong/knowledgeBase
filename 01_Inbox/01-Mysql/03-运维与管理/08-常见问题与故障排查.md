# MySQL 生产常见故障根因分析、排障 SOP 与 5.7/8.0 避坑指南

## 1. MySQL 5.7 vs MySQL 8.0 常见故障与排障对比矩阵

| 故障排查场景 | MySQL 5.7 表现与诊断路径 | MySQL 8.0+ 表现与诊断路径 | 核心演进与避坑收益 |
| :--- | :--- | :--- | :--- |
| **实例重启自增 ID 突变** | 自增计数器仅保存在内存，重启执行 `MAX(id)+1` 重新赋值，**容易复用已删自增 ID** | **自增计数器变更实时记录在 Redo Log 中** | 彻底解决 5.7 实例重启导致自增 ID 复用的历史 Bug |
| **连接数打满 DBA 被拒** | 仅依赖 1 个预留 `SUPER` 连接名额，极易被监控会话占用 | **引入独立管理端口 `admin_port` (33062) 与独立线程池** | 保障连接打爆时 DBA 拥有 100% 连通的急救通道 |
| **事务锁与阻塞定位** | 查询 `information_schema.innodb_locks` / `innodb_lock_waits` | **查询 `performance_schema.data_locks` / `data_lock_waits`** | 8.0 移除旧表，新表开销极低且支持精细化锁模式（`REC_NOT_GAP`, `GAP`） |
| **复杂查询内存暴涨** | 内部临时表使用 `MEMORY` 引擎，溢出后转为 MyISAM/InnoDB 磁盘表 | **采用 `TempTable` 内存引擎**，支持 mmap 内存映射 | 内存分配更加紧凑，大幅减少多表关联时的内存碎片 |
| **MDL 锁源头线程定位** | 需开启复杂的 performance_schema 内部 instruments 埋点 | **默认原生支持 `performance_schema.metadata_locks` 视图关联** | 秒级定位持有元数据锁导致阻塞的源头长事务 `thread_id` |

## 2. 磁盘与物理存储经典故障

### 2.1 为什么表数据删掉一半，物理表文件 (`.ibd`) 大小却没变？

#### 1. 根因分析：空洞与页碎片
在 InnoDB 中，数据是以 16KB 数据页为单位存储在 `.ibd` 表空间中的：
* **`DELETE` 操作的实质**：InnoDB 并没有在物理磁盘上将记录抹去或收缩文件，而是将该记录在行头标记为“**已删除 (Deleted Flag)**”，并挂入可重用空闲链表（Garbage List）。
* **页空洞产生**：如果删除了一整页数据，整个数据页会被标记为可重用，但表空间物理文件尺寸不会回退。后续若没有相同范围的新数据插入，这些空间便成为永久性的**磁盘碎片与空洞（Holes）**。

#### 2. 解决方案：重建表收缩空间

```sql
-- 方案 1: 执行 OPTIMIZE TABLE (适合中小型表，业务低峰期执行)
OPTIMIZE TABLE `t_trade_order`;

-- 方案 2: 执行 Inplace 模式表重建
ALTER TABLE `t_trade_order` ENGINE=InnoDB, ALGORITHM=INPLACE, LOCK=NONE;

-- 方案 3: 超大表推荐使用 gh-ost 无锁在线收缩，避免阻塞 DML
```

#### 3. 查看表碎片与空洞占比 SQL
```sql
SELECT 
    TABLE_SCHEMA, 
    TABLE_NAME, 
    TABLE_ROWS,
    ROUND(DATA_LENGTH / 1024 / 1024, 2) AS data_mb,
    ROUND(INDEX_LENGTH / 1024 / 1024, 2) AS index_mb,
    ROUND(DATA_FREE / 1024 / 1024, 2) AS free_fragment_mb,
    ROUND(DATA_FREE / (DATA_LENGTH + INDEX_LENGTH + DATA_FREE) * 100, 2) AS fragment_pct
FROM information_schema.tables 
WHERE TABLE_SCHEMA = 'prod_trade_db' AND DATA_FREE > 100 * 1024 * 1024
ORDER BY DATA_FREE DESC;
```
*若 `fragment_pct`（碎片率）超过 30% 且空洞大小超过数十 GB，建议安排表空间重构。*

### 2.2 自增主键不连续与自增 ID 耗尽危机

#### 1. 自增主键不连续的根因
1. **唯一键冲突或事务回滚 (`ROLLBACK`)**：自增计数器在申请 ID 时先行递增。若后续因唯一索引冲突或报错回滚，为了极致性能，**自增 ID 绝不会回退**，形成永久断号。
2. **批量插入倍增申请**：执行 `INSERT INTO ... SELECT` 时，InnoDB 按 $1, 2, 4, 8 \dots$ 倍增申请 ID 批次，未用完的 ID 也会被丢弃。

#### 2. 自增 ID 用尽的后果与解决对策
* **`INT` 主键溢出风险**：
  `INT UNSIGNED` 上限为 42.9 亿（$4,294,967,295$）。一旦达到上限，后续所有 `INSERT` 均会持续报 `Duplicate entry '4294967295' for key 'PRIMARY'`，导致业务彻底无法写入！
  * **治理对策**：高并发核心业务表建表时**一律强制使用 `BIGINT UNSIGNED`**。
* **InnoDB 系统隐式 `row_id` 用尽灾难**：
  若建表时未指定主键且无唯一非空索引，InnoDB 会在后台分配 6 字节全局共享的 `row_id`（上限 $2^{48}-1$）。用尽后会循环从 0 覆盖分配，**导致新数据直接静默覆盖并抹除历史老数据！**
  * **治理对策**：生产环境建表必须显式声明主键。

## 3. 性能与慢查询突发故障排查

### 3.1 为什么原本执行极快的 SQL 突然变慢？

1. **InnoDB 正在集中刷脏页 (Flushing)**：
   - *根因*：当 Redo Log 空间即将用满（Checkpoint 延迟过大）或 Buffer Pool 脏页比例超标时，InnoDB 会被迫放缓 SQL 执行并触发同步刷盘，导致吞吐出现瞬时毛刺。
   - *调优*：MySQL 8.0.30+ 在线动态调大 `innodb_redo_log_capacity`，并调大 `innodb_io_capacity` 匹配物理 SSD 性能。
2. **长事务 Undo Log 版本链过长**：
   - *根因*：在 `Repeatable Read` 隔离级别下，若系统存在运行数小时的长事务，当前快照读为了构造历史一致性视图，必须沿着 **Undo Log 版本链** 逆向回溯上百万次，导致单行主键等值查询消耗数秒。
3. **MDL 元数据锁阻塞**：
   - *根因*：有并发长事务持有了表级 MDL 读锁，阻塞了后来的 DDL 操作，进而导致所有后续的新增 DML 读写全部被挂起排队。

```sql
-- 生产级快速定位持有 MDL 锁的源头线程
SELECT 
    l.object_type,
    l.object_schema,
    l.object_name,
    l.lock_type,
    l.lock_status,
    t.processlist_id,
    t.processlist_user,
    t.processlist_host,
    s.sql_text
FROM performance_schema.metadata_locks l
JOIN performance_schema.threads t ON l.owner_thread_id = t.thread_id
LEFT JOIN performance_schema.events_statements_current s ON t.thread_id = s.thread_id
WHERE l.object_name = 't_trade_order';

-- 找到源头 processlist_id 后立即执行: KILL <processlist_id>;
```

## 4. 连接与进程控制排障

### 4.1 为什么会有 KILL 不掉的语句？

执行 `KILL <thread_id>` 后，MySQL 只是在该线程打上一个异步中断标记，线程在运行到特定的“埋点检测点”才会退出：

1. **大事务回滚中 (Undo Rollback)**：若该事务已写入了数千万行数据，被 KILL 后，InnoDB 必须执行漫长的物理逆向 Undo 回滚以确保原子性。
2. **大临时表排序中**：正在进行数百 GB 的外部磁盘临时表 `filesort` 排序，清理临时文件前无法响应退出。
3. **高危警示**：**绝对严禁对正在回滚的 mysqld 执行 `kill -9`！** 强杀重启后，MySQL 启动时依然会进入 Crash Recovery 阶段重放回滚，期间数据库完全不可写，耗时甚至比原先更长。
