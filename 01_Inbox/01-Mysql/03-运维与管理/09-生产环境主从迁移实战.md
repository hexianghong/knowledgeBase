## 2. MySQL 5.7 升 8.0 跨版本迁移专项排雷 Checklist

在进行跨版本升级迁移前，必须执行以下 5 项专项合规检查，杜绝导入后业务抛出 SQL 异常：

| 排雷检查项 | 5.7 现状与风险 | 8.0+ 变更要求 | 预先整改方案 |
| :--- | :--- | :--- | :--- |
| **保留关键字冲突** | 包含 8.0 新增关键字（如 `GROUPS`, `RANK`, `SYSTEM`, `ADMIN`, `EMPTY`, `LEAD` 等） | 8.0 直接解析为语法错误 | 业务代码与表结构中为字段名强制添加反引号（\`） |
| **`utf8` 字符集废弃** | 历史表大量使用 `utf8` (`utf8mb3`) | 8.0 将其标记为废弃，默认升级为 `utf8mb4` | 迁移前全量评估并转换为 `utf8mb4` + `utf8mb4_0900_ai_ci` |
| **`sql_mode` 严格模式** | 5.7 宽松模式可能允许 `0000-00-00` 零日期 | 8.0 默认开启 `NO_ZERO_DATE` 与 `ONLY_FULL_GROUP_BY` | 清洗历史非法日期，修复不规范的非聚合 `GROUP BY` SQL |
| **废弃认证插件** | 账号使用 `mysql_native_password` | 8.0 默认使用 `caching_sha2_password` | 升级应用驱动，或在 8.0 配置 `default_authentication_plugin=mysql_native_password` 过渡 |
| **官方升级检查工具** | 手工肉眼排查易遗漏 | **使用 MySQL Shell `util.checkForServerUpgrade()` 工具** | 自动扫描源端全量表结构与存储例程，输出 100% 自动化阻断诊断报告 |

```bash
# 使用 MySQL Shell 自动执行升级合规检测
mysqlsh root@192.168.10.101:3306 -e "util.checkForServerUpgrade()" > /tmp/upgrade_check_report.txt
```

## 3. 目标新库极端性能调优（突破磁盘 I/O 导入瓶颈）

导入百 G 级数据会引发海量的数据页写入、B+Tree 索引树重构与 Redo Log 刷盘。未优化前机械盘导入耗时可能超过 12 小时。

```sql
-- 导入前执行临时提速优化 (降低持久化保证，释放最大写吞吐)
SET GLOBAL innodb_flush_log_at_trx_commit = 2;
SET GLOBAL sync_binlog = 0;
SET GLOBAL innodb_doublewrite = 0;           -- 临时关闭双写缓冲 (仅用于全新初始化导入)
SET GLOBAL foreign_key_checks = 0;           -- 忽略外键约束检查
SET GLOBAL unique_checks = 0;                -- 忽略二级唯一索引实时检查
```

```bash
# 后台多线程流式解压并导入
nohup zcat /data/backup/full_dump_prod.sql.gz | mysql -S /tmp/mysql_3306.sock -u root -p > /tmp/import.log 2>&1 &
```

> [!CAUTION] 导入完成后的安全善后
> 导入完成后，**必须立即恢复高安全配置**：
> `SET GLOBAL innodb_flush_log_at_trx_commit = 1; SET GLOBAL sync_binlog = 1; SET GLOBAL innodb_doublewrite = 1;` 并重启实例！

## 4. 基于 GTID 的自动化从库挂载与延迟追平

```sql
-- 1. 在目标 8.0 实例上配置同步源 (使用现代化 SOURCE 语法)
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST = '192.168.10.101',
  SOURCE_PORT = 3306,
  SOURCE_USER = 'repl_user',
  SOURCE_PASSWORD = 'ReplPassword#2026_Secure',
  SOURCE_AUTO_POSITION = 1;

-- 2. 启动从库复制线程
START REPLICA;

-- 3. 观察同步状态
SHOW REPLICA STATUS\G
-- 确认: Replica_IO_Running: Yes 且 Replica_SQL_Running: Yes
-- 持续观察 Seconds_Behind_Master 逐步降至 0。
```

## 5. 数据一致性比对与生产割接 (Cut-Over) SOP

### 5.1 数据一致性校验 (`pt-table-checksum`)

```bash
# 在主库运行 pt-table-checksum (自动通过主从复制比对行数据 Hash)
pt-table-checksum --nocheck-replication-filters --no-check-binlog-format \
  --replicate=sys_tools.checksums --databases=prod_trade_db \
  -h 192.168.10.101 -u dba_admin -p "Password"
```

### 5.2 生产割接五步标准流程

1. **业务停机/灰度切流窗口**：在夜间低峰期将应用网关置为只读维护状态，等待最后几笔在途请求落库。
2. **源端主库设为只读**：在源端主库执行 `FLUSH TABLES WITH READ LOCK; SET GLOBAL read_only = ON; SET GLOBAL super_read_only = ON;`。
3. **确认从库追平**：检查新从库 `SHOW REPLICA STATUS\G`，确认 `Seconds_Behind_Master = 0` 且复制位点完全一致。
4. **新库解除只读并升主**：在目标新库执行 `STOP REPLICA; RESET REPLICA ALL; SET GLOBAL read_only = OFF; SET GLOBAL super_read_only = OFF;`。
5. **切换应用连接配置**：通过 DNS 域名解析切换、ProxySQL 配置重载或 Kubernetes ConfigMap 滚动更新将应用连接切至新数据库主库，恢复业务读写。
