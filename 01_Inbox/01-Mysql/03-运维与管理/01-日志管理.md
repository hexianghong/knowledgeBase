## 1. WAL 预写日志与 ARIES 崩溃恢复算法

关系型数据库保障数据物理持久性（Durability）与高吞吐并发的核心准则是 **WAL (Write-Ahead Logging)**：**物理日志写入磁盘优先于数据脏页刷盘**。

```
WAL 架构与 ARIES 崩溃恢复流转
客户端 DML 提交
       │
       ▼
写入 Redo Log Buffer 内存页 ───────────────────► 顺序落盘 Redo Log 文件 (快速顺序 I/O)
       │                                               │
       ▼                                               ▼
修改 Buffer Pool 内存页 (变脏页)                    崩溃重启 (Crash Recovery)
       │                                               │
       ▼ (后台异步 Async Checkpoint 刷盘)               ▼
写入 .ibd 物理磁盘数据页 (离散随机 I/O) <────── ARIES 前滚 (Redo) 与回滚 (Undo)
```

### 1.1 ARIES 崩溃恢复算法三大阶段

1. **分析阶段 (Analysis Phase)**：从上一个物理 **Checkpoint** 扫描 Redo Log，重建崩溃瞬间的**活跃事务表 (Transaction Table)** 和 **脏页表 (Dirty Page Table)**。
2. **Redo 前滚阶段 (Redo Phase)**：按 LSN 递增重做所有的物理变更。通过比较数据页的 `page_lsn` 与日志 `log_lsn` 保证前滚的**幂等性**（`page_lsn >= log_lsn` 则直接跳过）。
3. **Undo 回滚阶段 (Undo Phase)**：对崩溃前未提交的事务执行物理逆向撤销，并生成**补偿日志 (CLR, Compensation Log Record)**，确保回滚动作自身也是 Crash-Safe 的。

## 2. MySQL 5.7 vs MySQL 8.0 日志体系全景对比矩阵

| 特性维度 | MySQL 5.7 | MySQL 8.0+ | 生产收益与内核演进 |
| :--- | :--- | :--- | :--- |
| **Redo Log 容量管理** | 静态配置 `innodb_log_file_size` 和 `innodb_log_files_in_group`，修改必须停机 | **8.0.30+ 引入 `innodb_redo_log_capacity` 在线动态调整** | 实现生产环境 Redo Log **毫秒级在线扩容/缩容**，无需重启实例 |
| **Binlog 事务依赖追踪** | 默认采用 `COMMIT_ORDER`（仅同一组提交批次的事务可在从库并行） | **默认推荐 `WRITESET`**（基于修改行 Hash 并行） | 从库多线程复制（MTS）并行度**提升数倍至数十倍**，彻底根除复制延迟 |
| **Binlog 过期清理机制** | `expire_logs_days`（最小粒度仅支持整数“天”，无法按小时精细控制） | **`binlog_expire_logs_seconds`**（精确到“秒”） | 云原生与高并发生产环境下能够按小时精确回收磁盘空间，防止磁盘打满 |
| **Undo 表空间管理** | 默认集成于 `ibdata1` 系统表空间，无法在线收缩 | **默认启用独立 Undo 表空间，支持自动在线收缩 (Auto Truncate)** | 避免历史长事务导致 Undo 表空间永久膨胀，大幅节约磁盘资源 |
| **错误日志结构化** | 仅支持传统单文本格式输出 | **引入 Error Log Components 组件架构**，支持输出 **JSON 格式** | 方便云原生 ELK / Fluentd / Loki 等日志系统进行结构化日志采集与分析 |

## 3. 三大核心日志体系深度对比

```
MySQL 三大核心日志体系
├── Redo Log  ──► InnoDB 引擎层物理日志 (保障 Crash-Safe 崩溃恢复)
├── Undo Log  ──► InnoDB 引擎层逻辑日志 (保障 事务回滚 + MVCC 历史版本快照)
└── Binlog    ──► Server 层逻辑日志 (保障 主从复制 + 点对点数据恢复 PITR)
```

| 维度对比 | Redo Log (重做日志) | Undo Log (回滚日志) | Binlog (二进制日志) |
| :--- | :--- | :--- | :--- |
| **归属层级** | **InnoDB 引擎层** | **InnoDB 引擎层** | **Server 层** (所有存储引擎通用) |
| **日志物理格式**| 物理日志 (记录数据页字节级物理修改) | 逻辑逆向日志 (记录反向 SQL 指令) | 逻辑日志 (Statement / Row / Mixed 格式) |
| **文件存储模式**| 循环覆盖写 (8.0 支持动态容量) | 独立 Undo 表空间，支持动态 Truncate | 追加顺序写 (写满自动切换新文件 `binlog.00000n`) |
| **核心职责** | **Crash-Safe 崩溃恢复** | **事务原子性回滚 + MVCC 快照读** | **主从复制 + 任意时间点精准恢复 (PITR)** |

## 4. 两阶段提交 (Two-Phase Commit, 2PC) 原理与崩溃边界

因为 Redo Log（InnoDB 层）与 Binlog（Server 层）属于两个独立模块，在事务提交时必须保证两者的**物理写入原子一致**。若中途崩溃，可能导致主库与从库数据不一致。MySQL 采用 **内部 2PC 协议**：

```
内部两阶段提交 (2PC) 流水线
                    事务提交 (COMMIT)
                           │
                           ▼
        +-------------------------------------+
        |  阶段 1: Prepare 阶段                |
        |  - InnoDB 将 TRX 状态设为 PREPARE    |
        |  - 物理刷写 Redo Log 到磁盘 (fsync)  |
        +-------------------------------------+
                           │
                           ▼
        +-------------------------------------+
        |  阶段 2: Commit 阶段                 |
        |  - Server 层将 Binlog 刷写磁盘(fsync)|
        |  - InnoDB 将 TRX 状态设为 COMMIT     |
        |  - 在 Redo Log 写入 Commit 标记      |
        +-------------------------------------+
```

### 4.1 崩溃恢复判定规则 (2PC Boundary Checks)

如果在 2PC 过程中服务器发生**掉电崩溃**，重启后恢复引擎根据 **XID (分布式事务全局唯一 ID)** 进行仲裁：

```
崩溃恢复决断逻辑
┌────────────────────────────────────────────────────────┐
│ 崩溃点 1: Redo Log 处于 Prepare 状态，但 Binlog 中无 XID│
│ ──► 决断: 执行 ROLLBACK (回滚事务，主从均无该数据，一致) │
└────────────────────────────────────────────────────────┘
                            │
┌────────────────────────────────────────────────────────┐
│ 崩溃点 2: Redo Log 处于 Prepare 状态，且 Binlog 包含完整 XID│
│ ──► 决断: 执行 COMMIT (提交事务，从库已接收 Binlog，主库前滚)│
└────────────────────────────────────────────────────────┘
```

## 5. 二进制日志组提交 (BLGC) 内核

单线程每次事务提交都调用 `fsync()` 刷盘会导致磁盘 IOPS 迅速达到物理瓶颈。组提交（Binary Log Group Commit, BLGC）将多个并发事务的刷盘合并为一次物理 I/O：

```
BLGC 组提交三阶段流水线
   +-------------------+      +-------------------+      +-------------------+
   |   Flush Stage     | ───► |    Sync Stage     | ───► |   Commit Stage    |
   |  写 Binlog 内存   |      |  调用 fsync 刷盘  |      |  按顺序提交事务   |
   +-------------------+      +-------------------+      +-------------------+
             ▲                          ▲                          ▲
             │ (Leader 收集队列)         │ (批处理一次物理 fsync)    │ (按序释放锁)
     Tx1, Tx2, Tx3              Tx1, Tx2, Tx3              Tx1, Tx2, Tx3
```

* **Leader / Follower 模型**：进入 Flush 阶段的首个事务线程自动成为 Leader，锁住队列并代为收集 Follower 线程的日志批次，由 Leader 单次触发 `fsync()` 批量刷盘，大幅消除 I/O 争用。

## 6. Binlog 格式选型与生产解析实战

### 6.1 Binlog 三大格式对比

| 格式模式 | 记录内容 | 优缺点与生产建议 |
| :--- | :--- | :--- |
| **`STATEMENT`** | 记录执行的原始 SQL 文本 | 日志量小；但在并发或包含非确定性函数（如 `UUID()`, `NOW()`, `LIMIT`）时**极易导致主从数据不一致**。 |
| **`ROW` (生产强制)** | 记录每行记录被修改前后的完整物理字段值 | **主从一致性 100% 可靠**，支持 Flashback 闪回；日志量略大，但配合现代 NVMe SSD 完全无感。 |
| **`MIXED`** | 混合模式（默认 Statement，遇非确定性函数自动切 Row） | 难以精细控制，生产不推荐。 |

### 6.2 生产级 Row 格式 Binlog 解码排查指令

```bash
# 生产深度解析 Binlog 内容 (将 base64 行事件反编译为可读伪 SQL)
mysqlbinlog --no-defaults -vv --base64-output=DECODE-ROWS \
  --start-datetime="2026-08-25 09:00:00" \
  --stop-datetime="2026-08-25 10:00:00" \
  --database=prod_trade_db \
  /var/lib/mysql/binlog.000128 > /tmp/binlog_decoded.sql
```
