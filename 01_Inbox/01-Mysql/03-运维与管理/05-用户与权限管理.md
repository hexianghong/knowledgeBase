# MySQL 生产级用户认证、动态权限体系、安全审计与 5.7/8.0 全景演进指南

## 1. MySQL 权限系统内核模型与底层架构演进

MySQL 的权限与访问控制系统（Access Control System）是保障数据库机密性、完整性与可用性的第一道防线。理解权限系统在 Server 层的鉴权状态机、内存缓存结构以及元数据持久化方式，是设计高安全生产架构的前提。

### 1.1 权限层级与校验机制

MySQL 的权限模型采用**分层继承与短路校验**机制。权限自顶向下划分为 6 个层级：

```
MySQL 权限层级体系 (自顶向下逐级匹配)
┌────────────────────────────────────────────────────────┐
│ 1. 全局层级 (Global Level)     --> *.*                 │
│    存储于 mysql.user / Dynamic Privileges              │
└───────────────────────────┬────────────────────────────┘
                            │ (若未命中或需细化)
                            ▼
┌────────────────────────────────────────────────────────┐
│ 2. 数据库层级 (Database Level)  --> db_name.*          │
│    存储于 mysql.db                                     │
└───────────────────────────┬────────────────────────────┘
                            │
                            ▼
┌────────────────────────────────────────────────────────┐
│ 3. 表层级 (Table Level)        --> db_name.table_name  │
│    存储于 mysql.tables_priv                            │
└───────────────────────────┬────────────────────────────┘
                            │
                            ▼
┌────────────────────────────────────────────────────────┐
│ 4. 列层级 (Column Level)       --> (col1, col2)        │
│    存储于 mysql.columns_priv                           │
└───────────────────────────┬────────────────────────────┘
                            │
                            ▼
┌────────────────────────────────────────────────────────┐
│ 5. 例程/子程序层级 (Routine)   --> PROCEDURE / FUNCTION│
│    存储于 mysql.procs_priv                             │
└────────────────────────────────────────────────────────┘
```

#### 鉴权两阶段状态机

1. **连接握手阶段（Connection Verification）**：
   - 客户端建立 TCP 连接，MySQL 校验客户端 IP/Host、用户名以及密码凭证（或外部插件认证）。
   - 若认证成功，进入请求阶段；若失败，返回 `ER_ACCESS_DENIED_ERROR` (1045) 并立即终止连接。
2. **请求鉴权阶段（Request Verification）**：
   - 客户端发送具体的 SQL 指令，Server 层的解析器（Parser）和优化器（Optimizer）解析出操作类型及涉及的目标对象（库、表、列、视图、存储过程）。
   - **短路优先校验**：优先检查当前用户是否具有 Global 级权限。若已具备（例如 `*.*` 上的 `SELECT`），则直接放行，不再扫描低层级权限；若未满足，依次逐级向下检索 Database -> Table -> Column 层级。若到达最底层仍无对应权限，拒绝执行并抛出 `ER_TABLEACCESS_DENIED_ERROR` (1142) 或 `ER_DBACCESS_DENIED_ERROR` (1044)。

```
客户端请求鉴权流程
SQL Request
   │
   ▼
检查 Global 权限 (mysql.user) ──────────[满足]───► 允许执行
   │ [不满足]
   ▼
检查 DB 权限 (mysql.db) ─────────────────[满足]───► 允许执行
   │ [不满足]
   ▼
检查 Table 权限 (mysql.tables_priv) ─────[满足]───► 允许执行
   │ [不满足]
   ▼
检查 Column 权限 (mysql.columns_priv) ───[满足]───► 允许执行
   │ [不满足]
   ▼
抛出异常: Access Denied (Error 1044/1142)
```

### 1.2 Host 匹配规则与精确度排序机制

MySQL 用户账号由两部分构成：`'user_name'@'host_name'`。当客户端发起连接时，MySQL 会扫描权限缓存并按照**精确度从高到低**进行排序匹配：

```
Host 排序匹配优先级：
最精确 (Literal IP / Hostname) > 网段掩码 (CIDR / Subnet Mask) > 通配符 (%)
```

* **排序算法原则**：
  1. `Host` 列越具体，排序越靠前。具体 IP（如 `192.168.1.100`）优先于掩码网段（如 `192.168.1.%` 或 `192.168.1.0/255.255.255.0`），掩码优先于通用通配符（`%`）。
  2. 当 `Host` 精确度相同时，`User` 列非空的优先于空字符串（匿名用户）。
  3. **生产陷阱**：若同时存在 `'app'@'192.168.1.%'` 和 `'app'@'%'`，来自 `192.168.1.50` 的客户端连接将**命中前者**。若开发者修改了 `'app'@'%'` 的密码或权限，可能发现该客户端依旧使用旧凭证或旧权限，根因即为此处的最长前缀与精确度截胡。

### 1.3 权限元数据存储架构演进 (5.7 vs 8.0)

| 核心对比维度 | MySQL 5.7 及早期版本 | MySQL 8.0+ |
| :--- | :--- | :--- |
| **底层存储引擎** | **MyISAM 存储引擎** (`mysql.user`, `mysql.db`, `mysql.tables_priv` 等) | **InnoDB 事务型存储引擎** (集成于统一 Data Dictionary 数据字典) |
| **元数据 DDL 原子性** | **非事务性**：若批量授权中途崩溃，可能残留部分成功元数据，引发权限不一致 | **完全事务性与原子性 (Atomic DDL)**：支持 Crash-Safe 回滚与原子提交 |
| **直接 DML 修改系统表** | 允许（如 `UPDATE mysql.user SET ...`，但属极度不规范操作） | **严格受限/禁止直接 DML**：直接修改系统字典表会报错，强制统一使用 DCL 语法 |
| **动态扩展机制** | 静态硬编码于 Server 层内核，新增组件无法注册自定义权限 | **原生支持 Dynamic Privileges**，插件与组件可动态注册与注销权限 |

### 1.4 `FLUSH PRIVILEGES` 深度剖析：何时用？何时禁？

* **内存 ACL 缓存机制**：
  MySQL 启动时会将磁盘权限表全量加载至内存中的 ACL 结构（包括 `acl_users` 数组、`acl_dbs` 数组、Hash 表等），以实现高并发查询下的纳秒级无锁/读写锁快速鉴权。
* **执行 DCL 语句时的行为**：
  在执行标准 DCL 语句（如 `CREATE USER`、`GRANT`、`REVOKE`、`ALTER USER`、`DROP USER`）时，Server 层会**同时修改磁盘元数据并实时同步更新内存 ACL 缓存**。
* **什么时候不需要 `FLUSH PRIVILEGES`**：
  * **日常所有的标准 DCL 变更后，绝对不需要执行 `FLUSH PRIVILEGES`！**
* **什么时候必须使用 `FLUSH PRIVILEGES`**：
  1. 非法/非标准方式通过底层 DML 直接修改了 `mysql` 库权限表（如 `UPDATE mysql.user ...`）。
  2. 在 `--skip-grant-tables` 模式下启动实例，执行密码重置前，必须先执行 `FLUSH PRIVILEGES` 加载内存结构，才能使用 `ALTER USER` 语法。
* **生产滥用隐患**：
  在高并发生产环境中，执行 `FLUSH PRIVILEGES` 会向内存 ACL 结构加**全局写锁（Read/Write Lock）**，导致瞬时所有新建连接与鉴权请求发生线程排队与锁等待，极易诱发连接池雪崩。

## 2. MySQL 5.7 vs MySQL 8.0 权限与用户体系全景对比矩阵

### 2.1 核心特性全景对比表

| 维度对比 | MySQL 5.7 | MySQL 8.0+ | 生产影响与演进收益 |
| :--- | :--- | :--- | :--- |
| **创建与授权语法** | 支持 `GRANT ... IDENTIFIED BY 'pwd'` 隐式创建用户 | **彻底废除**隐式创建，必须先 `CREATE USER` 再 `GRANT` | 杜绝由于授权拼写错误意外创建无意图用户的安全隐患 |
| **超级管理员权限** | `SUPER` 权限一权独大（涵盖修改变量、主从控制、Kill 等） | `SUPER` 被标记废弃，拆解为 **30+ 项细粒度 Dynamic Privileges** | 实现精细化权限解耦，践行安全最小权限原则 |
| **角色管理 (RBAC)** | 原生不支持角色概念（需依赖外部中间件或应用层封装） | **原生完整支持 RBAC 角色体系** (`CREATE/GRANT/SET ROLE`) | 极大简化企业级多团队、多环境数百个账号的批量权限运维 |
| **默认认证插件** | `mysql_native_password` (基于 SHA-1 双重哈希) | **`caching_sha2_password`** (基于 SHA-256 + 内存快速缓存 + RSA) | 安全性提升至金融级，阻断彩虹表与中间人嗅探攻击 |
| **密码平滑轮换** | 单一密码机制，改密必须业务同步重启或短暂不可用 | **双密码机制 (Dual Passwords)**，支持 `RETAIN CURRENT PASSWORD` | 实现微服务/K8s 集群多 Pod 滚动更新下的**零停机改密** |
| **密码复杂度控制** | `validate_password` 插件（动态库 Plugin 形式） | `component_validate_password`（Server Component 架构） | 组件化架构解耦，动态装卸载且更稳定 |
| **登录失败锁定** | 社区版原生不支持失败重试锁定（需第三方插件） | **原生支持连续失败自动锁定** (`FAILED_LOGIN_ATTEMPTS`) | 原生防御暴力破解与字典碰撞攻击 |
| **密码历史防复用** | 不支持历史密码校验 | **支持密码历史与间隔校验** (`PASSWORD_HISTORY`) | 满足等保三级/SOC2/PCI-DSS 合规要求 |
| **参数持久化管理** | 仅支持 `SET GLOBAL`（重启丢失，需手工改 my.cnf） | 支持 `SET PERSIST` / `SET PERSIST_ONLY`，需专用权限控制 | 配合 `PERSIST_ROLES_ADMIN` 权限保障云原生动态调优安全 |
| **管理连接专用通道** | 仅依靠预留 1 个 `SUPER` 连接 (`max_connections + 1`) | **支持独立管理端口 `admin_port`** 与独立线程池 | 防止高并发连接爆满时 DBA 无法登录进行紧急排障 |
| **权限系统表存储引擎** | MyISAM 引擎，非事务性 | InnoDB 引擎，原子性 DDL，不可直接 DML | 消除主从复制权限同步中途异常造成的元数据脏状态 |
| **用户级别资源组** | 不支持 CPU 资源绑定 | 支持 **Resource Groups (资源组)**，可绑定 VCPU 核心 | 防止特定报表/后台批量账号抢占主业务 CPU 资源 |

### 2.2 授权语法变更与安全规范

#### MySQL 5.7 遗留语法（生产已淘汰）
在 MySQL 5.7 中，允许使用一条语句同时完成用户创建、密码设置与权限赋予：
```sql
-- 5.7 语法：若用户不存在则自动创建，若存在则修改密码并赋予权限
GRANT SELECT, INSERT ON app_db.* TO 'app_user'@'192.168.1.%' IDENTIFIED BY 'Old_Pass#2018';
```
> [!WARNING] 隐患说明
> 若 DBA 在执行上述命令时将用户名误输入为 `'app_usr'`，MySQL 将静默创建一个全新的高权账号，且不会给出任何阻断警告，带来极大的安全漏洞。

#### MySQL 8.0+ 强制标准语法（创建与授权显式分离）
MySQL 8.0 彻底废除了 `GRANT ... IDENTIFIED BY` 语法（执行直接报错 `ERROR 1064 (42000): You have an error in your SQL syntax`），必须分步显式执行：

```sql
-- 步骤 1: 显式创建用户并设置安全认证方式及密码
CREATE USER 'app_user'@'192.168.1.%' 
  IDENTIFIED WITH caching_sha2_password BY 'Strong_Pass#2026'
  PASSWORD EXPIRE INTERVAL 90 DAY
  FAILED_LOGIN_ATTEMPTS 5 PASSWORD_LOCK_TIME 1;

-- 步骤 2: 精准赋予所需最小业务权限
GRANT SELECT, INSERT, UPDATE, DELETE ON app_db.* TO 'app_user'@'192.168.1.%';
```

### 2.3 权限拆解：SUPER 权限废除与 8.0 动态权限体系

在 MySQL 5.7 中，`SUPER` 权限覆盖范围极其宽泛（包括 `SET GLOBAL`、`KILL` 连接、`CHANGE MASTER TO`、主从启停、Purge Binlog、跳过锁检查等）。给运维或监控人员赋予 `SUPER` 等同于交出数据库最高控制权。

MySQL 8.0 将 `SUPER` 权限全面解耦为 **细粒度动态权限 (Dynamic Privileges)**：

```
MySQL 8.0+ 动态权限分类模型
├── 运维控制类 ────► CONNECTION_ADMIN, SYSTEM_VARIABLES_ADMIN, PERSIST_ROLES_ADMIN
├── 主从复制类 ────► REPLICATION_SLAVE_ADMIN, REPLICATION_APPLIER, GROUP_REPLICATION_ADMIN
├── 备份恢复类 ────► BACKUP_ADMIN, CLONE_ADMIN, RELOAD
├── 观测监控类 ────► PROCESS, SHOW_ROUTINE, TELEMETRY_USER
└── 审计安全类 ────► AUDIT_ADMIN, ENCRYPTION_KEY_ADMIN, SENSITIVE_VARIABLES_OBSERVER
```

#### 核心动态权限场景替代对照表

| 生产运维场景 | MySQL 5.7 粗暴授权 | MySQL 8.0+ 最小动态权限推荐 | 安全风险收益 |
| :--- | :--- | :--- | :--- |
| **在线修改全局变量** | `GRANT SUPER ON *.*` | `GRANT SYSTEM_VARIABLES_ADMIN ON *.*` | 允许执行 `SET GLOBAL`，但无权杀线程或重置主从 |
| **持久化参数配置** | `GRANT SUPER ON *.*` | `GRANT PERSIST_ROLES_ADMIN, SYSTEM_VARIABLES_ADMIN ON *.*` | 允许执行 `SET PERSIST`，受控持久化配置 |
| **运维人员杀掉慢查询** | `GRANT SUPER ON *.*` | `GRANT CONNECTION_ADMIN, PROCESS ON *.*` | 仅能通过 `KILL` 终止异常线程，无权修改全局配置 |
| **Prometheus 监控采集** | `GRANT SUPER ON *.*` | `GRANT PROCESS, REPLICATION CLIENT ON *.*` | 仅能查看线程状态与从库延迟，杜绝越权 |
| **XtraBackup 物理备份** | `GRANT ALL PRIVILEGES ON *.*` | `GRANT BACKUP_ADMIN, RELOAD, PROCESS, LOCK TABLES ON *.*` | 仅授予物理表空间锁与备份接口权限，无 DML 删库权限 |
| **MHA / Orchestrator 高可用** | `GRANT SUPER ON *.*` | `GRANT REPLICATION_SLAVE_ADMIN, CONNECTION_ADMIN ON *.*` | 限制在拓扑切换与主从配置范围内 |

### 2.4 角色体系 (RBAC) 演进与自动化配置

MySQL 8.0 引入了工业标准的 **基于角色的访问控制 (Role-Based Access Control, RBAC)**，角色在底层实质上是一个不含密码、不可登录但拥有权限集合的特殊 User 实体。

```
RBAC 权限分发拓扑
┌───────────────────────────┐       ┌───────────────────────────┐
│  Role: r_prod_readonly    │       │  Role: r_prod_readwrite   │
│  - SELECT ON app_db.*     │       │  - SELECT, INSERT, UPDATE │
│                           │       │    ON app_db.*            │
└─────────────┬─────────────┘       └─────────────┬─────────────┘
              │ 赋予                               │ 赋予
              ▼                                    ▼
┌───────────────────────────┐       ┌───────────────────────────┐
│ User: dev_read_zhangsan   │       │ User: svc_order_app       │
└───────────────────────────┘       └───────────────────────────┘
```

#### 角色全生命周期实战

```sql
-- 1. 创建角色集合
CREATE ROLE 'r_developer_ro', 'r_developer_rw', 'r_dba_ops';

-- 2. 为角色赋予业务权限与系统管理权限
GRANT SELECT ON app_db.* TO 'r_developer_ro';
GRANT SELECT, INSERT, UPDATE, DELETE ON app_db.* TO 'r_developer_rw';
GRANT CONNECTION_ADMIN, PROCESS, SYSTEM_VARIABLES_ADMIN ON *.* TO 'r_dba_ops';

-- 3. 将角色赋予具体员工账号
CREATE USER 'dev_zhangsan'@'192.168.1.%' IDENTIFIED BY 'ZhangSan#Pass2026';
GRANT 'r_developer_ro' TO 'dev_zhangsan'@'192.168.1.%';

-- 4. 关键：激活角色 (默认情况下用户登录后角色处于 INACTIVE 状态)
-- 方案 A: 单用户设置默认全量激活
SET DEFAULT ROLE ALL TO 'dev_zhangsan'@'192.168.1.%';

-- 方案 B: 全局参数配置（推荐生产环境启用，所有用户登录自动激活拥有角色）
-- 在 my.cnf 中配置: activate_all_roles_on_login = ON
SET PERSIST activate_all_roles_on_login = ON;
```

#### 企业级强制角色（`mandatory_roles`）
对于全公司必须统一注入的安全监控、审计或限制类角色，可通过 `mandatory_roles` 实现系统级强制绑定，即使 DBA 漏配授权，用户登录时也会被强制应用：

```sql
-- 在 my.cnf 中配置强制角色 (用户无法被 REVOKE 剥离该角色)
-- mandatory_roles = 'r_security_audit,r_default_limiter'
SET PERSIST mandatory_roles = 'r_security_audit';
```

### 2.5 密码验证组件架构 (Plugin vs Component)

#### MySQL 5.7（Plugin 插件体系）
```sql
-- 5.7 安装与配置
INSTALL PLUGIN validate_password SONAME 'validate_password.so';

-- 查看与设置参数
SET GLOBAL validate_password_policy = 'MEDIUM';
SET GLOBAL validate_password_length = 12;
```

#### MySQL 8.0+（Component 统一组件架构）
MySQL 8.0 重构了底层扩展机制，全面采用 Component 架构取代传统 Plugin：

```sql
-- 8.0 安装密码复杂度组件
INSTALL COMPONENT 'file://component_validate_password';

-- 8.0 对应参数名称变更对照 (新增 component_ 前缀)
SET PERSIST validate_password.policy = 'MEDIUM';          -- 策略: 0(LOW), 1(MEDIUM), 2(STRONG)
SET PERSIST validate_password.length = 12;                -- 最小长度
SET PERSIST validate_password.mixed_case_count = 1;       -- 至少包含大小写字母数
SET PERSIST validate_password.number_count = 1;           -- 至少包含数字数
SET PERSIST validate_password.special_char_count = 1;     -- 至少包含特殊字符数
SET PERSIST validate_password.check_user_name = ON;       -- 禁止密码包含用户名
```

### 2.6 认证插件升级与加密机制

#### 加密算法与安全性对比
* **MySQL 5.7 (`mysql_native_password`)**：
  采用 `SHA1(SHA1(password))` 双重哈希算法。密码在网络传输过程中通过挑战-应答（Challenge-Response）机制防止明文暴露，但由于底层为 SHA-1，无法抵御现代 GPU 集群的高性能彩虹表碰撞攻击，且已被国际安全标准（NIST/PCI-DSS）判定为不合规。
* **MySQL 8.0 (`caching_sha2_password`)**：
  采用 **SHA-256** 散列算法，并引入 **20 轮加盐迭代（Salted Multi-Round Hashing）**。支持内存快速身份验证缓存（Fast Authentication Path）；在非 TLS 通信下，采用 RSA 非对称密钥对（2048 位公钥/私钥）加密传输密码。

```
caching_sha2_password 认证握手阶段
Client                                                  MySQL Server
  │                                                          │
  ├─────────────── 1. 发起 TCP 握手与连接请求 ────────────────►│
  │                                                          │
  │◄────────────── 2. 发送 Server Handshake ─────────────────┤
  │                   (包含 Auth Plugin 名 & 20 字节 Salt)     │
  │                                                          │
  ├─────────────── 3. 发送 Handshake Response ───────────────►│
  │                   (基于 Salt 生成 SHA256 哈希凭证)         │
  │                                                          │
  │              [Server 检查内存凭证缓存 (Fast Path)]          │
  │                                                          │
  │◄────────────── 4a. 缓存命中 (Fast Auth Success: OK) ──────┤ (握手结束，极快)
  │                                                          │
  │ [若缓存未命中 (Full Auth Path)]                            │
  │◄────────────── 4b. 请求密码明文/RSA 密钥 ─────────────────┤
  │                                                          │
  ├─────────────── 5. 发送 RSA 公钥加密的密码 ────────────────►│

  │◄────────────── 6. 私钥解密并比对成功 (Auth OK) ───────────┤
```

## 3. 生产环境用户生命周期与安全基线规范

### 3.1 生产最小权限标准角色矩阵

在企业级生产数据库中，严禁业务或普通运维使用 `root` 或拥有通配权限的账号。必须建立严格的**按需分级赋权模型**：

```sql
-- ====================================================================
-- 1. 业务应用读写账号 (App Read-Write User)
-- ====================================================================
-- 原则: 限制在具体业务库，仅授予 DML，严禁 DDL (CREATE/ALTER/DROP) 及管理权限
CREATE USER 'app_order_rw'@'192.168.10.%' 
  IDENTIFIED WITH caching_sha2_password BY 'Order#App_Prod_2026!xK9'
  WITH MAX_USER_CONNECTIONS 500;

GRANT SELECT, INSERT, UPDATE, DELETE ON order_db.* TO 'app_order_rw'@'192.168.10.%';

-- ====================================================================
-- 2. 业务应用只读账号 (App Read-Only User - 用于只读从库/读写分离)
-- ====================================================================
CREATE USER 'app_order_ro'@'192.168.10.%' 
  IDENTIFIED WITH caching_sha2_password BY 'Order#App_RO_2026!mQ3'
  WITH MAX_USER_CONNECTIONS 800;

GRANT SELECT ON order_db.* TO 'app_order_ro'@'192.168.10.%';

-- ====================================================================
-- 3. 主从复制同步账号 (Replication Slave User)
-- ====================================================================
-- 原则: 仅限制在从库专用 IP 段，仅授予 REPLICATION SLAVE
CREATE USER 'repl_slave'@'192.168.20.%' 
  IDENTIFIED WITH caching_sha2_password BY 'Repl#Slave_Sec_2026!zW8';

GRANT REPLICATION SLAVE ON *.* TO 'repl_slave'@'192.168.20.%';

-- ====================================================================
-- 4. 物理备份账号 (Backup Operator - 专用于 XtraBackup / MEB)
-- ====================================================================
-- 原则: 8.0 最小动态权限组合，不授予数据表 DML 读写权限
CREATE USER 'backup_admin'@'127.0.0.1' 
  IDENTIFIED WITH caching_sha2_password BY 'Bkp#Admin_Local_2026!vP1';

GRANT BACKUP_ADMIN, PROCESS, RELOAD, LOCK TABLES, REPLICATION CLIENT ON *.* TO 'backup_admin'@'127.0.0.1';

-- ====================================================================
-- 5. Prometheus 监控采集账号 (mysqld_exporter)
-- ====================================================================
CREATE USER 'exporter'@'192.168.30.15' 
  IDENTIFIED WITH caching_sha2_password BY 'Exp#Monitor_2026!kL4'
  WITH MAX_USER_CONNECTIONS 20;

GRANT PROCESS, REPLICATION CLIENT ON *.* TO 'exporter'@'192.168.30.15';
GRANT SELECT ON performance_schema.* TO 'exporter'@'192.168.30.15';
GRANT SELECT ON sys.* TO 'exporter'@'192.168.30.15';

-- ====================================================================
-- 6. BI / 报表分析账号 (BI / BigData Read-Only)
-- ====================================================================
-- 原则: 限制最大查询连接数与单小时资源上限，防止大 SQL 拖垮数据库
CREATE USER 'bi_report'@'192.168.40.%' 
  IDENTIFIED WITH caching_sha2_password BY 'BI#Report_ReadOnly_2026!uY7'
  WITH MAX_QUERIES_PER_HOUR 10000
       MAX_USER_CONNECTIONS 10;

GRANT SELECT ON order_db.* TO 'bi_report'@'192.168.40.%';
```

### 3.2 Host 网段白名单与安全准入基线

* **严禁通配符 `%`**：生产环境严禁创建 `'user'@'%'` 账号。必须限定到应用服务器的具体内网子网（如 `'10.20.30.%'`）或固定 IP。
* **本地管理账号限制**：`root` 账号必须且只能限定为 `'root'@'localhost'` 或 `'root'@'127.0.0.1'`，坚决关闭 `root` 远程登录通道。
* **网络与连接加密**：
  生产环境强制开启 TLS/SSL 加密传输，要求客户端连接必须携带 SSL 证书或启用传输加密：
  ```sql
  -- 强制指定用户必须使用 TLS/SSL 加密连接
  ALTER USER 'app_order_rw'@'192.168.10.%' REQUIRE SSL;
  
  -- 金融级要求: 强制双向 TLS 认证 (校验客户端证书 Subject)
  ALTER USER 'app_order_rw'@'192.168.10.%' 
    REQUIRE SUBJECT '/C=CN/ST=Beijing/O=Finance/CN=order-service.prod';
  ```

### 3.3 密码复杂度、历史防复用与防暴力破解策略

#### 密码生命周期全维度配置（MySQL 8.0+ 最佳实践）

```sql
-- 1. 全局配置：密码历史防复用（禁止使用最近 5 次使用过的密码，或 365 天内使用过的密码）
```

### 3.4 视图与存储过程 DEFINER / INVOKER 权限提升安全防护

在 MySQL 中，视图（View）、存储过程（Procedure）、函数（Function）和触发器（Trigger）默认采用 `SQL SECURITY DEFINER` 模式执行：

```
DEFINER 提权漏洞原理解析
┌───────────────────────────┐       ┌───────────────────────────┐
│ 普通低权用户 (dev_user)   │ ────► │ 视图: v_order_summary     │
│ 仅有 v_order_summary 权限 │ 调用  │ DEFINER = 'root'@'local'  │
└───────────────────────────┘       └─────────────┬─────────────┘
                                                  │ 以 root 身份执行
                                                  ▼
                                    ┌───────────────────────────┐
                                    │ 越权访问所有底层敏感物理表 │
                                    └───────────────────────────┘
```

* **安全隐患**：
  若开发者在创建视图或存储过程时指定了 `DEFINER = 'root'@'localhost'`，任何拥有该视图 `SELECT` 权限的低权限用户，在查询视图时都将**以 root 的完整权限在后台执行**。若视图内部包含敏感表关联或恶意函数，低权用户将实现垂直越权（Privilege Escalation）。
* **生产防范规程**：
  1. 生产环境创建视图和例程时，推荐显式指定 `SQL SECURITY INVOKER`（以调用者实际拥有的权限执行鉴权）：
     ```sql
     CREATE SQL SECURITY INVOKER VIEW v_user_public_info AS
     SELECT id, username, nickname, created_at FROM users;
     ```
  2. 严禁使用 `root` 或 DBA 账号作为业务视图的 `DEFINER`，必须使用专用的低权只读账号定义。
  3. 定期运行审计 SQL 扫描系统内所有 `DEFINER = 'root'` 的对象并进行合规整改。

### 4.2 8.0.14+ 零停机双密码平滑轮换 (Dual Passwords) 全流程演练

在微服务与容器化（Kubernetes）生产环境中，同一个数据库账号往往被数十甚至上百个 Pod 实例共享。传统单密码模式下，一旦修改数据库密码，未完成配置更新的 Pod 会立即因鉴权失败抛出大量连接异常。

MySQL 8.0.14 引入的 **双密码（Dual Passwords）** 机制彻底解决了这一痛点：

```
双密码零停机轮换时序图
时间线 ──────────────────────────────────────────────────────────────────────────►
MySQL Server: [当前主密码: Pwd_V1] ───► [主: Pwd_V2 | 备用: Pwd_V1] ───► [主: Pwd_V2 (废弃旧密码)]
                                             ▲
                                             │ 兼容期 (双密码同时有效)
K8s Pods:    [全部 Pod 运行使用 Pwd_V1] ───► [逐步滚动发布配置] ──────► [全部 Pod 运行使用 Pwd_V2]
                                             (新旧 Pod 均能成功鉴权)
```

#### 四步标准实战演练

```sql
-- ====================================================================
-- 步骤 1: 设置新密码，同时保留旧密码作为 Secondary Password (备用密码)
-- ====================================================================
ALTER USER 'app_order_rw'@'192.168.10.%' 
  IDENTIFIED BY 'OrderApp_Pass_2026_V2' 
  RETAIN CURRENT PASSWORD;

-- 验证状态: 查看当前用户的密码状态 (可观察到拥有主/备两个密码凭证)
-- 此时: 无论是老 Pod (使用旧密码 V1) 还是新 Pod (使用新密码 V2)，均可建立连接！

-- ====================================================================
-- 步骤 2: 推动应用微服务集群进行滚动发布 (Rolling Update)
-- ====================================================================
-- K8s 逐步销毁老 Pod，拉起挂载新配置中心密码 (V2) 的新 Pod，业务无感知。

-- ====================================================================
-- 步骤 3: 观察监控指标，确认所有老连接已全部优雅断开并使用新密码建立
-- ====================================================================
-- 检查 Performance Schema 中当前连接的认证状态。

-- ====================================================================
-- 步骤 4: 废弃旧密码，关闭备用凭证通道 (回归单密码安全基线)
-- ====================================================================
ALTER USER 'app_order_rw'@'192.168.10.%' DISCARD OLD PASSWORD;
```

> [!TIP] 紧急回滚预案
> 如果步骤 2 滚动发布中途发现应用程序新配置异常，需立即回滚，可随时执行：
> `ALTER USER 'app_order_rw'@'192.168.10.%' IDENTIFIED BY 'OrderApp_Pass_2026_V1' DISCARD OLD PASSWORD;`，一键还原至旧密码。

### 4.3 资源限制与配额隔离

为防止开发测试账号或 BI 统计分析由于慢查询/死循环拖垮整个数据库实例，MySQL 提供了账号级别的资源限制（Resource Limits）与 8.0 资源组（Resource Groups）：

#### 1. 账号级资源硬限制
```sql
ALTER USER 'bi_analyst'@'192.168.40.%' WITH
  MAX_QUERIES_PER_HOUR 5000       -- 每小时最大执行查询数
  MAX_UPDATES_PER_HOUR 0          -- 每小时最大更新数 (0 表示禁止 DML 更新)
  MAX_CONNECTIONS_PER_HOUR 100    -- 每小时最大新建连接数
  MAX_USER_CONNECTIONS 5;         -- 全局最大并发活跃连接数
```

#### 2. MySQL 8.0 资源组 (Resource Groups - CPU 绑定隔离)
MySQL 8.0 支持在操作系统层面将特定查询或线程绑定到指定 CPU 核心：

```sql
-- 1. 创建批处理/报表专用低优先级资源组 (绑定 CPU 0-1 核心，线程优先级 19 最低)
CREATE RESOURCE GROUP rg_batch_report
  TYPE = USER
  VCPU = 0,1
  THREAD_PRIORITY = 19;

-- 2. 将后台特定查询绑定至资源组执行 (利用 Optimizer Hint)
SELECT /*+ RESOURCE_GROUP(rg_batch_report) */ 
  customer_id, SUM(amount) 
FROM order_records 
GROUP BY customer_id;
```

## 5. 跨版本升级与驱动兼容性排障指南

### 5.1 `caching_sha2_password` 握手原理与 RSA 公钥检索

当从 MySQL 5.7 升级至 8.0 后，新创建的用户默认使用 `caching_sha2_password`。如果客户端应用没有开启 TLS/SSL，在执行完整身份验证（Full Auth Path）时，客户端必须获取 MySQL Server 端的 **RSA 2048 位公钥** 来加密发送密码。

```
客户端获取 RSA 公钥的两种机制：
1. 客户端本地配置公钥文件 (推荐生产): serverRsaPublicKeyFile=/path/to/public_key.pem
2. 向 Server 在线索取 (存在中间人攻击风险): allowPublicKeyRetrieval=true
```

```
RSA 公钥检索与加密流程
Client                                                  MySQL Server
  │                                                          │
  ├────────────── 1. Fast Auth 未命中，请求公钥 ──────────────►│
  │                                                          │
  │   (若客户端配置了 allowPublicKeyRetrieval=true)            │
  │◄───────────── 2. 返回 Server RSA 公钥 ────────────────────┤
  │                                                          │
  ├────────────── 3. 本地使用该公钥加密明文密码 ───────────────►│
  │                                                          │
  │◄───────────── 4. Server 使用私钥解密并校验成功 ────────────┤
```

### 5.2 主流语言客户端驱动兼容性矩阵

| 开发语言 / 框架 | 驱动名称 (Driver) | 支持 `caching_sha2_password` 的最低版本 | 常见错误信息与解决参数 |
| :--- | :--- | :--- | :--- |
| **Java (JDBC)** | `mysql-connector-java` / `mysql-connector-j` | **8.0.11+** (强烈建议 8.0.28+) | 报错：`Unable to load authentication plugin 'caching_sha2_password'`。<br>解决：升级驱动，并在 JDBC URL 中配置 `useSSL=true` 或 `allowPublicKeyRetrieval=true` |

## 6. 权限安全审计、合规巡检与应急救援

### 6.1 权限安全巡检 SQL 资产库

DBA 可定期（如每周或合规巡检期间）自动执行以下巡检脚本，输出安全风险清单：

```sql
-- ====================================================================
-- 巡检 1: 探测拥有通配符 '%' 的高危用户 (违反网络准入白名单规范)
-- ====================================================================
SELECT user, host, plugin, account_locked, password_expired 
FROM mysql.user 
WHERE host = '%' AND user NOT IN ('health_checker');

-- 巡检 2: 探测拥有全局高危权限 (SUPER, GRANT OPTION, ALL) 的非 DBA 账号
-- ====================================================================
SELECT user, host, Super_priv, Grant_priv, Reload_priv, Shutdown_priv 
FROM mysql.user 
WHERE (Super_priv = 'Y' OR Grant_priv = 'Y') 
  AND user NOT IN ('root', 'mysql.session', 'mysql.infoschema', 'dba_admin');

-- ====================================================================
-- 巡检 3: 探测仍在使用老旧不安全 mysql_native_password 的账号
-- ====================================================================
SELECT user, host, plugin 
FROM mysql.user 
WHERE plugin = 'mysql_native_password';

-- ====================================================================
-- 巡检 4: 探测未设置密码或密码已过期的僵尸账号
-- ====================================================================
SELECT user, host, authentication_string, password_expired, password_last_changed 
FROM mysql.user 
WHERE authentication_string = '' OR authentication_string IS NULL;

-- ====================================================================
-- 巡检 5: 探测视图中 DEFINER 为 root 的高危提权隐患对象
-- ====================================================================
SELECT table_schema, table_name, definer, security_type 
FROM information_schema.views 
WHERE definer LIKE 'root@%' AND security_type = 'DEFINER';
```

### 6.2 Root 密码丢失安全应急重置 (5.7 vs 8.0 差异化救援流程)

当生产数据库管理员密码丢失或被误篡改时，需通过 `--skip-grant-tables` 进行安全救援。

```
安全救援黄金准则：
必须同时添加 --skip-networking 参数！
禁止数据库在无鉴权模式下向网络开放监听，防止黑客通过网络端口免密直接登入删库！
```

#### 标准应急修复操作步骤

```bash
# 步骤 1: 停止正常运行的 mysqld 服务
systemctl stop mysqld

# 步骤 2: 以安全救援模式启动 mysqld (跳过权限表 + 禁用网络监听)
mysqld --user=mysql --skip-grant-tables --skip-networking &

# 步骤 3: 本地通过 socket 免密登录
mysql -u root -S /var/lib/mysql/mysql.sock
```

#### 关键差异：5.7 与 8.0 的修改密码语法

##### MySQL 5.7 救援重置语法：
```sql
-- 5.7 必须刷新权限或直接修改底层字段
FLUSH PRIVILEGES;
ALTER USER 'root'@'localhost' IDENTIFIED BY 'NewRoot#Secure_2026_57';
-- 或者 (底层更新模式)
-- UPDATE mysql.user SET authentication_string = PASSWORD('NewRoot#Secure_2026_57') WHERE User = 'root' AND Host = 'localhost';
-- FLUSH PRIVILEGES;
```

##### MySQL 8.0+ 救援重置语法：
```sql
-- 8.0 严禁直接 UPDATE 权限表！必须先 FLUSH PRIVILEGES 加载内存 ACL，再使用 ALTER USER
FLUSH PRIVILEGES;
ALTER USER 'root'@'localhost' IDENTIFIED WITH caching_sha2_password BY 'NewRoot#Secure_2026_80';
```

```bash
# 步骤 4: 退出 mysql 并杀掉救援进程，恢复正常模式
kill -9 $(pgrep -f "mysqld.*skip-grant-tables")
systemctl start mysqld
```

### 6.3 连接数爆满 (Too Many Connections) 应急抢救通道

当线上突发慢查询或流量洪峰导致连接数占满 `max_connections` 时，业务与普通连接将被拒绝并抛出 `ERROR 1040 (08004): Too many connections`。

```
应急管理通道演进
┌────────────────────────────────────────────────────────┐
│ MySQL 5.7 预留连接机制                                  │
│   保留 1 个额外连接名额 (max_connections + 1)，        │
│   仅限拥有 SUPER 权限的账号登入。                      │
│   * 缺陷: 若监控脚本或已有运维会话占用了该名额，DBA 仍被拒 │
└────────────────────────────────────────────────────────┘
                            │
                            ▼ 演进
┌────────────────────────────────────────────────────────┐
│ MySQL 8.0.14+ 独立管理端口 (Admin Port)                │
│   配置独立监听 IP、端口与独立线程池，不受 max_connections 限制 │
│   需具备 CONNECTION_ADMIN 权限                         │
└────────────────────────────────────────────────────────┘
```

#### MySQL 8.0+ 生产级 Admin Port 配置与登录

```ini
# 在 my.cnf 中配置专用管理监听
[mysqld]
admin_address = 127.0.0.1       # 绑定管理网络接口 (如本机或运维管理网卡)
admin_port = 33062              # 独立管理端口
create_admin_listener_thread = ON # 开启专有管理监听线程 (与主连接池物理隔离)
```

```bash
# 当 3306 业务端口打满报错时，DBA 携带管理端口进行救援登录
mysql -u dba_admin -p -h 127.0.0.1 -P 33062

# 登入后迅速执行排查与查杀慢连接
# SHOW PROCESSLIST;
# KILL CONNECTION <blocking_thread_id>;
```

### 6.4 主从复制架构下的权限同步陷阱

在主从复制（Master-Slave / Master-Replica）架构中，`mysql` 系统库的同步处理不当极易引发严重的从库同步中断或权限覆盖：

* **陷阱 1：`replicate-wild-do-table=mysql.%` 导致从库权限被冲掉**：
  若在从库配置中开启了全量同步 `mysql` 库，主库上执行的任何 `CREATE USER`、`GRANT` 会全量覆盖从库。如果主从库的物理网络拓扑不同（例如从库有独立的备份账号、只读账号或探活白名单），从库特有的权限元数据将被破坏。
* **最佳实践规范**：
  1. 生产环境推荐采用全库复制，但利用应用层/基础设施即代码（IaC / Ansible / Terraform）进行统一的 DCL 变更版本控制。
  2. 若主从库有差异化账号，主库执行 DCL 时若不希望同步到从库，可在会话级别临时关闭 Binlog：
     ```sql
     -- 仅在当前节点生效，不写入 Binlog 同步到从库 (需谨慎使用)
     SET sql_log_bin = 0;
     CREATE USER 'local_backup'@'127.0.0.1' IDENTIFIED BY '...';
     SET sql_log_bin = 1;
     ```
  3. 在 MySQL 8.0 中，DDL/DCL 是原子性并记录于 Binlog 中的，切忌直接在从库手工对系统表执行 DML 操作。
