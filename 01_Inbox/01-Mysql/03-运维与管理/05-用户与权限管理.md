## 1. 业务背景与技术定位 (Context & Core Architecture)

### 1.1 企业级数据库访问控制的核心痛点

数据库作为企业核心资产的最终持久化中枢，其权限与访问控制体系直接决定了系统的机密性（Confidentiality）、完整性（Integrity）与可用性（Availability）。在传统企业向云原生、微服务架构演进过程中，数据库权限管理通常面临以下严峻挑战：

1. **权限过度膨胀与粗粒度授权风险**：在 MySQL 5.7 时代，由于管理权限过度绑定于粗粒度的 `SUPER` 权限，运维、监控、备份甚至部分业务系统账号常被赋予全局高权，极易因人员误操作或凭证泄漏引发灾难性删库（Drop Database/Table）。
2. **密码轮换与业务高可用中断矛盾**：在微服务与 Kubernetes 容器化环境中，单账号常被数十至上百个 Pod 实例共享。传统单密码模型下，一旦修改密码，滚动发布期间未更新配置的 Pod 会瞬间因鉴权失败抛出海量异常，导致业务不可用。
3. **鉴权锁竞争与连接雪崩**：在高并发大流量生产场景下，运维人员若滥用 `FLUSH PRIVILEGES` 或高频执行 DCL 语句，会触发全局 ACL 缓存写锁竞争（`Waiting for acl cache lock`），导致新建连接池全部阻塞排队，进而诱发系统级雪崩。
4. **特权提升与安全合规审计脱节**：存储过程与视图的 `DEFINER` 机制若缺乏约束，攻击者或低权开发人员可利用高权 DEFINER 实施垂直越权；同时，金融等保 2.0 三级、PCI-DSS、SOC2 等合规标准对密码复杂度、生命周期、历史防复用、防暴力破解锁定提出了强制性要求。
5. **分布式主从复制与 MGR 权限漂移**：多节点拓扑中，`mysql` 系统库复制过滤配置不当或在节点间直接执行 DML 修改权限表，会导致主从节点元数据不一致或从库同步中断（Replication Break）。

### 1.2 架构演进全景：MySQL 5.7 到 8.0/8.4 的质变

MySQL 8.0（以及最新的 8.4 LTS）对底层的权限与用户系统进行了彻底的重构，实现了从“粗粒度、非事务、静态硬编码”向“细粒度、完全事务性、动态可扩展”的现代架构跃迁：

| 核心维度 | MySQL 5.7 遗留架构 | MySQL 8.0+ / 8.4 LTS 现代架构 | 架构演进价值与收益 |
| :--- | :--- | :--- | :--- |
| **元数据存储引擎** | MyISAM 引擎 (`mysql.user`, `mysql.db` 等) | **InnoDB 引擎** (统一集成于 Data Dictionary 数据字典) | DCL 具备**完全事务性与原子性 (Atomic DDL/DCL)**，消灭元数据半同步脏状态 |
| **超级管理员权限** | `SUPER` 一权独大（修改变量、杀连接、管主从合一） | `SUPER` 废弃，拆解为 **30+ 细粒度 Dynamic Privileges** | 践行安全最小权限原则（PoLP），实现权限精准解耦 |
| **角色管理 (RBAC)** | 原生不支持，需上层应用/中间件自行模拟 | **原生支持 RBAC 角色体系** (`CREATE/GRANT/SET ROLE`) | 简化数百个开发与业务账号的矩阵化批量权限运维 |
| **默认认证插件** | `mysql_native_password` (SHA-1 双重哈希) | **`caching_sha2_password`** (SHA-256 + 内存快速缓存 + RSA) | 防御高性能彩虹表与中间人嗅探攻击，达金融级合规标准 |
| **密码平滑轮换** | 单一密码，改密必须同步重启或滚动报错 | **双密码机制 (Dual Passwords)**，`RETAIN CURRENT PASSWORD` | 支撑 K8s/微服务集群多 Pod 滚动更新下的**零停机改密** |
| **特权账号隔离** | 具备 `CREATE USER` 的管理员可任意篡改所有账号 | 引入 **`SYSTEM_USER` 动态权限** 保护系统级账号 | 杜绝普通 DBA 或提权用户篡改 `root` 或云托管专有账号 |
| **权限挖洞机制** | 全局授权无法排除单个库（必须按库逐一授权） | **`PARTIAL_REVOKES` 机制**，支持在 `*.*` 下剥离特定 Schema | 大幅简化多租户场景下的权限下发与隔离配置 |
| **多因素认证 (MFA)**| 不支持原生 MFA | **原生支持 MFA 多因素认证** (8.0.27+) | 核心金融资产支持双因子动态校验，防御凭证撞库 |
| **创建与授权语法** | 允许 `GRANT ... IDENTIFIED BY 'pwd'` 隐式建号 | **彻底废除**隐式建号，必须显式 `CREATE USER` 再 `GRANT` | 阻断因拼写错误意外创建匿名或高危账号的安全隐患 |
| **管理连接通道** | 依赖预留 1 个 `SUPER` 连接 (`max_connections + 1`) | **独立管理端口 (`admin_port`)** 与物理独立管理线程池 | 连接池爆满 (`Too many connections`) 时仍能秒级登入排障 |

## 2. MySQL 权限系统内核模型与底层架构剖析 (Kernel & ACL Internal Architecture)

### 2.1 鉴权两阶段状态机

MySQL 的权限拦截与校验完全发生在 Server 层，在客户端请求生命周期中被严格划分为两个阶段：

```
MySQL 客户端交互两阶段状态机
┌────────────────────────────────────────────────────────────────────────┐
│ 阶段 1: 连接握手验证 (Connection Verification)                         │
│ 客户端连接 ──► 匹配 IP/Host ──► 校验密码散列 ──► 检查锁定与过期 ──► 放行│
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 连接成功建立
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 阶段 2: 请求指令鉴权 (Request Verification)                            │
│ 收到 SQL ──► 解析 Target Objects ──► 逐级短路校验 ──► 执行或拒绝      │
└────────────────────────────────────────────────────────────────────────┘
```

#### 阶段 1：连接握手阶段（Connection Verification）
1. 客户端建立 TCP 连接，Server 读取客户端 IP 地址，扫描内部排序的 `acl_users` 列表进行 Host 匹配。
2. 校验客户端提供的认证凭证（`caching_sha2_password` 或外部 LDAP/PAM）。
3. 检查账号生命周期状态：是否处于锁定状态（`account_locked = 'Y'`）、密码是否过期（`password_expired`）。
4. 校验并发连接配额：当前用户的总活跃连接数是否超过 `MAX_USER_CONNECTIONS` 或全局 `max_connections`。
5. 若任何一步失败，返回 `ER_ACCESS_DENIED_ERROR` (Error 1045) 并立即终止 TCP 连接。

#### 阶段 2：请求鉴权阶段（Request Verification）
1. 客户端发送具体的 SQL 指令，解析器（Parser）提取操作动词（`SELECT`, `UPDATE`, `DROP` 等）与目标元数据对象（Schema、Table、Column、View、Routine）。
2. **短路优先校验（Short-Circuit Evaluation）**：鉴权引擎自顶向下依次检索 Global -> Database -> Table -> Column 层级。若在某一层级命中满足条件，则立即放行，不再扫描下层；若扫描至最底层仍无对应权限，拒绝执行并抛出 `ER_TABLEACCESS_DENIED_ERROR` (Error 1142) 或 `ER_DBACCESS_DENIED_ERROR` (Error 1044)。

### 2.2 权限分层继承与短路校验机制

```
MySQL 权限分层体系与底层存储映射

│ 1. 全局层级 (Global Level)        --> *.*                               │

└────────────────────────────┬────────────────────────────────────────────┘
                             │ (未满足，向下深入)
                             ▼

│ 4. 列层级 (Column Level)        --> db_name.table_name(col1, col2)      │
│    存储表: mysql.columns_priv                                           │
└────────────────────────────┬────────────────────────────────────────────┘
                             │ (存储过程/函数)
                             ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ 5. 例程/子程序层级 (Routine)    --> PROCEDURE / FUNCTION                │
│    存储表: mysql.procs_priv                                             │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 短路校验算法实现路径
在 MySQL Server 源码中（`sql_authentication.cc` 与 `sql_authorization.cc`），鉴权函数（如 `check_access()` 与 `check_grant()`）遵循以下逻辑：
```cpp
// 伪代码逻辑示意
bool check_access(THD *thd, ulong want_access, const char *db, Table_ref *table) {
    // 1. 检查全局权限 (Global Level)
    if ((thd->security_ctx->master_access() & want_access) == want_access) {
        return false; // Access Granted (放行)
    }
    
    // 2. 检查库级权限 (Database Level)
    if ((thd->security_ctx->db_access(db) & want_access) == want_access) {
        return false; // Access Granted (放行)
    }
    
    // 3. 检查表级权限 (Table Level) 与 列级权限 (Column Level)
    return check_grant(thd, want_access, table);
}
```

### 2.3 Host 匹配规则与精确度排序算法

MySQL 用户的唯一标识由两部分构成：`'user_name'@'host_name'`。当客户端建立连接时，Server 将其 IP/主机名与内存中缓存的账号列表进行比对。比对顺序严格按照 **`ACL_HOST_AND_IP` 排序算法** 进行：

```
Host 排序匹配优先级：
Literal IP / Hostname (最精确) > 网段掩码 (CIDR / Subnet Mask) > 通配符 (%) > 匿名用户
```

#### 排序规则详解
1. **精确主机名/IP 优先**：如 `192.168.10.101` 比 `192.168.10.%` 排序更靠前。
2. **长掩码优先于短掩码**：如 `192.168.10.0/255.255.255.0` 比 `192.168.0.0/255.255.0.0` 排序更靠前。
3. **具名用户优先于匿名用户**：当 Host 完全相同时，`User` 字段非空的记录排在空字符串（`User=''`）之前。

#### 生产经典截胡陷阱
> [!WARNING] 生产真实故障：IP 截胡引发的凭证/权限不一致
> 假设系统中同时存在两个账号：
> 1. `'app_user'@'10.20.30.%'`（旧账号，密码 `OldPass123`，权限仅有 `SELECT`）
> 2. `'app_user'@'%'`（新运维创建的通用账号，密码 `NewPass456`，权限有 `SELECT, INSERT, UPDATE`）
> 
> 当来自 `10.20.30.15` 的应用服务器连接 MySQL 时，MySQL 根据精确度排序优先匹配到 `'app_user'@'10.20.30.%'`。如果应用使用 `NewPass456` 尝试连接，将直接收到 `Error 1045 (28000): Access denied for user 'app_user'@'10.20.30.15'`；即使使用旧密码连入，执行 `INSERT` 时也会抛出 `Error 1142 (42000): INSERT command denied`。

### 2.4 Server 层 ACL 内存缓存结构与锁竞争机理

为了在高并发下实现微秒级鉴权，MySQL 在 Server 启动时将磁盘权限表全量加载至内存中的专有数据结构中：

```
Server 内存 ACL 核心结构
├── acl_users (动态数组，按 Host/User 精确度排序，用于握手与全局权限判断)
├── acl_dbs   (动态数组，按 Host/DB/User 排序，用于库级权限判断)
├── tables_priv_hash  (基于 Hash(db+table+user+host) 的高效表级哈希表)
├── columns_priv_hash (基于 Hash(db+table+col+user+host) 的列级哈希表)
└── procs_priv_hash   (例程与存储过程哈希表)
```

#### 鉴权锁机制与并发雪崩机理
- **锁保护机制**：读取上述 ACL 内存结构时需要持有 **`LOCK_grant` 读锁**（在 8.0 内部通过 `acl_cache` 锁同步）。
- **写锁阻塞**：当执行 `FLUSH PRIVILEGES` 或 DCL 语句（`GRANT`, `REVOKE`, `ALTER USER`, `CREATE USER`）时，Server 需要对 ACL 内存结构施加 **`LOCK_grant` 全局排他写锁**。
- **雪崩诱因**：在高并发（例如 QPS > 50,000）的生产环境中，若定时任务或自动化脚本高频执行 `FLUSH PRIVILEGES`，写锁会阻塞所有新建连接与鉴权请求，产生大量处于 `Waiting for acl cache lock` 状态的线程，瞬间耗尽线程池与连接数，引发服务不可用。

### 2.5 权限元数据存储架构演进 (5.7 vs 8.0)

```
元数据存储演进
MySQL 5.7:
[mysql.user] ──► MyISAM 引擎 ──► 非事务性 (Crash 可能导致元数据残留)
                                 直接 DML (UPDATE mysql.user) 导致内存与磁盘脱节

MySQL 8.0+:
[mysql.user, mysql.global_grants, mysql.role_edges] 
        │
        ▼
[InnoDB 事务存储引擎 + 统一 Data Dictionary (mysqld.db)] ──► 原子性 DDL/DCL (Crash-Safe)
                                                              禁止直接 DML (强制标准 DCL)
```

- **原子性 DCL (Atomic DCL)**：在 MySQL 8.0 中，`CREATE USER 'u1', 'u2';` 或批量授权操作被包装为 InnoDB 事务。如果在创建 `u2` 时发生冲突或宕机，`u1` 会自动回滚，确保权限元数据的绝对一致。
- **禁止直接 DML 修改系统表**：在 8.0 中直接执行 `UPDATE mysql.user SET ...` 会触发报错或产生不可预期的状态，所有权限变更必须通过标准 DCL 语句进行。

### 2.6 `FLUSH PRIVILEGES` 深度剖析：何时用？何时禁？

| 操作场景 | 是否需要 `FLUSH PRIVILEGES` | 行为解释与底层机理 |
| :--- | :--- | :--- |
| **执行标准 DCL** (`CREATE/ALTER/DROP USER`, `GRANT`, `REVOKE`) | **绝对不需要（严禁盲目执行）** | Server 在修改磁盘元数据的同时，会在同一个事务内自动原子更新内存 ACL 缓存。 |
| **`--skip-grant-tables` 应急救援重置密码** | **必须执行** | 在跳过权限表启动时，Server 内存中未加载 ACL 结构，执行 `FLUSH PRIVILEGES` 才能载入内存并允许执行 `ALTER USER`。 |
| **非法通过 DML 直接更新了 `mysql` 库表** | **必须执行** | 直接执行 `UPDATE mysql.user` 仅修改了磁盘数据，内存 ACL 毫无感知，必须刷新以同步。生产严禁此类操作。 |

## 3. MySQL 5.7 vs 8.0 权限与用户体系全景对比与演进矩阵 (Evolution Matrix)

### 3.1 核心特性全景对比表

| 维度对比 | MySQL 5.7 架构 | MySQL 8.0+ / 8.4 LTS 架构 | 生产级影响与规范 |
| :--- | :--- | :--- | :--- |
| **创建与授权语法** | 允许 `GRANT ... IDENTIFIED BY` 隐式创建用户 | **彻底废除隐式创建**，强制分步执行 | 消除拼写手误导致意外创建无意图账号的漏洞 |
| **特权模型** | `SUPER` 一权独大 | `SUPER` 废弃，拆为 **30+ 项 Dynamic Privileges** | 实现权限精准解耦，践行最小权限原则 |
| **RBAC 角色体系** | 原生不支持 | **原生完整支持 RBAC 角色体系** | 批量管理大型研发团队与微服务账号权限 |
| **默认认证插件** | `mysql_native_password` (SHA-1) | **`caching_sha2_password`** (SHA-256 + RSA) | 金融级防嗅探与彩虹表攻击能力 |
| **密码平滑轮换** | 仅支持单密码 | **双密码机制 (Dual Passwords)** | K8s Pod 滚动更新无损改密，业务 0 中断 |
| **密码复杂度控制** | `validate_password` 插件 (Plugin 架构) | `component_validate_password` (Component 组件) | 规范化组件化管理，参数统一规范 |
| **防暴力破解** | 社区版无原生锁定机制 | **原生支持连续失败自动锁定** (`FAILED_LOGIN_ATTEMPTS`) | 阻断内网嗅探与字典暴破攻击 |
| **密码历史与生命周期** | 无原生防复用控制 | **支持密码历史与间隔校验** (`PASSWORD_HISTORY`) | 满足等保 2.0 三级与 SOC2 合规审计 |
| **特权账号防护** | 普通管理员可任意 KILL 或篡改任意账号 | **`SYSTEM_USER` 动态权限机制** | 保护核心系统级账号不被普通运维篡改 |
| **参数持久化管理** | 仅 `SET GLOBAL`（重启丢失） | **`SET PERSIST` / `SET PERSIST_ONLY`** | 配合 `PERSIST_ROLES_ADMIN` 规范云原生配置变更 |
| **管理连接专用通道** | 依赖预留 1 个 `SUPER` 连接 (`max_connections + 1`) | **独立管理端口 (`admin_port`)** 与物理独立管理线程池 | 连接打满 (`1040`) 时提供独立救灾入口 |
| **CPU 资源隔离** | 不支持用户级别 CPU 核心绑定 | **支持 Resource Groups (资源组)** | 防止后台分析或导出账号抢占业务 CPU |

### 3.2 授权语法变更与安全规范

#### MySQL 5.7 遗留语法（生产严禁使用）
```sql
-- 5.7 语法：若用户不存在则静默创建，若存在则重置密码并赋予权限
GRANT SELECT, INSERT ON app_db.* TO 'app_user'@'192.168.1.%' IDENTIFIED BY 'Old_Pass#2018';
```
> [!CAUTION] 高危风险
> 在 5.7 中，若 DBA 误将用户名输入为 `'app_usr'`，MySQL 将无警告地静默创建一个全新的高权账号，密码即为该指令中内容，极易产生权限遗留漏洞。

#### MySQL 8.0+ 强制标准语法（显式解耦）
```sql
-- 步骤 1: 显式创建用户，绑定安全认证插件、密码生命周期与失败锁定策略
CREATE USER 'app_user'@'192.168.1.%' 
  IDENTIFIED WITH caching_sha2_password BY 'Secure_Pass#2026!xK9'
  PASSWORD EXPIRE INTERVAL 90 DAY
  FAILED_LOGIN_ATTEMPTS 5 PASSWORD_LOCK_TIME 1;

-- 步骤 2: 精准授予业务最小所需 DML 权限
GRANT SELECT, INSERT, UPDATE, DELETE ON app_db.* TO 'app_user'@'192.168.1.%';
```

### 3.3 认证插件架构升级与加密算法底层原理

#### `mysql_native_password` vs `caching_sha2_password`
- **`mysql_native_password`**：采用 `SHA1(SHA1(password))` 双重哈希算法。在网络传输时虽然使用随机 Salt 进行了挑战-应答（Challenge-Response），但由于底层哈希长度仅为 160 位且已被证实存在碰撞缺陷，无法抵御现代 GPU 集群的彩虹表攻击。
- **`caching_sha2_password`**：采用 **SHA-256** 散列算法，引入 **20 轮加盐迭代（Salted Multi-Round Hashing）**。支持 Server 端内存凭证快速缓存（Fast Authentication Path）；在非 TLS 通信下，强制使用 2048 位 RSA 非对称密钥加密传输密码。

```
caching_sha2_password 握手时序图
Client                                                          MySQL Server
  │                                                                  │
  ├─────────────────── 1. 发起 TCP 连接请求 ─────────────────────────►│
  │                                                                  │
  │◄────────────────── 2. Initial Handshake Packet ──────────────────┤
  │                      (包含 Auth Plugin 名 & 20 字节 Salt)         │
  │                                                                  │
  ├─────────────────── 3. Handshake Response Packet ─────────────────►│
  │                      (发送 XOR(SHA256(password), SHA256(Salt)))   │
  │                                                                  │
  │                     [Server 检索内存凭证缓存 (Fast Path)]          │
  │                                                                  │
  │◄────────────────── 4a. 缓存命中 (Fast Auth Success: OK Packet) ──┤ (极速握手完成)
  │                                                                  │
  │ [若缓存未命中 (Full Auth Path)]                                    │
  │◄────────────────── 4b. 请求 RSA 公钥或明文凭证 ──────────────────┤
  │                                                                  │
  ├─────────────────── 5. 发送经 RSA 公钥加密的密码 ─────────────────►│
  │                                                                  │
  │◄────────────────── 6. Server 私钥解密、比对成功并写入缓存 (OK) ────┤
```

### 3.4 密码复杂度校验体系演进 (Plugin vs Component)

MySQL 8.0 采用统一的 Component 组件架构取代了传统的 Plugin 动态库：

```sql
-- 8.0 安装密码复杂度组件
INSTALL COMPONENT 'file://component_validate_password';

-- 生产级安全基线推荐配置 (持久化写入 mysqld-auto.cnf)

SET PERSIST validate_password.length = 12;                -- 最小长度 12 位
SET PERSIST validate_password.mixed_case_count = 1;       -- 至少包含 1 个大写与 1 个小写字母
SET PERSIST validate_password.number_count = 1;           -- 至少包含 1 个数字
SET PERSIST validate_password.special_char_count = 1;     -- 至少包含 1 个特殊字符
SET PERSIST validate_password.check_user_name = ON;       -- 禁止密码包含用户名
```

### 3.5 管理连接专用通道 (Admin Port)

在 MySQL 5.7 中，当连接数打满 `max_connections` 时，Server 仅保留一个额外的连接名额（`max_connections + 1`）给具备 `SUPER` 权限的用户。如果监控脚本或已有运维会话占用了该名额，DBA 将彻底无法登录排障。

MySQL 8.0.14 引入了**独立管理端口（Admin Port）**，具备独立的监听 IP、端口及物理隔离的专属处理线程：

```ini
# my.cnf 配置
[mysqld]
admin_address = 127.0.0.1          # 绑定管理网络接口 (如本机或专有运维内网网卡)
admin_port = 33062                 # 独立管理端口
create_admin_listener_thread = ON  # 启用专属监听线程 (与主连接池完全隔离)
```

```bash
# 紧急情况下即使 3306 端口报 Too many connections，DBA 通过 33062 秒级连入
mysql -u dba_admin -p -h 127.0.0.1 -P 33062
```

## 4. MySQL 8.0 细粒度动态权限 (Dynamic Privileges) 全景体系

### 4.1 为什么必须废弃 `SUPER` 权限？

在 MySQL 5.7 中，`SUPER` 权限所赋予的能力过于庞大，包括但不限于：
1. 修改全局系统变量 (`SET GLOBAL`)；
2. 强制终止任意客户端连接与查询 (`KILL`)；
3. 控制主从复制启停与重构 (`CHANGE REPLICATION SOURCE TO`)；
4. 绕过只读模式 (`read_only` / `super_read_only`)；
5. 执行 Binlog 清理与强制刷盘 (`PURGE BINARY LOGS`)。

将 `SUPER` 授予任何监控、备份或普通运维人员，都意味着直接让渡了实例的最高控制权。MySQL 8.0 将 `SUPER` 拆解为细粒度的 **Dynamic Privileges**，存储于 `mysql.global_grants` 表中，由组件或 Server 动态管理。

## 5. 基于角色的访问控制 (RBAC) 体系深度实战与图谱管理

### 5.1 RBAC 模型原理与角色本质

在 MySQL 8.0 中，角色（Role）在底层的物理结构与用户（User）完全同构——它本质上是一个**不含密码凭证、被标记为锁定状态（`account_locked='Y'`）、无法直接建立 TCP 连接但拥有独立权限集合的特殊 User 实体**。

```
RBAC 权限分发模型
┌──────────────────────────────┐       ┌──────────────────────────────┐
│  Role: r_order_readonly      │       │  Role: r_order_readwrite     │
│  - SELECT ON order_db.*      │       │  - SELECT, INSERT, UPDATE,   │
│                              │       │    DELETE ON order_db.*      │
└──────────────┬───────────────┘       └──────────────┬───────────────┘
               │ 赋予                                 │ 赋予
               ▼                                      ▼
┌──────────────────────────────┐       ┌──────────────────────────────┐
│ User: dev_zhangsan           │       │ User: svc_order_api          │
└──────────────────────────────┘       └──────────────────────────────┘
```

---

### 5.2 角色图谱 (Role Graph) 继承与循环检测

MySQL 8.0 支持多层嵌套角色继承（Nested Roles）。权限关系在底层通过 `mysql.role_edges` 系统表进行持久化图谱存储：

```
角色多层嵌套继承拓扑
┌────────────────────────┐
│ Role: r_base_read      │ (基础只读)
└───────────┬────────────┘
            │ 继承 (GRANT r_base_read TO r_data_analyst)
            ▼
┌────────────────────────┐
│ Role: r_data_analyst   │ (分析员: 继承只读 + 临时表权限)
└───────────┬────────────┘
            │ 继承 (GRANT r_data_analyst TO 'dev_lisi'@'%')
            ▼
┌────────────────────────┐
│ User: dev_lisi         │ (最终用户生效所有上游展开的权限并集)
└────────────────────────┘
```

- **循环依赖检测（Cycle Detection）**：Server 在执行 `GRANT role1 TO role2;` 时会自动遍历 Role Graph。若发现闭环路径（如 `role1 -> role2 -> role3 -> role1`），将直接阻断并抛出 `ERROR 3530 (HY000): A cycle occurred in the role graph.`。

### 5.4 角色激活策略与生产最佳实践

默认情况下，用户连入 MySQL 后，所赋予的角色处于 **未激活（INACTIVE）** 状态。必须通过以下策略之一进行激活：

#### 方案 1：会话级显式激活
```sql
-- 查看当前激活的角色
SELECT CURRENT_ROLE();

-- 显式激活已拥有的全部角色
SET ROLE ALL;
```

#### 方案 2：用户级设置默认激活（推荐单用户方案）

```sql
-- 设置该用户每次登录时自动激活所有拥有的角色

```

#### 方案 3：实例全局自动激活（推荐生产环境启用）
```sql
-- 在 my.cnf 中配置 activate_all_roles_on_login = ON
SET PERSIST activate_all_roles_on_login = ON;
```

#### 企业级强制角色（`mandatory_roles`）
对于全公司必须统一注入的安全监控、审计或限流角色，可通过 `mandatory_roles` 实现系统级强制绑定，即使用户被执行 `REVOKE` 也无法剥离：
```sql

```

## 6. 特权保护、部分撤销与高级安全加固机制 (Defensive Security & Privilege Hardening)

### 6.1 `SYSTEM_USER` 特权账号保护机制

在 MySQL 8.0.16 之前，只要某个管理员拥有 `CREATE USER` 或 `SUPER` 权限，他就可以随意修改 `root` 账号的密码、删除核心系统账号、或在排障时随意 `KILL` 掉关键后台复制线程。

MySQL 8.0.16 引入了 **`SYSTEM_USER` 动态权限**，在用户层面对账号实施“普通用户”与“系统级特权用户”的物理隔离：

```
SYSTEM_USER 权限隔离机制
┌──────────────────────────────────────┐       ┌──────────────────────────────────────┐
│ 普通管理员 (具备 CREATE USER, KILL)  │       │ 超级特权账号 (拥有 SYSTEM_USER 动态权限)
│ (如: ops_admin)                      │       │ (如: root, 云托管管控账号, 关键备份)
└──────────────────┬───────────────────┘       └──────────────────┬───────────────────┘
                   │                                              │
                   ├──────── 尝试 ALTER USER root / KILL root ────┤
                   │                                              │
                   ▼                                              ▼
            [Server 鉴权拦截] ──────────────────────────► 抛出 ERROR 1227 (42000):
                                                         Access denied; you need SYSTEM_USER
```

#### 实战配置
```sql
-- 1. 将 root 及核心自动化运维账号标记为系统级特权账号
GRANT SYSTEM_USER ON *.* TO 'root'@'localhost', 'cloud_master'@'127.0.0.1';

-- 2. 普通 DBA 运维账号仅授予常规管理权限，严禁授予 SYSTEM_USER
CREATE USER 'dba_junior'@'10.20.10.%' IDENTIFIED BY 'Junior#Pass2026';
GRANT CREATE USER, CONNECTION_ADMIN, SYSTEM_VARIABLES_ADMIN ON *.* TO 'dba_junior'@'10.20.10.%';

-- 此时: dba_junior 可以管理普通业务账号，但若尝试修改 root 密码或 KILL root 连接，将被系统强行拒绝！
```

---

### 6.2 `PARTIAL_REVOKES` 机制：实现全局授权下的库级挖洞

传统 MySQL 的权限模型是严格累加的。如果授予了 `GRANT SELECT ON *.* TO user`，则无法单独收回某个特定数据库（如 `mysql.*` 或 `hr_salary.*`）的查询权限。

MySQL 8.0 引入了 **`PARTIAL_REVOKES`（部分撤销机制）**，彻底解决了这一历史难题：

```sql
-- 1. 开启全局部分撤销特性 (需持久化)
SET PERSIST partial_revokes = ON;

-- 2. 赋予开发人员全局数据库只读权限
CREATE USER 'dev_audit'@'10.20.10.%' IDENTIFIED BY 'Audit#Pass_2026';
GRANT SELECT ON *.* TO 'dev_audit'@'10.20.10.%';

-- 3. 关键：从全局权限中精准“挖洞”，剥离核心敏感库的访问权限
REVOKE SELECT ON mysql.* FROM 'dev_audit'@'10.20.10.%';
REVOKE SELECT ON hr_salary.* FROM 'dev_audit'@'10.20.10.%';

-- 4. 验证权限 (可见全局授权后附带了 Restrictions 限制子句)
-- SHOW GRANTS FOR 'dev_audit'@'10.20.10.%';
-- 输出: GRANT SELECT ON *.* TO `dev_audit`@`10.20.10.%` RESTRICT ON `mysql`.*, `hr_salary`.*
```

### 6.3 视图、存储过程、函数与触发器的 `DEFINER` 提权安全防护

在 MySQL 中，视图（View）、存储过程（Procedure）、函数（Function）和触发器（Trigger）默认采用 `SQL SECURITY DEFINER` 模式执行：

```
DEFINER 垂直提权攻击漏洞机理
┌──────────────────────────────┐       ┌──────────────────────────────┐
│ 低权限普通用户 (dev_user)    │ ────► │ 视图: v_user_public          │
│ (仅有 v_user_public 查询权限)│ 查询  │ DEFINER = 'root'@'localhost' │
└──────────────────────────────┘       └──────────────┬───────────────┘
                                                      │ 以 root 最高特权身份执行底层查询
                                                      ▼
                                       ┌──────────────────────────────┐
                                       │ 绕过底层敏感表的权限拦截     │
                                       │ (甚至调用危险的底层提权函数) │
                                       └──────────────────────────────┘
```

#### 生产防范规程与最佳实践
1. **显式使用 `SQL SECURITY INVOKER`**：创建公开业务视图和子程序时，推荐指定 `INVOKER`，强制以当前调用者自身的权限执行鉴权：
   ```sql
   CREATE SQL SECURITY INVOKER VIEW v_user_public AS
   SELECT id, username, nickname, created_at FROM users;
   ```
2. **严禁使用 `root` 作为业务视图的 DEFINER**。
3. **第三方与大数据数据脱敏授权规程**：对外部调用方或数仓只读账号（如 `bigdata`），推荐使用非 root 专用定义者绑定 `DEFINER` 视图实现底层物理基表彻底隔离，具体单视图赋权标准 SOP 参见：[视图特权矩阵与大数据用户单视图安全授权 SOP](../02-进阶特性/05-视图_存储过程_触发器.md#18-视图权限管理与生产数据脱敏授权规程)。

#### 生产级自动化扫描与批量修复 DEFINER 的 SQL 脚本
```sql
-- 巡检 1: 扫描全库中 DEFINER 为 root 或已不存在用户的视图
SELECT table_schema, table_name, definer, security_type 
FROM information_schema.views 
WHERE definer LIKE 'root@%' OR security_type = 'DEFINER';

-- 修复脚本生成: 动态生成将 DEFINER 变更为专用只读账号或切换为 INVOKER 的 DDL
SELECT CONCAT(
  'ALTER DEFINER = \'app_view_definer\'@\'127.0.0.1\' SQL SECURITY INVOKER VIEW `', 
  table_schema, '`.`', table_name, '` AS ', view_definition, ';'
) AS fix_ddl
FROM information_schema.views
WHERE definer LIKE 'root@%' AND table_schema NOT IN ('sys', 'mysql', 'information_schema', 'performance_schema');
```

### 7.4 8.0.14+ 零停机双密码平滑轮换 (Dual Passwords) 实战演练

```
双密码零停机轮换生命周期时序
时间线 ──────────────────────────────────────────────────────────────────────────►
MySQL Server: [当前主密码: Pwd_V1] ───► [主: Pwd_V2 | 备用: Pwd_V1] ───► [主: Pwd_V2 (废弃旧密码)]
                                             ▲
                                             │ 兼容期 (主备双密码均可成功鉴权)
K8s Pods:    [全部 Pod 运行使用 Pwd_V1] ───► [逐步滚动发布新 Pod] ───► [全部 Pod 运行使用 Pwd_V2]
```

#### 四步标准实战演练

```sql
-- ====================================================================
-- 步骤 1: 设置新密码，同时保留当前密码作为 Secondary Password (备用密码)
-- ====================================================================
ALTER USER 'app_order_rw'@'10.20.10.%' 
  IDENTIFIED BY 'OrderApp_Pass_2026_V2' 
  RETAIN CURRENT PASSWORD;

-- 此时: 无论是挂载旧密码 V1 的老 Pod，还是挂载新密码 V2 的新 Pod，均能成功建立连接！

-- ====================================================================
-- 步骤 2: 触发 Kubernetes / 容器集群微服务滚动发布 (Rolling Update)
-- ====================================================================
-- 配置中心下发新密码 V2，K8s 逐步销毁旧 Pod 并拉起新 Pod。

-- ====================================================================
-- 步骤 3: 观测监控指标，确认所有旧连接已释放且新连接全部基于 V2 建立
-- ====================================================================

-- ====================================================================
-- 步骤 4: 废弃旧密码，关闭备用凭证通道 (回归单密码安全基线)
-- ====================================================================
ALTER USER 'app_order_rw'@'10.20.10.%' DISCARD OLD PASSWORD;
```

> [!TIP] 紧急故障一键回滚预案
> 若步骤 2 滚动发布期间应用配置异常需紧急终止发布并回滚，可随时执行：
> ```sql
> ALTER USER 'app_order_rw'@'10.20.10.%' IDENTIFIED BY 'OrderApp_Pass_2026_V1' DISCARD OLD PASSWORD;
> ```
> 瞬间将密码还原至 V1，无需改动数据库其他结构。

## 9. 分布式主从与 MGR 集群下的权限同步陷阱 (Replication & HA Considerations)

### 9.1 主从复制中 `mysql` 系统库同步的陷阱

在 MySQL 主从复制拓扑中，`mysql` 库的 DCL 语句通过 Binlog 进行复制：

```
主从复制权限同步流转
Master Node (执行 DCL) ──► 写入 Binlog (GTID 事务) ──► Slave I/O Thread ──► Relay Log ──► SQL Thread 回放
```

- **陷阱 1：`replicate-wild-do-table=mysql.%` 导致从库特有账号被冲掉**：
  若在从库配置了全量强制同步 `mysql` 库，主库上的所有用户变更会全量覆盖从库。如果从库部署了独立的备份账号、监控账号或只读白名单，这些特有权限元数据将被破坏。
- **陷阱 2：直接在从库底层修改系统表导致 GTID 漂移**：
  在 MySQL 8.0 中，严禁在从库手工执行底层 DML 修改 `mysql` 表，否则会导致主从元数据校验不一致或产生主从冲突。

---

### 9.2 `sql_log_bin = 0` 会话级隔离授权的正确使用规范

当需要在某个主库或从库上配置**单机特有的本地运维账号**（如单机专用的物理备份脚本账号）时，可通过会话级关闭 Binlog 写入来阻断复制流转：

```sql
-- 必须具备 SESSION_VARIABLES_ADMIN 或 SYSTEM_VARIABLES_ADMIN 权限
SET sql_log_bin = 0;
CREATE USER 'local_backup'@'127.0.0.1' IDENTIFIED BY 'Local#BkpPass_2026';
GRANT BACKUP_ADMIN, PROCESS, RELOAD ON *.* TO 'local_backup'@'127.0.0.1';
SET sql_log_bin = 1;
```

> [!WARNING] 生产红线
> 执行完毕后**必须立即恢复 `SET sql_log_bin = 1`**，切忌遗漏导致后续业务变更丢失 Binlog。

---

### 9.3 `read_only` / `super_read_only` 对权限操作的边界影响

- **`read_only = ON`**：阻断所有无 `SUPER` / `CONNECTION_ADMIN` 权限的普通用户的 DML/DDL。
- **`super_read_only = ON`**：阻断**包括超级管理员在内的所有人**执行 DML/DDL。在此模式下，执行 `CREATE USER`、`GRANT` 等 DCL 语句也会被直接阻断（仅从库 SQL 回放线程不受影响）。
- 在执行 MGR 或主从切换容灾维护前，必须充分考虑 `super_read_only` 对自动化授权工具的影响。

### 10.1 权限安全审计与自动化合规巡检 SQL 资产库

```sql
-- ====================================================================
-- 巡检 1: 探测拥有通配符 '%' 的高危账号 (违反内网白名单准入规范)
-- ====================================================================
SELECT user, host, plugin, account_locked, password_expired 
FROM mysql.user 
WHERE host = '%' AND user NOT IN ('health_checker');

-- ====================================================================
-- 巡检 2: 探测具备全局高危权限 (SUPER, GRANT OPTION, ALL) 的非 DBA 账号
-- ====================================================================
SELECT user, host, Super_priv, Grant_priv, Reload_priv, Shutdown_priv 
FROM mysql.user 
WHERE (Super_priv = 'Y' OR Grant_priv = 'Y') 
  AND user NOT IN ('root', 'mysql.session', 'mysql.infoschema', 'dba_admin');

-- ====================================================================
-- 巡检 3: 探测仍在使用老旧不安全 mysql_native_password 插件的账号
-- ====================================================================
SELECT user, host, plugin 
FROM mysql.user 
WHERE plugin = 'mysql_native_password';

-- ====================================================================
-- 巡检 4: 探测密码为空或密码永不过期的账号
-- ====================================================================
SELECT user, host, authentication_string, password_expired, password_lifetime 
FROM mysql.user 
WHERE authentication_string = '' OR authentication_string IS NULL;

-- ====================================================================
-- 巡检 5: 探测视图中 DEFINER 为 root 的高危提权隐患对象
-- ====================================================================
SELECT table_schema, table_name, definer, security_type 
FROM information_schema.views 
WHERE definer LIKE 'root@%' AND security_type = 'DEFINER';

-- ====================================================================
-- 巡检 6: 探测 8.0 动态权限中拥有 SYSTEM_VARIABLES_ADMIN 或 PERSIST_ROLES_ADMIN 的账号
-- ====================================================================
SELECT user, host, priv, with_grant_option 
FROM mysql.global_grants 
WHERE priv IN ('SYSTEM_VARIABLES_ADMIN', 'PERSIST_ROLES_ADMIN', 'SYSTEM_USER');
```

### 10.2 Root 密码丢失安全应急重置 (5.7 vs 8.0 差异化救援)

```
安全救援黄金第一定律：
救援启动时必须显式添加 --skip-networking 参数！
严禁在无权限控制模式下向网络暴露 TCP 端口，防止内网扫描器或恶意程序瞬间免密登入删库！
```

```bash
# 步骤 1: 优雅停止 mysqld
systemctl stop mysqld

# 步骤 2: 安全单机救援模式拉起实例 (禁用网络端口，仅监听本地 UNIX Socket)
mysqld --user=mysql --skip-grant-tables --skip-networking &

# 步骤 3: 本地 Socket 登录
mysql -u root -S /var/lib/mysql/mysql.sock
```

```sql
-- 步骤 4: 执行密码重置
-- 关键: 必须先执行 FLUSH PRIVILEGES 载入内存 ACL 结构！
FLUSH PRIVILEGES;

-- MySQL 8.0+ 语法:
ALTER USER 'root'@'localhost' IDENTIFIED WITH caching_sha2_password BY 'NewRoot#Secure_2026_80!';

-- MySQL 5.7 语法:
-- ALTER USER 'root'@'localhost' IDENTIFIED BY 'NewRoot#Secure_2026_57!';
```

```bash
# 步骤 5: 杀掉救援进程，恢复正常网络服务
kill -9 $(pgrep -f "mysqld.*skip-grant-tables")
systemctl start mysqld
```

### 10.4 生产环境一键反向导出并生成权限重构 SQL 脚本 (DCL Re-engineering Script)

DBA 可在数据库迁移或权限重构时，通过以下 Python 自动化脚本一键提取并反向生成全量用户的 `CREATE USER`、`ALTER USER` 与 `GRANT` 声明式 DCL：

```python
#!/usr/bin/env python3
# -*- coding: utf-8 -*-
"""
MySQL 8.0 权限全景声明式反向提取脚本 (DCL Re-engineering Script)
用途: 自动化提取当前实例所有非系统用户的创建、密码哈希、属性与精准授权语句
"""

import pymysql

DB_CONFIG = {
    'host': '127.0.0.1',
    'port': 3306,
    'user': 'root',
    'password': 'YourSecurePassword2026!',
    'charset': 'utf8mb4',
    'cursorclass': pymysql.cursors.DictCursor
}

IGNORE_USERS = (
    'root', 'mysql.sys', 'mysql.session', 
    'mysql.infoschema', 'health_checker'
)

def export_dcl():
    conn = pymysql.connect(**DB_CONFIG)
    try:
        with conn.cursor() as cursor:
            # 1. 提取所有业务用户
            cursor.execute("""
                SELECT user, host, plugin, authentication_string, 
                       account_locked, password_expired 
                FROM mysql.user 
                WHERE user NOT IN %s
            """, (IGNORE_USERS,))
            users = cursor.fetchall()
            
            print("-- ========================================================")
            print("-- 1. 用户创建与凭证还原 (CREATE USER & RESTORE CREDENTIALS)")
            print("-- ========================================================")
            for u in users:
                create_sql = f"CREATE USER IF NOT EXISTS `{u['user']}`@`{u['host']}` "
                create_sql += f"IDENTIFIED WITH {u['plugin']} AS '{u['authentication_string']}';"
                print(create_sql)
                if u['account_locked'] == 'Y':
                    print(f"ALTER USER `{u['user']}`@`{u['host']}` ACCOUNT LOCK;")
            
            print("\n-- ========================================================")
            print("-- 2. 权限与角色分发 (GRANT STATEMENTS)")
            print("-- ========================================================")
            for u in users:
                cursor.execute(f"SHOW GRANTS FOR `{u['user']}`@`{u['host']}`")
                grants = cursor.fetchall()
                for g in grants:
                    grant_stmt = list(g.values())[0]
                    print(f"{grant_stmt};")
                    
    finally:
        conn.close()

if __name__ == '__main__':
    export_dcl()
```
