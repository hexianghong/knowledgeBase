## 三、 高频核心面试专题与标准深度解答 (Deep-Dive QA)

### 专题 1：InnoDB 内核与内存管理

#### Q1: 请详细阐述 InnoDB Buffer Pool 的冷热分离 LRU 算法，以及它是如何防止全表扫描导致缓存污染的？
* **标准解答**：
  * **问题本质**：传统 LRU 算法在遇到 `SELECT *` 等大表扫描时，会将大量只读取一次的“冷页”直接装载到 LRU 头部，将真正高频访问的“热页”挤出内存，造成严重的缓存污染（Cache Pollution）。
  * **InnoDB 分段设计**：InnoDB 将 LRU 链表按比例分为 **Young 区域（热数据区，约 58%）** 和 **Old 区域（冷数据区，约 42%）**。
  * **加载与沉淀机制**：
    1. 磁盘新读取的数据页**优先插入 Old 区域的头部**，而不是 Young 区域。
    2. 配合参数 `innodb_old_blocks_time`（默认 1000ms）。只有当该页在 Old 区停留时间超过 1s 且**再次被访问**时，才会提升到 Young 区域头部。
    3. 全表扫描的数据页在 1s 内被多次读取后便不会再被触碰，直接留在 Old 区快速老化淘汰，彻底保障了 Young 区热点数据的物理稳定性。

---

#### Q2: 请解释什么是 Partial Page Write（部分页写入失效），InnoDB 是如何通过 Doublewrite Buffer 保障 Crash-Safe 的？
* **标准解答**：
  * **失效根因**：InnoDB 的数据页物理大小为 16KB，而 Linux 文件系统的物理 Sector/Page 通常为 4KB。当内存脏页刷写磁盘时，如果写到第 8KB 时服务器突然断电，导致物理页在磁盘上损坏（前 8K 是新数据，后 8K 是旧数据）。此时 Checksum 校验失败，物理页结构损坏，导致 **Redo Log 无法在坏页上进行崩溃重放**。
  * **Doublewrite 原理**：在脏页写入 `.ibd` 数据文件前，InnoDB 会先将 16KB 物理页**顺序写入**内存的 Doublewrite Buffer，并 `fsync` 到磁盘的独立双写表空间（MySQL 8.0 为独立的 `ib_doublewrite` 文件）。然后再将脏页**随机写入**对应的数据文件。
  * **崩溃恢复**：若崩溃重启发现某页 Checksum 校验失败，InnoDB 直接从 Doublewrite 恢复该页的完整物理镜像，随后再重放 Redo Log 完成恢复。

### 专题 2：事务、MVCC 与并发锁机制

#### Q3: 请详细推导 InnoDB 的 ReadView 可见性判定算法，并说明 RC 和 RR 隔离级别的本质物理区别？
* **标准解答**：
  * **ReadView 核心结构**：包含 `m_ids`（活跃未提交事务列表）、`min_trx_id`（最小活跃 ID）、`max_trx_id`（下一个待分配 ID）、`m_creator_trx_id`（当前事务 ID）。
  * **判定公式**：遍历行记录 Undo 版本链的 `DB_TRX_ID`：
    1. 若 `DB_TRX_ID == m_creator_trx_id`：本事务修改，可见。
    2. 若 `DB_TRX_ID < min_trx_id`：生成 ReadView 前已提交，可见。
    3. 若 `DB_TRX_ID >= max_trx_id`：生成 ReadView 后才开启，不可见。
    4. 若 `min_trx_id <= DB_TRX_ID < max_trx_id`：若在 `m_ids` 中说明尚未提交，不可见；不在 `m_ids` 中说明已提交，可见。
  * **RC 与 RR 物理区别**：
    * **RC**：事务中**每次执行 `SELECT` 均重新生成一个 ReadView**。
    * **RR**：仅在事务中**第一次执行 `SELECT` 时生成一个 ReadView**，后续完全复用。

---

#### Q4: 在 RR 隔离级别下，非唯一普通索引进行等值查询时，Next-Key Lock 是如何锁定的？为什么会有退化？
* **标准解答**：
  * **锁机制**：Next-Key Lock 是记录锁与间隙锁的组合，默认闭区间 $(a, b]$。
  * **退化规则**：当对非唯一二级索引做等值查询时：
    1. 对匹配到的记录加 Next-Key Lock $(a, b]$；
    2. 继续向右扫描遍历到第一个不满足条件的记录 $c$，将该右侧区间退化为**间隙锁 (Gap Lock)** $(b, c)$；
    3. 最终锁定的物理范围是开区间 $(a, c)$，防止并发插入导致幻读。

### 专题 3：日志系统、两阶段提交与高可用架构

#### Q5: 请说明 MySQL 内部两阶段提交 (2PC) 的物理流程，如果 Crash 发生在 Prepare 或 Commit 阶段，MySQL 如何恢复？
* **标准解答**：
  * **2PC 流程**：
    1. **Prepare 阶段**：InnoDB 将事务状态置为 PREPARE，将 Redo Log 刷盘 (`fsync`)。
    2. **Commit 阶段**：Server 层将 Binlog 刷盘 (`fsync`)；随后在 Redo Log 写入 COMMIT 标记并释放事务锁。
  * **Crash 恢复判定**：
    * 若 Crash 在 Redo Log Prepare 后、Binlog 刷盘前：系统重启扫描发现 Redo 为 Prepare 状态，但 Binlog 中无该 XID，**直接执行 ROLLBACK**。
    * 若 Crash 在 Binlog 刷盘后、Redo COMMIT 前：扫描发现 Redo 为 Prepare 状态，且在 Binlog 中找到了完整 XID，**强制执行 COMMIT**，保障主从数据绝对一致。

### 专题 4：MySQL 5.7 升级到 8.0/8.4 架构演进与避坑深度考核

#### Q6: 请系统性总结 MySQL 8.0 相比 5.7 在内核架构、权限体系、DDL 及高并发上有哪些重大革新？
* **标准解答**：
  1. **元数据与原子 DDL**：废弃 `.frm` 文件与 MyISAM 系统表，全量集成至 InnoDB 事务型数据字典，支持 Atomic DDL。
  2. **权限解耦与角色**：废除 `SUPER` 一权独大，解耦为 30+ 细粒度动态权限（Dynamic Privileges）；原生支持 RBAC 角色体系与双密码（Dual Passwords）零停机改密。
  3. **在线 DDL**：引入 Instant DDL，实现表尾及任意位置加列秒级完成，大幅减少对 `gh-ost` 等第三方工具的依赖。
  4. **复制与性能**：MTS 默认引入 `WRITESET` 依赖追踪，彻底消除从库复制延迟；引入 Hash Join 替代 BNL；提供 `NOWAIT` / `SKIP LOCKED` 秒杀高并发语法。
  5. **自增与持久化**：自增计数器变更实时写入 Redo Log，彻底解决 5.7 重启自增 ID 复用 Bug；支持 `SET PERSIST` 参数持久化。

## 四、 真实生产故障突发应对 STAR 实战案例库

### 案例 1：主库 CPU 100% 与全库锁阻塞紧急救援 (SOP)

```
【Situation 场景】
某核心交易数据库在促销期间 CPU 爆发式冲高到 100%，大量的 SQL 堆积在 Waiting for table metadata lock 与 Lock Wait 状态，线程数突破 2000，应用连接池爆满。

【Task 任务】
在 3 分钟内完成紧急止血，找到死锁/长事务排头兵，恢复数据库可用性，随后完成 Root Cause Analysis (RCA)。

【Action 行动】
1. 登录管理端口: 通过预留的管理端口 (33062) 使用专职账号紧急登录。
2. 查找源头排头锁: 运行 performance_schema 锁查询 SQL，定位到一个运行了 1800 秒的慢事务 (源自某报表导出 SQL)。
3. 判定与干预: 确认该长事务持有 MDL 锁，阻塞了 ALTER TABLE 与后续写操作。直接执行 KILL [thread_id] 终止该慢查询。
4. 应急善后: 临时调高 max_connections 至 3000，限制报表账号的并发连接数。

【Result 结果】
数据库 CPU 在 30 秒内恢复至 15% 正常水平，连接池降至 200，系统恢复服务。事后规范了报表查询走独立只读从库的规约。
```
